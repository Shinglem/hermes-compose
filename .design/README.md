## 写作规则

1. **一篇文档一个主题**。不要把选型和架构混在一起。
2. **数字要给口径**。行数、成本、尺寸都注明来源与计算方法（例：`草案/01-feasibility.md` 的口径声明）。
3. **决策写进 ADR**，不要散落在正文里。改了主意就加新编号，不改旧编号。
4. **坑要写三件事**：现象、原因、规避方式。只写现象等于没写。
5. **不做清单和做清单同等重要**。"我们决定不做 X" 必须留痕，否则下一个 agent 会重新提议。
6. **草案与详细设计不重复**：草案写取舍与结论，详细设计写可直接照着实现的结构、数值与映射。
7. **视觉稿不是像素基准**：UI 视觉稿（HTML）只作参考，且本身不严格遵循 M3；实现用 M3 + Compose 原生，
   允许差异。详见 `AGENTS.md` 硬约束 12 与 `详细设计/UI设计/README.md`。

## 变更流程

| 变更类型 | 做法 |
|---|---|
| 新增功能 / 改范围 | 先改 `草案/00-overview.md` + `草案/06-roadmap.md`，再动代码 |
| 换库 / 加依赖 | 先查 `.ai/skill/compose-multiplatform-desktop/references/component-selection.md`，再改 `草案/02-selection.md` |
| 改架构 | 加一条 ADR，然后改 `草案/03-architecture.md` |
| 改验收标准 | 改 `草案/05-acceptance.md`，并在提交信息里说明原因 |
| 改 UI 视觉或组件结构 | 改 `详细设计/UI设计/`，并回写 `草案/04-ui-spec.md` 里受影响的口径 |
| 发现文档与实现不符 | 优先改文档；若实现更优，把原因写进 ADR |
