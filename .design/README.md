# .design · 设计文档

> **本目录是设计的事实源。** 代码与文档冲突时，以本目录为准（或先改文档，并记录偏差）。
> **基线：v0.6.0（2026-11-15）** —— 描述的是**已落地**的形态，不是计划。
>
> 规则（编码规范、硬约束、提交纪律）的**唯一权威源是仓库根的 [`AGENTS.md`](../AGENTS.md)**，
> 本目录只解释「为什么」与「怎么做」。

```

└── 待修复问题-归档.md 已修完 / 已定论 / 明确不做的
```

## 写作规则

1. **一篇文档一个主题**。不要把选型和架构混在一起。
2. **数字要给口径**。行数、成本、尺寸都注明来源与计算方法。
3. **决策写进 ADR**，不要散落在正文里。改了主意就加新编号，不改旧编号。
4. **坑要写三件事**：现象、原因、规避方式。只写现象等于没写。
5. **不做清单和做清单同等重要**。"我们决定不做 X" 必须留痕，否则下一个 agent 会重新提议。
6. **草案与详细设计不重复**：草案写取舍与结论，详细设计写可直接照着实现的结构、数值与映射。
7. **规则不进本目录**：编码规范、硬约束、提交纪律一律写 `AGENTS.md`，这里只链接。
8. **计划类文档执行完就归档**：不要把已完成的计划留在正文里冒充现状 —— 这是下一次
   「文档与实现不符」的来源。归档时把仍然有效的结论提炼进常设文档。
9. **视觉稿不是像素基准**：见上。

## 变更流程

| 变更类型 | 做法 |
|---|---|
| 新增功能 / 改范围 | 先改 `草案/00-overview.md`，再动代码 |
| 换库 / 加依赖 | 先查 `search.maven.org` 与许可证，再改 `草案/02-selection.md` |
| 改架构 | 加一条 ADR，然后改 `草案/03-architecture.md` |
| 改验收标准 | 改 `草案/05-acceptance.md`，并在提交信息里说明原因 |
| 改 UI 视觉或组件结构 | 改 `详细设计/UI设计/`，并回写 `草案/04-ui-spec.md` 里受影响的口径 |
| 某个计划执行完 | 提炼有效结论 → 原文移入 `归档/` |
| 发现文档与实现不符 | 优先改文档；若实现更优，把原因写进 ADR |
