### #1 原生集成能否改用 Nucleus 生态（托盘 / WebView / 打包）

- **类型**：改进（技术调研，非缺陷）
- **优先级**：P2
- **涉及层**：平台集成（托盘 / 通知 / 单实例 / 自启 / 提权）、打包链
- **调研日期**：2026-11-04，基线 v0.4.0（commit `f04da8b`）

**结论**：
1. **托盘可换**（L1.5 试点，独立依赖、不拉 Tao）。
2. **WebView 有第二个用途**：不是替换 Markdown 渲染，而是**给 hermes 的浏览器操作能力做界面**（整窗口浏览器面板）。这条路可行，但前提是整个窗口壳迁到 Nucleus Tao，属 L1.5 大改；消息内嵌 HTML 仍走 JCEF OSR，两者互补。
3. **单实例 / 自启 / 提权不换**：Nucleus 的计划任务明确用 `TASK_RUNLEVEL_LUA`（普通权限），做不到我们"最高权限 + 无 UAC"；提权重启无对应模块；单实例能互斥但语义不同（见下）。
4. **打包不换**：Nucleus packaging 解决"生成安装包"，我们自研的是"纯外壳 + payload 分离 + toolchain 版本化解耦 + 计划任务安装"，不在同一层。

#### 托盘为什么可换

- 它绕开了我们自绘的**同一个理由**：`UnicodeTrayDemo` 明确验证"UTF-8 → UTF-16"（法语 / 中文 + 特殊标点），Windows 走自家 native 桥（`WindowsNativeBridge.nativeCreateTray(iconPath, tooltip)`），不是 AWT `PopupMenu` 的 ANSI 转换路径 —— 即 CMP-1936 的成因。
- 白送的能力：HDPI 修复、`primaryAction`（左键）、勾选 / 子菜单 / 分隔线、托盘位置探测、菜单随 Compose 重组刷新。
- 依赖面小：只引 `composenativetray`，**不**拉 `decorated-window-tao`（2.1.0 按 issue #418 拆包）；要求 CMP 1.12.0（我们一致）、JDK 17+（我们 Temurin 27）、Gradle 9.0+。

#### WebView 接入 hermes 浏览器能力：可行，但要先迁 Tao

**hermes 侧能力（已核实）**：
- `tools/browser_tool_cdp.py:14 _resolve_cdp_override(cdp_url)`：接受 `http://host:port`、`ws://…`、完整 `/devtools/browser/…`；给 HTTP 根时去 `/json/version` 取 `webSocketDebuggerUrl`。
- 入口两处：`browser.cdp_url`（config.yaml）与 `/browser connect`（会话内，按 profile 隔离 —— 同文件 `_live_overrides`）。
- 结论：**不改后端**，把 `browser.cdp_url` 指向我们的 WebView2，它就能操作并复用页面。
- payload 另有 browser_use / browserbase（云 CDP）、firecrawl（抓取）、agent-browser（自带 Chromium）。

**WebView2 侧（已核实）**：
- `composewebview` 桌面 = Tao `NativeView` + WebView2 `CreateCoreWebView2CompositionController`（DirectComposition 合成）→ 适合**整窗口**，不适合嵌进 LazyColumn（无 OSR）。
- 库已暴露 `enableDevtools` / `openDevTools()` / `closeDevTools()`；native 走 `CreateCoreWebView2EnvironmentWithOptions`。
- 未暴露 `AdditionalBrowserArguments`；但 WebView2 支持进程级 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS`（微软文档用它传 Chromium 开关），`--remote-debugging-port=<port>` 可试 —— **必须实测**。
- 体积与性能现状：`cef/` 是随包 **310.4 MB** 的 Chromium 135；系统 WebView2 Runtime 是 `156.0.4314.58`（随 Edge 更新）。分发体积与冷启动 WebView2 占优；代价是版本随系统漂移。

**接入形态（spike 目标）**：

```text
nucleusApplication(backend = Tao, enableSingleInstance = false)   // 保留自研单实例
  └ 窗口内 WebView2 面板
启动前设 WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=<随机端口>
browser.cdp_url = http://127.0.0.1:<端口>                          // 用户配置，不改后端
```

**必须先验的四点**：

1. WebView2 是否真的监听该端口并提供 `/json/version`（不支持就退化成分叉 native 暴露 `CallDevToolsProtocolMethod`，成本陡增）。
2. hermes 常用动作在该 WebView2 上是否完整：`Input.*` 点击/键入、`Page.captureScreenshot`、多标签 `Target`。
3. 安全：CDP 端口等于完整浏览器控制权（含 cookie），只能绑 `127.0.0.1`、随机端口、用完即关；且宿主进程是管理员（我们的提权形态）。
4. Tao 迁移回归面：[Main.kt](../composeApp/src/desktopMain/kotlin/dev/shinglem/hermes/Main.kt)（396 行）的窗口创建、自研单实例、托盘、提权、自启都要重新对齐；Tao 把触摸降为 `Pan` 事件，`touchDragScroll` 需重测。

#### 单实例 / 自启 / 提权：不用的具体理由

- **自启（硬理由）**：Nucleus `scheduler` 的 Windows 原生实现是
  `principal->put_LogonType(TASK_LOGON_INTERACTIVE_TOKEN)` + `principal->put_RunLevel(TASK_RUNLEVEL_LUA)`
  （`scheduler/src/main/native/windows/nucleus_scheduler.cpp`）—— **LUA = 普通权限**。
  我们 [ScheduledAutostart.kt](../composeApp/src/desktopMain/kotlin/dev/shinglem/hermes/core/app/ScheduledAutostart.kt) 写的是
  `<RunLevel>HighestAvailable</RunLevel>`（:295）+ `InteractiveToken`（:294）+ `<Arguments>--silent</Arguments>`（:310），
  注释还解释了为什么不用 `RequireHighest`（非管理员用户会直接失败）与 `S4U`（无 UI 会话加不上托盘）。
  换过去 = 登录后只有普通权限：要么每次 UAC 弹窗，要么托盘进程无权做需要管理员的事。
  `autolaunch` 更远：Windows 只有 `Win32RegistryBackend`（HKCU Run）与 `MsixStartupTaskBackend`（MSIX），做不到提权。
- **提权**：Nucleus 的 40+ 模块里没有"以管理员重启/提权"对应物，[Elevation.kt](../composeApp/src/desktopMain/kotlin/dev/shinglem/hermes/core/app/Elevation.kt) + [ElevationRelaunch.kt](../composeApp/src/desktopMain/kotlin/dev/shinglem/hermes/core/app/ElevationRelaunch.kt)（326 行）只能自研。
- **单实例**：Nucleus `SingleInstanceManager` 用**文件锁**（`FileChannel.lock` + `WatchService`）；我们的 [SingleInstance.kt](../composeApp/src/desktopMain/kotlin/dev/shinglem/hermes/core/app/SingleInstance.kt) 用 **`CreateMutexW`**，且 `Main.kt:84-90` 有"`--silent` 的第二次触发只记录、不抢前台"的语义。
  技术上可换，但我们会传 `enableSingleInstance = false`（Tao 迁移时同样），因为它给不了这条语义 —— 换它没有收益。

#### 打包：覆盖到哪一层

| 我们依赖的 | 位置 | Nucleus packaging 能否覆盖 |
|---|---|---|
| 出安装包（MSI / exe / DMG …） | — | ✅ 能（`AbstractJPackageTask` / `AbstractElectronBuilderPackageTask`） |
| 纯外壳、**不含 payload**（用户自备 `hermes/`） | `desktop-release.yml:152-154` 显式校验 `release-test\hermes` 不存在 | ❌ 不涉及（它默认打完整应用目录） |
| 启动器 + 裁剪运行时**独立版本化**（`toolchain-v1`，只增不改） | `toolchain-windows.yml` → `launcher-*.zip` / `runtime-*.zip` | ❌ 不涉及（运行时打进应用） |
| `--silent` 启动器契约、`app/*.cfg`、`startup.log` | `packaging/App.bat`、自写 launcher | ❌ 不涉及 |
| 计划任务安装/对账、提权重启 | `ScheduledAutostart.kt` / `Elevation*` | ❌ 不涉及 |

结论：它解决"打包器"那一层；我们换不起的是**流程层**（两段式 CI + toolchain 版本化解耦 + 纯外壳 + payload 分离）。只发 Windows 便携 7z、不做商店签名分发的前提下收益接近 0，不换。

### #2 内置文件查看/编辑能否直接用 BossConsole 的编辑器

- **类型**：改进（能力评估，触发产品范围决策）
- **优先级**：P2
- **涉及层**：UI（编辑器）/ 产品范围（ADR-005「不做内置编辑器」）
- **调研日期**：2026-11-04

**先澄清对象**（链接里的那个模块不是编辑器）：

- [`modules/boss-app-editor`](https://github.com/risa-labs-inc/BossConsole/tree/main/modules/boss-app-editor) 是**独立进程的 gRPC 服务**：`EditorServiceImpl`（477 行）只做 `open_file` / `write_file` / `detect_main_functions`，依赖 `:boss-ipc` 的 protobuf 契约；真正的「BossEditor + LSP + PSI」在 composeApp 里（其注释原文："GetTokens / NavigateToDefinition: require PSI (in composeApp)"）。
- 真正的编辑器是另一个仓库的制品：**`com.risaboss:bosseditor-compose-desktop:1.0.26`**（Maven Central 有 `jar` / `sources.jar` / `javadoc.jar` + `.asc` 签名，Apache-2.0，最近发布 2026-09-17）。
- 但 `github.com/risa-labs-inc/BossEditor` 现在返回 **404**（无公开 issue / 文档渠道，只有制品可查）。

**为什么不能直接用（硬伤）**：

- 主编辑区是**自绘 Canvas**：`rendering/EditorCanvas.kt`（39.9 KB）、`rendering/EditorCanvasRenderer.kt`（62.7 KB）。
- 文本输入靠按键码：`input/EditorInputHandler.kt:417` `val codePoint = event.utf16CodePoint; val char = codePoint.toChar()` —— 这是**唯一**的字符输入路径（全仓只有这一处 `utf16CodePoint`）。
- Compose Desktop 上，**输入法组合态不走 KeyEvent**（走 `TextInputService` / `BasicTextField` 的 IME 通道）；`utf16CodePoint` 只对物理按键直接映射的字符有效。
- 后果：**中文输入法打不出字**（连注释、搜索框里的中文都不行），且 `toChar()` 只取 BMP —— 代理对（emoji 等）也会坏。对中文优先的应用是致命项。
- 对照：`LargeFileViewer.kt:358` 用的是 `BasicTextField`（只读查看器），说明作者知道两种输入方式的差别，主编辑器选了自绘。

**其他适配成本**（就算 IME 能接受）：

| 项 | BossEditor 1.0.26 | 我们 | 风险 |
|---|---|---|---|
| Compose | 1.9.3（material3 1.9.0） | 1.12.2 | 跨三个小版本的 runtime/ui |
| Kotlin | 2.1.21 | 2.4.21 | 元数据一般向后兼容，但下面那条不是元数据问题 |
| PSI | `kotlin-compiler-embeddable 2.1.21`（go-to-definition） | 项目 Kotlin 2.4.21 | 同一 classpath 出现两代 `org.jetbrains.kotlin.*`，冲突面大；体积再涨 |

**如果确实要做内置编辑**（需先改 ADR-005 的产品决策）：

1. **JCEF + Monaco / CodeMirror**：我们已有 CEF OSR（`cef/` 310 MB 随包，`CefBrowserOsrWithHandler`），Chromium 自己处理 IME（中文天然可用），JS↔Kotlin 桥在 markdown-one 里已有先例。
2. **只读查看**：用 markdown-one 的代码块渲染 + `SelectionContainer`（现成），不引编辑器。

### #3 WebView2 的定位：能否替代 JCEF、能否做文件编辑器

- **类型**：改进（技术路线评估）
- **优先级**：P2
- **涉及层**：UI 渲染 / 打包体积 / 产品范围（ADR-005）
- **调研日期**：2026-11-04

#### 别人的 webview 实现有多复杂

- BossConsole 里**没有 UI 层 WebView**：`modules/boss-app-browser` 与 `boss-app-editor` 一样是**独立进程的 gRPC 服务**（`BrowserServiceImpl` 14.6 KB），全仓没有 `.cpp` 或 WebView 封装。
- 可直接参考的是 ComposeNativeWebview 的 Windows 实现（`webview-compose/src/jvmMain/native/windows` + `.../web/windows`）：

| 文件 | 行数 |
|---|---|
| `view_lifecycle.cpp` | 463 |
| `navigation.cpp` | 227 |
| `cookies.cpp` | 167 |
| `view_signals.cpp` | 155 |
| `view_input.cpp` | 154 |
| `jni_bridge.cpp` | 120 |
| `screenshot.cpp` | 85 |
| `javascript.cpp` | 31 |
| `compose_webview_internal.h` | 120 |
| **C++ 合计** | **≈ 1522** |
| `WindowsWebView2NativeWebView.kt` | 255 |
| `WebView2WindowsBridge.kt` | 224 |

即 **≈ 2000 行**，且不含 Tao 提供的窗口与输入。

#### 关键限制：WebView2 没有离屏渲染

- `ICoreWebView2CompositionController` 是 DComp 视觉，输入要**手动转发**（`view_input.cpp` 通篇是 `SendMouseInput`）。
- 唯一的"像素"能力是 `CapturePreview`（一次性 PNG，见 `screenshot.cpp`），不是帧流。
- 官方 issue **#547 "Off-screen rendering with webview2" 至今 open**（138 条评论）。
- → **不能替代 JCEF 做消息内嵌**：我们用的是 `CefBrowserOsrWithHandler` + `windowless_rendering_enabled=true`，帧进 Compose 图元，可随 LazyColumn 裁剪。

#### 自研 WebView2 组件（只做整窗口/固定面板）可行

| 路线 | 关键 API | 估量 | 风险 |
|---|---|---|---|
| **HWND 子窗口**（推荐） | JNA `CreateWindowEx` + `SetWindowPos` + WebView2 `put_ParentWindow` | 600-900 行 Kotlin/JNA，**无 C++** | 原生子窗口永远压在 Compose 之上：裁剪、圆角、滚动、弹层遮挡只能靠布局规避 |
| DComp 合成 | C++ + `CreateCoreWebView2CompositionController` + 手动输入转发 | 1500-2000 行 | 与 AWT/Skia 抢 Z 序；Nucleus 敢走是因为有 Tao 窗口 |
| Tao（现成） | 直接用 `composewebview` | 0 行 | 换整个窗口壳（见 #1） |

#### 用 WebView2 做文件编辑器：可行，但不是必需

- 形态：WebView2 加载 Monaco / CodeMirror，IME 由 Chromium 处理（中文没问题），文件 I/O 走 JS bridge。
- 但**同一套前端在 JCEF 上也能跑**，而我们已有 `cef/`（310 MB）与 OSR —— 编辑器面板直接用 JCEF，**零新增 native 代码**。
- WebView2 唯一优势是省掉 310 MB 随包体积（系统已有 WebView2 `156.x`），代价是 600+ 行自研 + 失去 OSR（不能叠在 Compose 内容里，只能是固定矩形）。
- 结论：**保持 JCEF 时编辑器成本最低；只有确定要砍掉 `cef/` 310 MB 才值得自研 WebView2。**
- 两者都触碰 ADR-005（"不做内置编辑器"），需先改产品决策。

#### 建议顺序

1. 近期要做"浏览器面板"：先用 **JCEF 全窗口**（零新增）验证 `browser.cdp_url` 链路与交互 —— 同时服务 #1 的 spike 6-7。
2. 面板验证通过且确需省体积：再做 HWND 版 WebView2 spike（先只做 navigate + JS bridge，不含 cookie/截图）。
3. 文件编辑器：等 ADR-005 改完再评估，优先 JCEF + Monaco。

#### 验证口径

- 自研 WebView2 的最小验收：窗口缩放时视图跟随不错位、输入框能用微软拼音打中文、`Ctrl+C/V` 生效、关闭面板不泄漏进程。
- **"替代 JCEF"没有验收路径**：要求"把一帧 HTML 贴进 LazyColumn item 并随滚动裁剪"，而 WebView2 不具备该能力（issue #547）。

### #4 升级 JCEF 到 152 并启用 markdown 的 JCEF 托底

- **类型**：缺陷（托底链路在当前依赖下不可用）+ 改进（依赖升级）
- **优先级**：**P1**（一旦启用托底即抛异常）
- **涉及层**：Markdown 渲染（`modules/markdown-one` submodule）/ 打包（`cef/` 体积）
- **调研日期**：2026-11-04

#### 版本坐标已经对上（升级本身很轻）

| 组件 | 当前 | 最新（2026-09-30） |
|---|---|---|
| `me.friwi:jcefmaven` | `135.0.20` | **`152.0.6`** |
| `me.friwi:jcef-api` | `jcef-ca49ada+cef-135.0.20+ge7de5c3+chromium-135.0.7049.85` | `jcef-17e805a+cef-152.0.6+g708dc14+chromium-152.0.7977.83` |
| `me.friwi:jcef-natives-windows-amd64` | 同 135 字符串 | 同 152 字符串 |
| jcefbuild release | — | `1.0.71`（JCEF `17e805a`，CEF `152.0.6`，Chromium `152.0.7977.83`） |

改 [`libs.versions.toml`](../gradle/libs.versions.toml) 两处即可（`jcefmaven`、`jcef-natives`），`jcef-api` 由 `jcefmaven` 传递。

**javap 对比 135 / 152**（`CefSettings` 字段、`CefApp.startup/getInstance/getState/createClient`、`CefRequestContext.getGlobalContext`、`CefBrowser` 接口方法、`CefClient.dispose`）**全部存在**；唯一公开变更是 `CefLoadHandler.ErrorCode` 新增 38 个枚举（1.0.71 说明）。→ 升级风险集中在 native 侧，不在 Java API。

#### 但托底现在根本跑不起来（真正的阻塞）

`modules/markdown-one` 的 CEF 适配层是按 **JBR 补丁版 jcef** 写的，与 `me.friwi:jcef-api`（135 与 152 一样）有四处不匹配：

| 用法（`CefRefs.kt` / `CefEngine.kt`） | jcef-api 实际 | 后果 |
|---|---|---|
| `Class.forName("org.cef.browser.CefBrowserOsrWithHandler")` + 4 参构造 `(CefClient, String, CefRequestContext, CefRenderHandler)`（`CefRefs.kt:24,69`） | **没有这个类**（两版 jar 都只有 `CefBrowserOsr`） | `ClassNotFoundException` |
| `CefSettings.getField("no_sandbox")`（`CefRefs.kt:29`） | 无该字段 | `NoSuchFieldException` |
| `CefBrowser.getMethod("wasResized", int, int)`（`CefRefs.kt:80`） | 接口无此方法 | `NoSuchMethodException` |
| 帧来源 = 构造时传 `CefRenderHandler` | `CefBrowserOsr(CefClient, String, boolean, CefRequestContext, CefBrowserSettings)` + `addOnPaintListener(Consumer<CefPaintEvent>)` / `getRenderHandler()` | 实现要改 |

**为什么一直没暴露**：[HermesMarkdown.kt](../composeApp/src/commonMain/kotlin/dev/shinglem/hermes/markdown/HermesMarkdown.kt) 的 `MarkdownConfig` 没有设 `webFallback` / `allowRawHtml` / `cefNativeDir` → 默认 `WebFallback.Source`，`JcefAdapter` 不注册；`Main.kt:144-151` 只设置了 `-Dmarkdown.cef.dir`。所以这条链路从未被触发。

> #1 表格里"消息内 HTML 走 JCEF OSR"是**设计意图**，实现层成立性见本条。

#### 启用托底的接线（修完适配层之后）

```kotlin
MarkdownConfig(
    webFallback = WebFallback.Jcef,
    allowRawHtml = true,             // 否则默认 HTML 块只显示源码
    cefNativeDir = /* 或沿用 -Dmarkdown.cef.dir */ null,
    webDocument = { block -> /* 注入 KaTeX / mermaid.js 的 HTML */ },
    jcefPoolSize = 2,
)
```

- `webDocument` 默认只处理 `MdBlock.Html`；数学与图表需要**自己提供** KaTeX / mermaid.js 资源（库不打包脚本，保持零体积）。
- 因此"启用托底"= 适配层修复 + 资源注入两件事，缺一不可。

#### 升级 152 的 native 风险（需真机验）

- 绝对路径加载顺序仍是 `jawt → chrome_elf → libcef → jcef`（`CefBootstrap` 已内置），需确认 152 的依赖链没变。
- `jcef_helper.exe` 子进程要能从 `<home>/cef` 拉起。
- CEF 152 要求 Windows 10+。
- 体积：`windows-amd64.tar.gz` **167.6 MB**（135 时代解压后 `cef/` 已是 **310.4 MB**），预计升到 450-550 MB —— 发版说明与 patch 策略要同步。

#### 建议顺序

1. **先修适配层**：`CefBrowserOsr` 五参构造 + `addOnPaintListener` 取帧，在 **135** 上跑通"出帧"。
2. 再升 **152**（改两行版本号），核对启动日志 `cef native dir=...`、子进程与帧率。
3. 最后接线 `webFallback = Jcef` + `webDocument` 资源注入，并决定是否默认开启。
4. 记录 `cef/` 体积变化；若走 patch 发布，注意 `cef/` 属于"整目录替换"而非差异文件。

#### 验证口径

- 扩充 `CefBootstrapSmokeTest`（现 45 行）：初始化 → 创建 OSR 浏览器 → **收到至少一帧 `onPaint`**，否则 fail。
- 真机：含 `<details>` / KaTeX / mermaid 的消息滚动不白屏、不崩，渲染进程数受 `jcefPoolSize` 限制。
- 升级前后各跑一次，记录 `cef/` 目录体积与首帧耗时。

**何时改用 submodule**（明确的触发条件，出现任一才 fork）：

- 上游 bug 阻塞（候选窗位置 / DPI / 中文组合态）且等不到修复；
- 需要加私有联动（与审批卡片 / 引用 / 会话状态打通，UP 流里无法通过 `EditorCommand` 完成）；
- 需要裁掉 android / wasm 目标以缩短构建（这属于构建优化，不是采用前提）。

fork 时的做法（沿用 `terminal-bossterm` 的路子）：

1. fork 成 `Shinglem/aardink`，开 `hermes` 分支；
2. **只留 `:editor` + `:languages`**，在 `editor/build.gradle.kts` 里移除 android / wasmJs 目标（否则要 Android SDK 与 Node 下载）；
3. `settings.gradle.kts` 加 `include(":modules:aardink")`（源码并入，像 markdown-one）或 `includeBuild`（composite，像 terminal-bossterm）；
4. `.gitmodules` 加 `ignore = untracked` —— 它的 settings 会在 dev 环境生成 `local.properties`；
5. 主仓库 `git add modules/aardink` 只更新指针，改动在 fork 里提交。

HtmlText 的发布情况（供参考）：`de.charlex.compose:html-text-material3`（另有 `html-text-common`），最新 `3.0.0-beta02`（2025-12-01，近一年未更新），**有 `-jvm` 变体**，desktop 能用 —— 但能力上限就停在内联样式。

**判定标准**（用一条就能筛掉）：能否渲染
`<div style="padding:8px;border:1px solid red">` 里嵌 `<table border="1">` 和外部 CSS？
三者都不行。

#### 所以内嵌 HTML 只有两条路

1. **扩展现有 `HtmlContainerAdapter`**：把 `div` / `p` / `h1-h6` / `ul` / `ol` / `table` / `pre` / `img` 解析成 Compose 原生块（行内 `<br>` / `<b>` / `<code>` / `<a>` / `<img>` 已有改写）。这能覆盖 LLM 实际输出里的绝大多数 HTML，零新依赖，与 #7 的扩展同源。
2. **真需要任意 HTML/CSS/JS 时只有 JCEF**（#4）—— WebView2 因无离屏渲染已排除（#3），HtmlText 类库的能力上限不够。

#### 标准层面：没有"带 CSS/JS 的 HTML"渲染标准，GFM 反而明令禁用

| 规范 | 对原始 HTML 的规定 |
|---|---|
| **CommonMark 0.31.2「Raw HTML」** | `<` `>` 之间形如标签的内容**原样输出、不转义**；标签/属性名不限于现有 HTML（自定义标签也算）。**只定义语法，不定义安全与渲染语义**。 |
| **GFM 6.11「Disallowed Raw HTML (extension)」** | 启用 **tagfilter**：渲染时把下面 9 个标签的前导 `<` 替换成 `&lt;`（即当文本处理）：<br>`title` `textarea` `style` `xmp` `iframe` `noembed` `noframes` `script` `plaintext`<br>理由是"这些标签会改变 HTML 的解释方式（嵌套解析不同），在 Markdown 上下文里通常不可取"。**其余标签原样保留**。 |

也就是说：**规范里不存在"内嵌 CSS/JS 应当生效"的标准**；反过来，GFM（GitHub 的行为契约）把 `<style>`、`<script>`、`<iframe>` 显式列为禁用。真正"能跑 CSS/JS"的场合是 Hugo / Jekyll / docsify / notebook 这类**把 Markdown 当站点源码、不做消毒**的产品选择，不是标准。

实践中各渲染器都自带白名单：GitHub 的 HTML pipeline + SanitizationFilter、`markdown-it` 默认 `html:false`、VS Code 预览禁用脚本、前端事实标准 DOMPurify、Java 侧 OWASP Java HTML Sanitizer。

**对 Hermes 的硬要求**：

1. 本客户端以管理员权限运行（计划任务 `HighestAvailable`），**绝不能执行 AI 输出里的 JS** —— 那等于把本机管理员权限交给网页内容。
2. 若启用 JCEF 渲染 HTML，必须同时做到：
   - 页面禁用脚本（`CefBrowserSettings` 关 JS + HTML 里加 CSP `script-src 'none'`，双保险）；
   - 只加载 `data:` 内容，拦截一切外链请求（markdown-one 路线图里的「请求拦截」）；
   - 禁止 `iframe` / `object` / `embed`。
3. 这与我们现有策略一致：`HTML_INLINE` 只改写成等价 Markdown 标记，`<div>` 类容器剥壳后递归渲染 —— 比 GFM 的"转义 9 个标签"更宽容，但不执行任何东西。

### #9 自研 HTML 标签子集的原生渲染

- **类型**：改进（渲染能力）
- **优先级**：**P1**（做成了就能把 JCEF 从"必需"降为"仅公式/图表需要"）
- **涉及层**：`modules/markdown-one`（解析 / 块渲染 / 行内渲染）
- **调研日期**：2026-11-05
- **状态（2026-11-05）**：✅ 已实现 L1→L3（`HtmlNativeAdapter` + `HtmlSanitizer` + `text/HtmlInline.kt`），
  单测覆盖白名单、`script` 子树丢弃、深度/节点上限、1000 节点性能门槛。

**结论：可行，而且比 JCEF 更适合我们** —— 没有 310 MB native、没有渲染进程、没有脚本攻击面，代价只是"只支持标签语义 + 极少量样式"，而这恰好是 LLM 输出 HTML 的实际形态。

#### 现状（可复用的部分）

- `builtin/HtmlContainerAdapter.kt`：已经在做"剥容器标签 → 交回 `MarkdownText` 递归"（只特判 `align`）。
- `parse/HtmlNormalizer.kt`：解析前把行内 HTML（`<br>` `<b>` `<code>` `<a>` `<img>`）改写成等价 Markdown 标记。
- `text/MdTable.kt`、`DetailsAdapter`：表格与 `<details>` 已有渲染器，可直接被 HTML 路径复用。

#### 实现路径

1. **不要自己写 HTML parser**。统一用 **ksoup**：`com.fleeksoft.ksoup:ksoup:0.2.6`（KMP，jsoup 的移植，2026-02-19）。实测其行为与 jsoup 1.24.1 一致（未闭合补全、`tbody` 自动插入、`script` 节点、属性原样保留），性能约慢 1.6 倍（1000 个 `<p>`：56ms vs 34ms），仍在可接受范围。
   - **不用 jsoup**（JVM-only）：markdown-one 目标多端，用 ksoup 可以省掉将来换库与 `expect/actual` 分叉。
2. **新增 `HtmlNativeAdapter`**（priority 高于 `builtin.html` 的 105），命中 `MdBlock.Html` 后用解析树渲染；`HtmlContainerAdapter` 保留作兜底。
3. **行内不动**：继续走 `HtmlNormalizer` 的标记改写（已经覆盖 `<b>/<i>/<code>/<a>/<img>/<br>`），避免两套行内实现打架。
4. **递归 + 防护**：限制最大深度（如 32）与节点数（如 5000），超出直接走源码兜底，避免病态输入。

#### 范围收敛（按标签语义，不做 CSS 布局）

| 层 | 必做 | 可选 | 明确不做 |
|---|---|---|---|
| 块级 | `div`（透明）`p` `h1-h6` `ul/ol/li` `blockquote` `pre` `hr` `center` `details/summary` | `table/thead/tbody/tr/th/td`（复用 `MdTable`）、`figure/figcaption` | flex / grid / position / float / 列布局 |
| 行内 | `b/strong` `i/em` `u` `s/del/strike` `code` `kbd` `mark` `sub/sup` `br` `a[href]` `img[src|alt|width|height]` | `span` / `font` 的**颜色**、`abbr[title]` | 事件属性 `on*`、`form/input`、`iframe/object/embed`、`link/meta` |
| 属性 | `align` `color` `width/height`（仅 img/table） | `style` 里只取 `color` / `background-color` / `font-size` / `font-weight` / `font-style` / `text-align` | `display` `position` `z-index` `transform`、外部/内联 `<style>` 块 |
| 丢弃 | `script` `style` `iframe` `noscript` 的内容（与 GFM 的 tagfilter 一致） | — | — |

#### 工作量估计

| 阶段 | 内容 | 规模 |
|---|---|---|
| L1 | 解析接入 + 块级 10 个 + 行内 10 个 + 属性白名单 + 递归防护 | ≈ 400-600 行 + 单测 |
| L2 | HTML `<table>` 接 `MdTable`、嵌套列表、`<details>`、图片尺寸 | ≈ 200-300 行 |
| L3 | `style` 属性子集解析（颜色/字号/字重/对齐） | ≈ 100-200 行 |

合计 ≈ 800-1000 行（含测试），比接 JCEF（#4 的适配层修复 + native 分发 + 安全加固）更可控。

#### 风险

1. **嵌套与不闭合标签**：LLM 输出经常缺闭合标签，必须靠 ksoup 的容错模式，不能正则。
2. **递归栈**：`<div><blockquote><ul><li><p>` 这类嵌套要限深。
3. **外链图片**：`<img src="http://…">` 会真的发请求（隐私）。沿用现有策略：默认允许图片，但应加"是否需要网络图片"的开关（与 #4 的请求拦截同一件事）。
4. **与既有改写冲突**：`HtmlNormalizer` 在解析前就改写了部分标签，可能出现"已经变成 Markdown 了，又走 HTML 适配器"的情况 —— 接线时先写 3-5 个真实样本的回归用例锁定行为。

#### 验收

- 样本集：`<div align="center">`、`<details><summary>`、`<table>`、`<br>` 行内、`<span style="color:#f00">`、未闭合的 `<div><p>text`、`<script>alert(1)</script>`（必须不执行且不显示）。
- 断言：每个样本渲染后**无空白块**、无源码泄漏（除非明确兜底）、无异常、无网络请求（`script`/外链除外按策略）。
- 性能：1000 个节点的 HTML 块首帧 < 16ms（可与现有 markdown 渲染基准一起跑）。

#### 白名单直接采用 GitHub 的 sanitizer 配置（已决定）

**布局级 `style` 不实现** —— 依据是 GitHub 自己的行为：其 HTML pipeline 的 `SanitizationFilter`
（[`lib/html_pipeline/sanitization_filter.rb`](https://github.com/gjtorikian/html-pipeline/blob/HEAD/lib/html_pipeline/sanitization_filter.rb)）
**允许的属性里根本没有 `style`**（也没有 `class`），只保留传统呈现属性。

可直接照搬的**元素白名单（60 个）**：

```text
h1 h2 h3 h4 h5 h6 br b i strong em a pre code img tt div ins del sup sub p
picture ol ul table thead tbody tfoot blockquote dl dt dd kbd q samp var hr
ruby rt rp li tr td th s strike summary details caption figure figcaption
abbr bdo cite dfn mark small source span time wbr
```

**属性白名单**（`all` 列表，节选关键项）：

```text
align width height border valign colspan rowspan start type open title id
dir lang scope headers colspan rows span size alt src href srcset loading
cite datetime tabindex role aria-* itemprop itemscope itemtype
```

> 注意：**没有 `style`、没有 `class`、没有 `on*`**。这正是我们要的行为。

**我们的取舍**（比 GitHub 略宽一点点，成本极低）：

- 保留 `align`（HTML 传统属性，已实现）与 `width` / `height`（仅 `img` / `table`）；
- `style` **只解析 6 个能映射到 `TextStyle` 的属性**：`color`、`background-color`、`font-size`、`font-weight`、`font-style`、`text-align`；其余（`display` / `flex` / `grid` / `position` / `float` / `margin` / `padding` / `z-index` / `transform`）**静默忽略**；
- 若后续想完全对齐 GitHub，把 `style` 整条关掉即可（加一个开关）。

**为什么不实现布局**：布局属性会诱导"用 HTML 写页面"，而我们的渲染目标是"对话里的富文本"。忽略它们时绝大多数内容仍然可读（顺序、层级、强调都在），而实现它们需要迷你 CSS 引擎 + 布局算法，收益与投入完全不成比例。

**结论：不值得 fork。** 它的架构与我们要的块级渲染不兼容；真正有价值的是几段局部实现，Apache-2.0 直接借鉴即可。

#### 实现实况

- 生产代码总共 **27 个 `.kt` / 61.3 KB**，核心是 `html-text-common/src/commonMain/kotlin/HtmlParser.kt`（**219 行**）与 `BaseHtmlText.kt`（81 行）。
- 解析用 **Ksoup**（`com.mohamedrejeb.ksoup:ksoup-html:0.6.0`，KMP），而且是 **SAX handler 风格**（`KsoupHtmlParser` + `KsoupHtmlHandler`），**不建 DOM 树**。
- 产物是**单个 `AnnotatedString`**：
  - 样式靠 `tagStack: MutableList<TagInfo>`；
  - 列表靠 `Builder.BulletScope` + `TextIndent` / `LineHeightStyle`（纯文本缩进）；
  - 链接靠 `getStringAnnotations("url")` + `BaseHtmlText` 里自绘点击矩形（81 行）；
  - 颜色解析自己写了 `#RRGGBB` / `#AARRGGBB` / `rgb(...)`。
- 有 `-jvm` 变体，desktop 能用；最新版本 `3.0.0-beta02`（2025-12-01）。

#### 为什么不 fork

1. **输出模型不匹配（根本原因）**：`AnnotatedString` 只能表达文字样式与段落缩进。`<table>` 的行列、`<details>` 的折叠、块级 `<img>`、`<pre>` 代码块、深层嵌套列表**都无法表达**。要支持它们必须把返回类型从 `AnnotatedString` 改成 `@Composable` 树 —— 那等于把 219 行核心逻辑推倒重写，fork 就只剩"拿了个 Ksoup 用法样例"。
2. **SAX 无树**：表格需要成对标签的结构信息，SAX + 手工栈能做但极别扭；jsoup / ksoup 的 DOM 模式直接给树，省一大截。
3. **上游 beta 且半年多未更新**：fork 等于接手维护。
4. 它只按 11 个标签设计，扩展要改 `htmlToAnnotatedString` 内部，不是加插件。

#### 可借鉴的部分（Apache-2.0，保留声明即可）

- 行内样式栈的堆叠方式（`TagInfo` 记录 `start` 偏移，出栈时 `addStyle`）；
- `#RGB` / `#RRGGBB` / `rgb()` 的颜色解析；
- 有序列表 `start` / `type`（a./A./1.）的序号与缩进算法；
- 链接点击区的 `computeLinkRects` 思路（我们已有 `LinkAnnotation`，用不上，但可选）。

#### 结论与替代

维持 #9 的方案：markdown-one 里新增 `HtmlNativeAdapter`，用 **ksoup 的 DOM 模式** → 块级 `@Composable` 树 + 行内 `AnnotatedString`。

**唯一例外**：如果将来只想做"行内富文本"（不需要表格/详情块），可以直接依赖 `de.charlex.compose:html-text-material3:3.0.0-beta02` 的 `-jvm` 变体，连 fork 都不用 —— 但能力不比现有 `HtmlNormalizer` 强多少，收益有限。

#### 对 #9 的意义

两条可选做法：

1. **参考实现**（推荐）：把它的 `HtmlEntities`（完整实体表，省得自己维护 2000+ 条目）与 `HtmlHandler` 的三回调接口设计借鉴过来；颜色表用 `HtmlColors` 的 CSS4 命名色清单。
2. **混合架构**（可选）：用 **ksoup 负责切块与结构**（块级：table/details/pre/img），**每块的行内内容交给它的 `htmlToAnnotatedString`** 转成 `AnnotatedString`。这样行内样式、实体、颜色都不用自己写，块级仍由我们控制。

### #12 混合方案：行内原生 + 块级 HTML 走 JCEF

- **类型**：改进（方案评估，接 #4 / #9）
- **优先级**：P2
- **涉及层**：`modules/markdown-one`
- **调研日期**：2026-11-05

**结论：可行，且复杂 HTML 上效果确实更好；但在我们最高频的简单 HTML 上体验更差，成本也不比全原生低。建议维持"原生优先、JCEF 兜底"，而不是把块级 HTML 默认交给浏览器。**

#### 逐维度对比

| 维度 | 全原生（#9） | 混合（行内原生 + 块级 JCEF） |
|---|---|---|
| 简单 HTML（`div/p/table/align/br/span style=color`） | ✅ 主题一致、无白屏、高度由 Compose 测量 | ⚠️ 每块一个 Chromium，滚动时按 `jcefPoolSize` 排队，可能先显示占位 |
| 复杂 HTML（CSS 布局、定位、浮动、自定义 CSS） | ❌ 布局属性只能忽略 | ✅ 浏览器级正确 |
| 流式输出 | ✅ 逐帧渲染 | ⚠️ 库规定流式期间 JCEF 不参与（`jcefDuringStreaming=false`），结束后一次性替换 → 视觉跳变 |
| 高度自适应 | ✅ 自然测量 | ❌ 需 JS 量 `scrollHeight` 再回传；高度变化会让 `LazyColumn` 抖动 |
| 包体积 | 0 | `cef/` 310 MB（升 152 后估 450-550 MB），且不能删 |
| 进程 / 内存 | 无 | 每块一个渲染进程，`jcefPoolSize` 默认 2 |
| 安全面 | 无脚本 | 必须禁 JS + 禁网络 + 禁 `iframe`（见 #8） |
| 前置工作 | L1/L2/L3 共 800-1000 行 | **#4 适配层修复** + 高度同步 + 池调度 + 安全加固 |

#### 为什么"效果更好"只对复杂 HTML 成立

LLM 实际输出的 HTML 绝大多数是：`<div align="center">`、`<br>`、`<details>`、`<table>`、`<img>`、`<span style="color:…">`、`<kbd>`。这些都是**标签语义级**，原生映射能画得一模一样，而且：
- 跟随主题（明暗/配色）而不是浏览器默认样式；
- 没有白屏与进程启动延迟；
- 高度稳定，长对话滚动不抖。

真正需要浏览器的只有：`display:flex/grid`、`position`、`float`、`<canvas>`、交互式 `<svg>`、web component —— 在 AI 输出里占比极低。

#### 建议路线

1. **先做 #9 的 L1**（块级 10 个 + 行内 10 个）。
2. **保留 `webFallback = WebFallback.Jcef` 作为显式兜底**：只给"原生适配器画不出"的块用（例如块内含布局级 `style`），其余全走原生。
3. 这样 JCEF 从"必需"降为"可选"，`cef/` 可以做成**可选下载**（不随主包），包体积与攻击面一起降下来。
4. 若将来要做"任意 HTML 预览 / 交互页面"，再单独开一个"在浏览器中打开"的入口，而不是把消息流默认交给浏览器。

#### 触发条件（什么时候才值得交给 JCEF 渲染一个块）

满足任一即可：

- 块内含布局级 `style`（`display` / `flex` / `grid` / `position` / `float`）；
- 含 `<canvas>` 或需要交互的 `<svg>`；
- 原生适配器解析失败且用户可见（不是静默降级）。

#### 验收

- 同一批 10 个 HTML 样本分别走原生与 JCEF，截图对比 + 记录首帧耗时与内存；
- 硬指标：**长对话滚动时块高度不变**（用滚动位置记录判定），以及**流式结束后不跳变**（若走 JCEF 则允许一次跳变但必须有占位）。

#### 连锁结论（2026-11-05 更新）

既然确定「HTML 全自研 + 忽略布局级 `style`」（#9），上面这张表里 JCEF 唯一的优势项（复杂 CSS 布局）**主动放弃**了。于是：

- JCEF 在消息渲染里**没有必须用途** —— mermaid 走纯 Kotlin 引擎、公式走 `latex-renderer`、HTML 走自研；
- 因此 **#4（修 JCEF 适配层）可以不做**，`cef/` 310 MB 也可以从主包移除（或改成可选下载）；
- `webFallback` 保持默认 `Source`（源码兜底），不启用 `Jcef`。

只有在"将来要内嵌任意网页 / 交互式 HTML 预览"时才重新评估 JCEF。

**V2 解析器能力 —— 已完成**

- **Alerts：GFM flavour 原生支持**。`> [!NOTE]` 直接产出：
  `Markdown:ALERT` → [`BLOCK_QUOTE`, `ALERT_TITLE("«[!NOTE]»")`, `EOL`, `BLOCK_QUOTE`, `PARAGRAPH/TEXT`]；

  → 实现成本大幅下降：只需在 `MdBlockFactory` 增加一个 `Alert` 块类型并映射，**不需要预处理**。

### #15 原生通知：复用已存在的、指向本程序的开始菜单快捷方式

- **类型**：缺陷（与既有设计不一致）
- **优先级**：P2
- **涉及层**：`platform/NativeNotifications.desktop.kt`
- **记录日期**：2026-11-05

**现状（已实现一半）**：`NativeNotifications.desktop.kt:89-112` 已经做了"已存在就不再重写"：

```kotlin
val existedBefore = shortcut.isFile
val policy = if (existedBefore) ShortcutPolicy.REQUIRE_NO_CREATE else ShortcutPolicy.REQUIRE_CREATE
```

但它判的是**文件名**：`%APPDATA%\Microsoft\Windows\Start Menu\Programs\<产品名> (<home 哈希>).lnk`
（`12-通知窗.md` §快捷方式）。于是这些情况仍会**多建一个**：

| 情况 | 现象 |
|---|---|
| 用户自己创建过指向 `hermes-desktop-compose.exe` 的快捷方式（任意名字） | 开始菜单出现两个入口 |
| 旧版本用固定名 `Hermes Desktop Compose.lnk`（无哈希）创建的 | 升级后并存 |
| 便携包换了目录（`<home>` 变了 → 哈希变了） | 两份快捷方式，且旧的那份还带旧 AUMID |

**要的行为**：创建前先看**是否已有指向本程序的快捷方式**，有就直接用（不新建、不重写）。

**可行实现**（待实现方确认细节）：

1. 仅当 `<appName>.lnk` **不存在**时才扫描（避免每次启动都多花时间）；
2. 扫描 `%APPDATA%\Microsoft\Windows\Start Menu\Programs`（递归）下的 `*.lnk`，取 `TargetPath` 与 AUMID；
   - `WScript.Shell.CreateShortcut(path).TargetPath` 需要 COM；用 `cscript`/PowerShell 一次性批处理，
     或直接在 Kotlin 里解析 `.lnk`（LinkInfo 的 LocalBasePath）—— 前者简单、后者无外部依赖，二者取其一；
   - AUMID 在 `.lnk` 的 property store 里（`System.AppUserModel.ID`），
     `Shell.Application` 的 `ExtendedProperty` 可读。
3. 命中（TargetPath == 当前 exe）时：
   - 若该 `.lnk` **已带 AUMID** → 采用它的 AUMID 与文件基名，`initialize(aumid, baseName, REQUIRE_NO_CREATE)`；
   - 若**不带 AUMID** → 它不能用于 toast，仍需创建带 AUMID 的条目（此时按现状新建，并在日志里说明原因）。
4. 兜底：扫描失败（COM 不可用 / 权限）→ 退回现有按文件名判定的逻辑，**不能因此不发通知**。

**约束**：`WindowsNotificationCenter.initialize(aumid, appName, policy)` 只接受 `appName`
（库自行拼成 `Programs\<appName>.lnk`），**没有"指定已有路径"的参数** ——
所以"复用"只能是"用同一个名字 + 不重建"，或者"读它的 AUMID 后按该 AUMID 初始化"。

**验收**：

- 场景 1：开始菜单已有 `Hermes Desktop Compose (abc123).lnk` → 启动后 mtime 不变、无新增文件；
- 场景 2：手动建一个 `我的 Hermes.lnk` 指向同一 exe（带 AUMID `Shinglem.HermesDesktop.abc123`）→ 启动后不新建，toast 正常；
- 场景 3：删除所有快捷方式 → 启动后按现状新建一个；
- 日志新增一行 `shortcut ... reused=<name|none> reason=<target|filename|created|no-aumid>`。

### #16 非原生通知：同一会话多个审批只弹出一个右下角通知

- **类型**：缺陷
- **优先级**：**P1**（会漏掉待处理请求：用户以为只批准了一个）
- **涉及层**：`platform/NotificationInbox.kt`、`ui/notification/NotificationOverlay.kt`、`feature/shell/AppShell.kt`
- **记录日期**：2026-11-05

**现象**（用户报告）：关闭「使用系统原生通知」时，同一对话里同时到达多个审批，右下角自绘通知窗**只弹出一个**，其余不出现。

**根因**（`NotificationInbox.kt:34-36` 的注释就写着）：

```kotlin
// 同一时刻只留一条：审批一次只会有一个，堆叠反而挡屏幕。
private val _current = MutableStateFlow<NotificationRequest?>(null)
```

`post()` 直接覆盖 `_current`；`NotificationOverlay` 订阅单槽并只渲染一个 `Window`。
第二个审批到达即顶掉第一个（第一个既没被看见，也不会再出现；`ReminderGate` 已记过 id，
所以也不会重复提醒）→ 表现为"只通知一个"。

注意：这与 `NotificationRules.shouldRemindForSession` / `ReminderGate` 无关 ——
两条审批都会"允许提醒"，是**投递层**把前一条丢了。**不是**窗口内卡片的问题（窗口内
`ChatState.visibleApprovals` 会把它们都画出来，且都还在）。

**要的行为**：多条并存时都要能被看到，且不能变成"同时压 5 个窗口"。

**建议方案**（实现方定稿）：

1. `NotificationInbox` 从单槽改为**队列 + 最多 N 条同屏**（建议 N=3）：
   `post()` 入队，`current` 改为 `active: StateFlow<List<NotificationRequest>>`；
2. `NotificationOverlay` 渲染一个**纵向堆叠**的容器（右下角，新条目在下方或上方，需在实现时定）；
   每条自动收起计时**独立**；
3. 超过 N 条时排队：前面的消失后再补位（避免一次弹几十个窗口）；
4. 同一 `id` 的重复投递继续忽略（沿用现有"同一请求只提醒一次"的语义）；
5. 用户点了某个审批的按钮后，只移除那一条（`dismiss(id)` 语义保持）。

**验收**：

- 同一会话连发 3 个审批 → 3 个通知都能看到（或 3 条堆叠）；
- 连发 5 个 → 先显示 3 条，点掉 1 条后第 4 条补上；
- 点「允许一次」只处理对应那条，其它通知仍在；
- 自动收起互不干扰（先到的那条先消失，不会连带清空全部）。
