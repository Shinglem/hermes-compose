### #2 内置编辑器：Aardink 接入 spike

- **优先级**：P2
- **涉及层**：UI（编辑器）/ 产品范围（ADR-005）
- **前置**：ADR-005「不做文件树 / 内置编辑器」仍是当前非目标 —— **先改产品决策，再谈实现**。

**候选排序**：`Aardink` > `SweetEditor` > `JCEF + Monaco` > `BossEditor`（后者被 IME 硬伤排除：只认 `event.utf16CodePoint`，微软拼音打不出字）。

**推荐接入**：Maven 依赖 `com.aardarch:aardink:0.8.0`（Apache-2.0，Compose 1.12.2 / Kotlin 2.4.21 与本仓库逐项相同，纯 Kotlin 无 native）。
**不 fork**：它有 `editor/api/editor.klib.api` 做 API 锁定，主题/命令/语言接入都走公开扩展点。
**出现上游阻塞才 fork**：fork 时只留 `:editor` + `:languages`，移除 android / wasmJs target（否则要 Android SDK 与 Node 下载），`.gitmodules` 加 `ignore = untracked`。

**spike 判据**：

1. 在 1.12.2 / 2.4.21 工程里能编译运行；
2. 微软拼音端到端（候选窗跟随光标、上屏、撤销、保存重开）；
3. 150–200% DPI 下光标与候选窗位置；
4. 提权进程里正常工作；
5. 体积增量（预计 < 2 MB）；
6. 与 `LazyColumn` 的滚动关系 —— 编辑器自身是滚动容器，必须放独立 pane，不能塞进消息流。

**风险**：2★、0.8.0（2026-11-01）、contributors 4（主力 1 人）—— 采用前观察 1–2 个版本。

### #3 原生集成 spike：托盘与浏览器面板

- **优先级**：P2
- **涉及层**：`core/app/DesktopTray.kt`、窗口壳（`Main.kt` 396 行）

**已定论、不必再评**（单实例 / 开机自启 / 提权重启 / 打包四项均**不换**）—— 结论与证据见 [`待修复问题-归档.md`](待修复问题-归档.md)。

**待 spike A · 托盘换 `dev.nucleusframework:composenativetray`**

- 只引 `composenativetray`（2.1.0 起与 `-app` 拆分），**不要** `composenativetray-app`（要 `nucleusApplication`，等于连窗口层一起换）；
- 好处：它正是为解决 CMP-1936（中文菜单乱码）而用原生桥（`WindowsNativeBridge.nativeCreateTray`），还附带 HDPI 修复、左键 primary action、勾选/子菜单；
- 判据：中文菜单 + 100/150/200% DPI 不错位 + 暗色可读；点图标仍先走 `SystemNotifications.consumePendingAction()`；native dll 进 `packaging/assemble-release-test.ps1`；保持 `DesktopTray` 对外形状（`install()` / `dispose()` / `menu()`）；
- 版本纪律：锁定 2.5.18，不碰 `nucleus-3.0` 主线。

**待 spike B · 浏览器面板（hermes 浏览器能力的界面）**

- 前提：整窗口壳迁到 Tao（`nucleusApplication(backend = Tao)`）；`composewebview` 桌面实现是 WebView2 + DirectComposition 原生视觉，**没有离屏路径**，只能整窗口/固定面板；
- 第一步只验一件事：启动前设 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=<port>`，`curl http://127.0.0.1:<port>/json/version` 是否返回 `webSocketDebuggerUrl`；

- 安全：CDP 端口等于完整浏览器控制权，只绑 `127.0.0.1`、随机端口、用完即关；
- 迁移回归面：`Main.kt` 的窗口创建、自研单实例、托盘、提权、自启；Tao 把触摸降为 `Pan` 事件，`touchDragScroll` 需重测。

### #20 发出带附件的消息后，对话里看不到附件链接

- **优先级**：P3（功能已通，只是"发过什么"不可回溯；不影响发送本身）
- **涉及层**：UI / 数据层（`ChatRow` 投影 + 本地乐观行）
- **记录日期**：2026-11-13（#19 修完后用户实测提出）
- **现象**：附加图片并发送后，本轮的用户消息在对话里只有文字，**看不到任何附件标识 / 链接**；
  回头看历史也看不出这一轮带过图片。图片本身是送达的（agent 能描述内容），只是界面没留痕。
- **原因（初判，待验证）**：
  1. 发送时的本地乐观行（`ChatState.appendLocalUser`）只带 `text`，不带 `attachments`；
  2. 后端为这一轮落的 user 行是按 `@image:<path>` 之类正文嵌入的（`state.db` 的 user 行），
     客户端 `projectChat` 没有把这类引用投影成可点击的附件卡片；
  3. `ComposerAttachment` 在 `markSent` 之后被清空，界面上没有任何"这一轮带过图"的残留。
- **修法方向**（下次做）：
  - `appendLocalUser` 增加可选 `attachments`，渲染成行内附件 chip（图标 + 文件名，点击用
    `openExternalUrl` / 预览打开图片）；
  - `projectChat` 识别 user 行里的图片引用（`@image:` / 绝对路径）并同样产出 chip，
    保证"刷新后也能看到"；
  - 附件 chip 用 markdown-one 的图片块能力做点击放大，不自己造预览窗口。
- **验收口径**：发一张图 → 本轮用户消息下方出现可点击的附件条；刷新/重进会话后仍在；
  点击能打开/放大图片。
### 已否决：后端改用 Windows 服务（SCM）托管（2026-11-10）

> 记录原因见 `AGENTS.md` §「不做清单和做清单同等重要」—— 不写下来，下一个 agent 会重新提议。

**原提案**：写一个 daemon 注册成 Windows 服务托管后端；新装时索要 UAC 创建服务；桌面端做服务管理；
后端由 SCM 自启、前端用普通自启；顺带让通知不再依赖开始菜单快捷方式。

**否决理由**（逐条核实后）：

| 提案想达到的目的 | 结论 |
|---|---|
| 后端独立于前端 | **已达成**，不需要服务：`gateway` 路线的 daemon 用 `CREATE_BREAKAWAY_FROM_JOB` 脱离我们的 Job Object |
| 登录自启不弹 UAC | **已达成**：计划任务 `RunLevel=HighestAvailable`（本机任务 XML 实测） |
| 日常不提权 | 真需求，但**不需要服务**：`app.elevate=never` + `HKCU\...\Run` 自启即可，更干净 |
| 开机即启动（不登录） | SCM 唯一独有的能力，但**对我们无价值** —— 服务在 Session 0，没有交互式桌面 |

**致命冲突：Session 0 无交互桌面。** 后端要跑在**用户的交互会话**里才能：

- `computer_use` 模拟键鼠操作真实窗口（上游 `hermes_cli/tools_config_cua.py:200` 自己写着
  「needed when driving Windows over SSH (**Session 0 has no interactive desktop**)」）；
- `browser.headed` 弹出可见浏览器窗口（本机 `config_custom.json` 就是 `headed: true`）。

也就是说「登录后才启动」恰好是**需要的**，而不是待消除的限制。
[`07-提权与自启动.md`](详细设计/工程与代码/07-提权与自启动.md) §2.1 早已论证并否掉过这条路。

**另外两条不成立的理由**：

- 上游**没有** Windows SCM 服务安装入口：`hermes gateway install` 在 Windows 上装的是
  **计划任务**（`hermes_cli/gateway.py:5542`）。`WindowsGatewayService` 与
  `hermes_owns_windows_service` 只用于**检测**归属（更新器判定「这是不是我自己的服务」，
  `gateway_windows.py:136`），`gateway-service/` 目录里放的是 `.vbs`/`.cmd` 启动器，不是 SCM 服务。
  做服务化等于与上游分叉。
- #13 / #14 的根因都不在后端形态：#13 是上游优雅关闭超时被取消后半死；#14 是客户端换端口后
  没重建会话订阅。服务化修不了这两条，还会把 `gateway.lock` 语义与 SCM 进程身份叠在一起，更难排障。

**替代方案**（已采纳方向，见 #15）：

1. `app.elevate` 默认 `never`，客户端全程普通权限；
2. `app.autostart` 增加 `run` 选项（`HKCU\...\Run`，无需 UAC、零系统对象），`task` 保留给确实需要时刻提权的用户；
3. 需要操作管理员窗口时，按需 `runas` 拉起**一次性**提权动作，主进程不动；
4. 后端管理与端口跟随按 #15 做。

**关于通知不绑快捷方式**：与后端形态无关，是 Windows Shell 层硬限制 —— toast 归属只认开始菜单
`.lnk`（[`12-通知窗.md`](详细设计/工程与代码/12-通知窗.md) §1 的四组实测已排除桌面 `.lnk`、
注册表、`App Paths`、COM activator 等全部替代）。真要摆脱快捷方式，只能**放弃原生 toast、
只用自绘通知窗** —— 这是产品决策，随时可单独重开。
