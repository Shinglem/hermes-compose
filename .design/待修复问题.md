### #2 内置编辑器：调研中（三条候选线）

- **优先级**：P2
- **涉及层**：UI（`files` 域）/ 产品范围（ADR-005 待重审）/ 契约（`/api/fs/*`）
- **状态（2026-11-16）**：**调研记录，未选型。** 现有**三条候选**：
  - **方向一 · WebView + Monaco**（ADR-078）：宿主是 Nucleus 官方 WebView 构件
    `dev.nucleusframework:composewebview`；宿主页走**本地 loopback http 服务**（Ktor CIO，反代 `/api/fs`）；
    **不接 LSP / git**。S1–S4 已实测通过，**S5 体积未达 8 MB（最小可用 AMD 集 22.04 MB）**。
  - **方向二 · 自研 + 对标开源**（ADR-079 / **ADR-080 可抄清单**）：照抄 aardink 的编辑内核
    （GapBuffer + LineIndex + CodeDocument + TokenStore + IME 桥 + 虚拟化，Apache-2.0）、
    auto-dev 的文件系统抽象形状与 LCS diff（MPL-2.0，**代码慎用**）。**不 fork 整仓**。
  - **方向三 · Markdown 编辑分工**（ADR-081）：**md-one 不废弃**，作为预览器；
    md-one 只加 ~55 行加性改动（`onBlockClick` + `activeBlockKey` + 稳定块 key + 源码态 adapter），
    编辑态放 `:modules:md-editor`。分栏模式 3–5 天 / L1 块级编辑 2–4 周。
  
  **三条在数据层可合流**（共用 `HermesFileSystem` / Repository），只在渲染层分叉。
  ADR-005 仍按现行实现执行（跳外部编辑器）。
- **已核实的后端事实**（不要再查一遍）：
  - `/api/fs/list` 只给 `{name, path, isDirectory}` → **`mtime` 无任何端点提供，补 0**；
  - 后端无文件系统监听，WebSocket 端点上无文件通道 → **`watch` 走方案 3**（agent 工具事件启发式刷新）+ 手动刷新；
  - `read-text` 超 512 KiB 截断（`truncated`）；`write-text` 上限 8 MiB 且**无版本比对**（stale 检测是客户端责任）；
  - `/api/fs/list` 失败是 **HTTP 200 + `error` 字段**，不能当成异常。
  - **后端 CORS 是白名单制**（`_LocalOriginCORSMiddleware` 只放行 bound_port /
    `dashboard.public_url` / `HERMES_DESKTOP_DEV_SERVER`）→ 编辑器页面**不能直连后端**，
    必须由本地 loopback 服务反向代理。
- **设计文档**：[`详细设计/功能/07-文件与编辑器.md`](详细设计/功能/07-文件与编辑器.md)、ADR-078
- **spike 判据（S1–S4 通过；S5 未达；不等于方向已选）**：
  1. ✅ **宿主页必须走本地 http 真源** —— 实测 `data:` 源下 `fetch` 失败、`new Worker(http)` 抛异常，
     只有 blob worker 能用；`http://127.0.0.1:<port>` 真源下全部正常（8 并发 worker 全 ok）。
     实现为 Ktor CIO loopback 服务 + 反代 `/api/fs`；后端 CORS 白名单制，页面不能直连；
  2. ✅ `composewebview 1.0.3` 与 Nucleus 3.0 运行期共存：窗口能开、WebView 能显示、JS 桥正常；
  3. ✅ 真实 Monaco 在真源下可用：91 种语言、`colorize` 26 span、`editor.worker` 可构造；
  4. ✅ `createDiffEditor` 正常：`getLineChanges()` 返回 1 条；
  5. ❌ **体积未达 8 MB**：最小可用 AMD 集 22.04 MB。Monaco 的 `editor.main.js` 硬依赖 4 个语言服务
     worker，删任一即加载失败（实测）；只能安全删非中文语言包（省 2.34 MB）。
     处置三选一：接受 22 MB / 手剥 AMD 依赖到 ~12 MB / 换 `@codingame/monaco-vscode-api`（5–10 MB，
     且是唯一提供 explorer 的）。
- **附带修正**：纯 `monaco-editor` **没有** explorer / `IFileSystemProvider`（`monaco.FileType` 不存在）。
  「文件树交给 Monaco」只有走 `monaco-vscode-api` 才能实现，否则文件树自己用 Compose 画。
- **回归判据**：`./gradlew :composeApp:webViewProbe`（S1/S2）、`:composeApp:webViewProbe3`（S3/S4）。
- **已否决的候选**（理由见 ADR-078「替代方案」）：纯 Compose 预览器、Zed、Lapce、Kortex（skiko 跨度太大，保留备选）、

### #21 原生 toast 能否不再依赖开始菜单快捷方式

- **优先级**：P2（体验 / 技术债；当前默认路径不触发，不阻断使用）
- **涉及层**：`core/platform`（`NativeNotifications.desktop.kt` 502 行 / `ShortcutScan.kt` 369 行 /
  `ShortcutAumidWriter.kt` 197 行 / `ProcessAumid.kt` 41 行）、打包（native dll）、依赖（`nucleus`）
- **状态**：**待 spike，明确不进 v0.6.0**（v0.6.0 只搬包不改逻辑，见
  [09-refactor.md](归档/v0.6.0-重构/09-refactor.md) §4 与验收口径 18）
- **触发**：v0.6.0 讨论 Alert-KMP 时提出「能否用 pwsh 直接调 .NET 注册 AUMID」

**先说清一个概念**：.NET / PowerShell **没有「注册 AUMID」这个 API**。AUMID 不是"写到某个键就生效"的对象。
旧 WinRT 方案里"注册"的实质是让 shell 能把这个 AUMID 解析到一个 exe，已知有两类写入：

| 写入 | 内容 | 解决什么 |
|---|---|---|
| 快捷方式 | 开始菜单 `.lnk` 里的 `PKEY_AppUserModel_ID` | 显示 + 归属（`.lnk` 自带 exe 路径） |
| COM 注册 | `HKCU\Software\Classes\CLSID\{GUID}\LocalServer32` = `"exe" -ToastActivated`<br>+ `AppUserModelId\<AUMID>` 的 `CustomActivator` = 该 GUID | **点击通知时启动/激活应用** |

**Toolkit 的 `RegisterAumidAndComServer<T>(aumid)` 做了什么（源码实证）**：
方法名里的 "Aumid" **有误导性** —— 它不建快捷方式、也不写 `AppUserModelId` 键，
**只注册 COM server**（用于点击后拉起应用）。所以既不能据此断言"注册了就能免快捷方式"，
也不能排除「COM 注册恰好够用」（官方示例从不建快捷方式）。**只能实测。**

**本机注册表现状（只读实测，作为对照证据）**

| AUMID 项 | DisplayName/IconUri | `CustomActivator` | CLSID `LocalServer32` | 开始菜单 `.lnk` |
|---|---|---|---|---|
| `Shinglem.HermesDesktop.fb97bfde`（我们） | ✅ | ❌ | — | ✅ |
| `C:/app/PowerToys/PowerToys.PowerLauncher.exe` | ✅ | ✅ | ✅ | ✅ |
| `oray.sunlogin`（向日葵） | ✅ | ✅ | 该 CLSID 无 | ✅ |
| `SkykakapoPortableToast-…` | ✅ | ✅ | 该 CLSID 无 | ✅ |

**全部样本都同时有快捷方式 → 无法反推**，必须做对照实验。

**三条候选路（含一条官方支持的）**

| 方案 | 快捷方式依赖 | 按钮 / 通知中心 | 成本 |
|---|---|---|---|
| 现状 `nucleus`（旧 WinRT） | 需要 | 都有 | 0（已工作） |
| **旧 WinRT + 只做 COM 注册**（Toolkit 做法去掉快捷方式） | **？ 待实测** | 都有 | **负成本**：若成立可删 607 行 + 381 行测试 |
| **Windows App SDK `AppNotificationManager`** | **不需要**（官方文档：unpackaged 应用 `Register()` 自动配好 COM 激活） | 都有 | 自写 JNI（Maven 无 JVM 封装）+ 运行时 30–40 MB；**提权应用不支持** |

**spike 第一步（三组对照实验，半小时出结论）**

必须用 **Windows PowerShell 5.1**（`pwsh` 7 已移除 WinRT 互操作）。判据不是"我看到了吗"，
而是 `ToastNotificationManager.History.GetHistory($aumid).Count` —— 它反映 toast 是否真的入队。

- **A 组**：只有 AUMID 字符串，什么都不注册（且无快捷方式）
- **B 组**：只写 `HKCU:\Software\Classes\AppUserModelId\<AUMID>` 的 `DisplayName` / `IconUri`
- **C 组**：B + `CLSID\{GUID}\LocalServer32` + `CustomActivator`

**结果判读**

| 结果 | 含义 | 后续 |
|---|---|---|
| A、B 失败，**C 成功** | COM 注册即可免快捷方式 | **收益最大**：可删 `ShortcutScan` + `ShortcutAumidWriter` + `ProcessAumid`（607 行 + 381 行测试），`nucleus` 只需补一次 COM 注册 |
| 全失败 | 快捷方式仍是硬需求 | 维持现状；免快捷方式只能走 Windows App SDK 或只自绘窗 |
| A 就成功 | 连注册都不需要 | 复核 [`12-通知窗.md`](详细设计/工程与代码/12-通知窗.md) §1 的四组旧实测再决定 |

**注意**：v0.6.0 迁 Tao 后 `NotificationOverlay` 不再是「`application {}` 里的第二个 `Window`」，
**自绘通知窗那条路线本身要重新验证**（见 09 篇 §2.9 / S6 第 6 步）。

### 已否决：后端改用 Windows 服务（SCM）托管（2026-11-10）

> 记录原因见 `AGENTS.md` §「不做清单和做清单同等重要」—— 不写下来，下一个 agent 会重新提议。

**原提案**：写一个 daemon 注册成 Windows 服务托管后端；新装时索要 UAC 创建服务；桌面端做服务管理；
后端由 SCM 自启、前端用普通自启；顺带让通知不再依赖开始菜单快捷方式。

**否决理由**（逐条核实后）：

| 提案想达到的目的 | 结论 |
|---|---|
| 后端独立于前端 | **已达成**，不需要服务：`gateway` 路线的 daemon 用 `CREATE_BREAKAWAY_FROM_JOB` 脱离我们的 Job Object |
| 登录自启不弹 UAC | **已达成**：计划任务 `RunLevel=HighestAvailable`（本机任务 XML 实测） |
| 日常不提权 | 真需求，但**不需要服务**：`app.elevate=never` + `HKCU\...\Run` 自启即可，更干净 |
| 开机即启动（不登录） | SCM 唯一独有的能力，但**对我们无价值** —— 服务在 Session 0，没有交互式桌面 |

**致命冲突：Session 0 无交互桌面。** 后端要跑在**用户的交互会话**里才能：

- `computer_use` 模拟键鼠操作真实窗口（上游 `hermes_cli/tools_config_cua.py:200` 自己写着
  「needed when driving Windows over SSH (**Session 0 has no interactive desktop**)」）；
- `browser.headed` 弹出可见浏览器窗口（本机 `config_custom.json` 就是 `headed: true`）。

也就是说「登录后才启动」恰好是**需要的**，而不是待消除的限制。
[`07-提权与自启动.md`](详细设计/工程与代码/07-提权与自启动.md) §2.1 早已论证并否掉过这条路。

**另外两条不成立的理由**：

- 上游**没有** Windows SCM 服务安装入口：`hermes gateway install` 在 Windows 上装的是
  **计划任务**（`hermes_cli/gateway.py:5542`）。`WindowsGatewayService` 与
  `hermes_owns_windows_service` 只用于**检测**归属（更新器判定「这是不是我自己的服务」，
  `gateway_windows.py:136`），`gateway-service/` 目录里放的是 `.vbs`/`.cmd` 启动器，不是 SCM 服务。
  做服务化等于与上游分叉。
- #13 / #14 的根因都不在后端形态：#13 是上游优雅关闭超时被取消后半死；#14 是客户端换端口后
  没重建会话订阅。服务化修不了这两条，还会把 `gateway.lock` 语义与 SCM 进程身份叠在一起，更难排障。

**替代方案**（已采纳方向，见 #15）：

1. `app.elevate` 默认 `never`，客户端全程普通权限；
2. `app.autostart` 增加 `run` 选项（`HKCU\...\Run`，无需 UAC、零系统对象），`task` 保留给确实需要时刻提权的用户；
3. 需要操作管理员窗口时，按需 `runas` 拉起**一次性**提权动作，主进程不动；
4. 后端管理与端口跟随按 #15 做。

**关于通知不绑快捷方式**：与后端形态无关，是 Windows Shell 层硬限制 —— toast 归属只认开始菜单
`.lnk`（[`12-通知窗.md`](详细设计/工程与代码/12-通知窗.md) §1 的四组实测已排除桌面 `.lnk`、
注册表、`App Paths`、COM activator 等全部替代）。真要摆脱快捷方式，只能**放弃原生 toast、
只用自绘通知窗** —— 这是产品决策，随时可单独重开。

### #22 `ChatViewModel` 仍是单文件（唯一 >600 行）

- **优先级**：P2（可维护性，不影响功能）
- **涉及层**：`component/chat/ChatViewModel.kt`（1951 行）、`component/chat/DefaultChatComponent.kt`
- **现状**：v0.6.0 的验收口径要求「单文件 > 600 行从 11 个降到 0」，实际降到 **1 个**。
  已拆出去的：六类平行簿记（`SessionRuntimeStore` / `PendingRequests` / `SessionSnapshotCache` /
  `SessionModelCache`）、三份流式实现合并成 `ChatReducer`、`handleGatewayEvent` 137 → 30 行。
- **为什么没继续拆**：剩下的体量是「单实例多会话状态机」本身的复杂度，不是排列问题。
  继续拆需要 **per-session Component**（S4 的完整形态）—— 涉及 `RootComponent` 的 `ChildStack`
  与 `InstanceKeeper` 作用域，是独立一轮的量级。
- **偿还方式**：按会话拆 Component（每个会话一个 `ChatComponent`，由 `ChildStack` 管理），
  这样 `SessionSnapshotCache` / 影子状态可以整体删除。
- **验证口径**：`ChatViewModel.kt` 归档删除；per-session 测试覆盖「切走 → 后台推进 → 切回」。
