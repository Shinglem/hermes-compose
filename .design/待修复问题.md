### 第二轮追记（2026-11-04，真机复现后修）

**#2 补充现象**：审批只在 A 里发起，切到 B 后 B 的对话区也画出那张卡片 —— 用户会当成 B 的事。
根因：`pendingApprovals` 是跨会话的全局集合（后端在等，卡片丢了会白等到超时），而 `ChatPane`
无条件全画。修法：`ChatState.visibleApprovals` / `visibleClarify` 按 `SessionKey` 过滤，
归属不明（`sessionKey == null`）的仍显示 —— 藏起来就永远没人处理。判据见
`ChatStateVisibilityTest`。

**#2 增强**：审批通知上直接给「允许一次 / 拒绝」按钮（`NotificationPopup` 自绘窗，右下角）。
系统托盘气泡不支持按钮，Windows Toast 的按钮要注册 AppUserModelID + COM 激活回调，
绿色版路径会变、清理成本高；自绘窗跨版本稳定，且不走"先拉窗口再找卡片"这条弯路。

**#3 复现与根因（第二轮）**：在 A 发消息 → 切到 B → 切回 A，界面停在切走前那一帧，
必须点「刷新」才出内容。根因不在决策表，而在**丢弃的增量再也补不回来**：

```
切走 → stash 快照；A 的事件因 otherKey != 当前会话 → 只标 dirtyKeys，内容丢弃
切回 → RESTORE_SNAPSHOT（正确）→ 查 isSessionLive
       └─ 那轮还在跑（审批就是在等它）→ true → 跳过补拉
       └─ 后续事件只从"当前这一帧"往后接，中间那段永久缺失
```

`isSessionLive` 本身是 `runCatching` 后**回退为 true**（失败时保守当作还在跑），
所以"补拉"这条路在审批挂起期间基本不会走到。修法：切走期间把事件**继续应用到该会话的快照**上
（`ChatState.applyShadowEvent`，纯数据变换，见 `SessionShadow.kt`），切回时快照本身就是最新一帧；
判据见 `SessionShadowTest`（7 例：正文累积、思考分段、工具起止、整轮落盘、无流式时不凭空加条目、历史保留）。

### 触屏手势的两种路径（实测，Windows）

| 手势 | 系统合成 | 能否跟手 |
|---|---|---|
| **按住后再移动** | 鼠标拖动（`MOUSE_PRESSED/DRAGGED`，一次 3 秒手势 127 个 move） | **可以** —— 由 `touchDragScroll` 手动 `dispatchRawDelta` |
| **直接快速甩动** | pan 滚轮（`PointerEventType.Scroll`，一次手势只有 4–6 个事件） | **不可能** —— 拿不到触点，只能离散滚动 |

坑：按住拖动期间系统**同时**在发 pan 滚轮（实测一次手势 189 个 `Scroll`），不吞掉会与手动位移叠加，
表现为"滚一段跳一下"。`touchDragScroll` 在拖动中与松手后 250ms 内 `consume()` 掉这些事件。

实测修复后（会话列表）：`presses=1 moves=127 dragging=true`，`first` 从 10 连续走到 23。

**#1 第一次实现无效（2026-11-03 复核）**：在 `Main` pass 里检查 `isConsumed` 时，
消息正文的 `SelectionContainer` 已经消费了全部 `DRAGGED`，所以一个像素都没滚。
demo 里加了一栏「`SelectionContainer` + 拖动」复现：`first` 完全不动；改成 `Initial` pass
（先于子节点）后同一栏 `first` 从 0 走到 4。代价是**拖动选字让位给滚动**，选字改用
「复制整条 / 引用」。

状态口径：`待调查`（根因未定）→ `已定位`（根因明确、方案待定）→ `修复中` → `待验证` → `已修复`。

优先级口径：**P0** 主功能不可用或造成数据/状态错乱；**P1** 功能可用但会卡住流程或让人误判；
**P2** 体验问题，有替代操作。

## 1. 触屏滑动不跟手，轻划翻页过多

**优先级** P2 ｜ **状态** **已修复**（2026-11-04，真机确认）

> 根因不是 Compose 不会滚，而是 **JBR 把触摸合成成离散滚轮事件**（同版本对照见 10 篇 §9）。
> 运行时基线换成 Temurin 27 后触摸还原成 press/move，`Modifier.touchDragScroll` 即可跟手，
> `WM_TOUCH` 子类化方案与 `:modules:win-touch` 一并删除（10 篇 §14）。
> 下面保留原始现象与实测数据，供回归时对照。

### 现象

Windows 触屏设备上：

- 手指拖动时列表位移落后于手指（不跟手）；
- 一次很轻的划动会滚过远超预期的距离（"翻页过多"）；
- **缓慢地一直向下滑时，内容先迅速翻很多行，然后停住不再跟随，无法连续滑动**。

最后一条是关键判据：它不是"惯性太大"（缓慢滑动不产生 fling），而是**一次手势只换来极少几次、
每次位移极大的滚动**，之后事件流就断了。

### 实测结论（2026-11-03，demo 见 `S:\mine\project\touch-probe`）

用真实触摸屏在四个区同时记录事件，**结论与最初假设相反**：

| 操作 | 事件形态 | 结果 |
|---|---|---|
| 手指拖动 2.4–3.2 s（缓慢） | `Press` + 密集 `Move`（AWT `DRAGGED`）+ `Release`，**0 个 `Scroll`** | A 区（普通 `LazyColumn`）**完全不动**；B 区（`draggable`）连续滚动 |
| 手指在 C 区（接管 `Scroll`）拖动 | Move 52 个、`Scroll` **0 个** | C 区不动 → **"接管 Scroll"方案对触屏无效** |
| 鼠标滚轮各 3 格 | 34 / 47 个 `Scroll`，`preciseWheelRotation` 是小数（0.71/0.17/0.21…），`scrollAmount=3` | A 区滚 4.4 行；C 区滚 20 行 |

关键数字（日志 `%TEMP%\touch-probe.log`，共 611 条事件）：

- A 区四段触摸拖动 226 个事件、Move 91 个、**Scroll 0 个**；`first` 全程为 0；
- B 区一段触摸拖动 94 个事件（Move 52），`first` 从 0 连续涨到 10（279 次位置更新）
  → **`draggable` 跟手且连续**；
- 触摸拖动在 AWT 里就是 `MOUSE_PRESSED / MOUSE_DRAGGED / MOUSE_RELEASED`，`pt=Mouse`、
  `mods=1024`（左键按下），与鼠标拖动**无法区分**；
- D 区（无滚动容器）同样收到 `Press` + 46 个 `Move` —— 事件到达正常，只是没人处理。

因此：

1. 触摸**不是**被合成为 wheel（原假设错误），而是合成成鼠标拖动；
2. `LazyColumn` 不动的原因正是 `CanDragCalculation = { type != PointerType.Mouse }`；
3. wheel 路径只服务鼠标滚轮 / 触控板；`scrollAmount=3` 的放大确实存在
   （`delta × 视口/20 × 3`），但与本问题无关；
4. `LocalScrollConfig` 是 `internal`，应用层改不了这个公式；
5. **"迅速翻很多行然后停住"就是吸底，已用 demo 复现确认**（2026-11-03，第二次触摸实测）：
   `ChatPane` 的 `followTail` 初始为 `true`，只由 `PointerEventType.Scroll` 置位/复位；
   触摸拖动**永远不产生 `Scroll`** → `followTail` 恒为 `true` → `totalItems` 一变
   （流式新增、工具卡片）就 `scrollToItem(totalItems - 1)` 把列表拽到底。
   用户手指滑不动（`scrollable` 忽略 mouse drag），却看到列表不断"跳" —— 那是吸底，不是滚动。

   复现数据（demo 三栏，内容每 900ms 增一行，一次触摸拖动期间）：

   | 栏 | 拖动期间 `first` 更新 | 拖动期间吸底跳转 | 观察 |
   |---|---|---|---|
   | A 无吸底 | **0 次** | — | 手指滑，列表**纹丝不动** |
   | F 吸底（复刻项目） | 4 次（`102→103→104→105`） | **4 次**（`jump-to=112..115`），且 `followTail` 从未变 `false` | 手指滑不动，列表**每 900ms 自己跳到底**（用户原话："一直在自增"） |
   | B `draggable` | **226 次**（`idx 0→11`，逐帧） | — | 连续跟手 |

   即：**F 栏 = 项目现状**（吸底无视正在进行的拖动），A 栏 = 去掉吸底后暴露出的真实问题
   （拖动完全没被处理），B 栏 = 唯一能工作的方案。

### demo 与复现方法

- 代码：`S:\mine\project\touch-probe`（**独立 Gradle 项目，不属于本仓库**，不影响项目构建）。
- 四栏：A 普通 `LazyColumn`（无吸底）、B `draggable` 手动滚、C 接管 `Scroll`、D 空白区；
  每栏标题的 `first=` 是首个可见行，底部是事件日志。
- 事件同时写入 `%TEMP%\touch-probe.log`（含 `LAYOUT` 坐标与 `FIRST` 滚动位置），便于脚本分析。

**已复现"翻很多行然后停住"（2026-11-03，第二次实测）**：demo 的 F 栏复刻了项目的吸底
（`followTail` + `scrollToItem(totalItems - 1)`，内容每 900ms 增长）。一次触摸拖动期间，
F 栏发生 4 次吸底跳转、`followTail` 从未变 `false`，用户观察为"一直在自增、手指没用"；
同一次拖动在 A 栏（无吸底）`first` 更新 **0 次**、在 B 栏更新 **226 次**（连续）。

### CMP 桌面触摸能力：官方没有方案（2026-11-03 调查）

**结论：CMP 桌面端不提供触摸输入通路，官方明确依赖操作系统把触摸转成鼠标事件。**
这不是本项目漏接，也不是配置问题，应用层无法"打开"。

| # | 证据 | 说明 |
|---|---|---|
| 1 | 官方回复 [compose-multiplatform#1555](https://github.com/JetBrains/compose-multiplatform/issues/1555)（contributor akurasov，2021-12，closed） | 原文："There is no explicit touch screen support, Compose relies on OS level conversion of touch Screen events to mouse events."；需要处理拖动手势时建议用 `Modifier.draggable` |
| 2 | `ui-desktop` 的 `ComposeSceneMediator.desktop.kt` | AWT 的 `MouseEvent` / `MouseWheelEvent` 一律以 `type = PointerType.Mouse` 送入；整个 `ui-desktop` 源码里 `TouchEvent` / `enableEvents` / `AWTEvent.TOUCH` **零命中** |
| 3 | `foundation` 的 `AbstractScrollableNode.kt` | `CanDragCalculation = { type -> type != PointerType.Mouse }`，旁边写着 `// TODO: provide public way to drag by mouse (especially requested for Pager)` —— **`scrollable` 主动禁止鼠标类型拖动**，而触摸恰好就是鼠标类型，所以 `LazyColumn` 根本收不到拖动滚动 |
| 4 | JDK 层 | 打包用的 JBR 25 与开发用的 JDK 27 上，`javap java.awt.event.TouchEvent` / `GestureEvent` 均为 **MISS**（AWT 触摸 / 手势 API 在这两个发行版里不存在），连 AWT 原始触摸事件都拿不到 |
| 5 | `PointerType.Touch` / `PointerEventType.PanMove` | 只出现在公共 API 默认参数、文档与测试里；桌面输入转换不产生它们（`PanMove` 只在 macOS / Linux 的手势分支被消费） |

**唯一被官方认可的替代**：`Modifier.draggable`（不过滤指针类型，能吃触摸合成的鼠标拖动）
手动驱动 `scrollState.scrollBy(-delta)`，见 #1555 里的社区示例。

### 可选路径评估

| 路径 | 可行性 | 代价 | 副作用 |
|---|---|---|---|
| 1. 接管 `PointerEventType.Scroll`，按自己的比例滚 | **已实测否证**（触屏 0 个 Scroll 事件） | — | 只覆盖鼠标滚轮 / 触控板 |
| 2. `Modifier.draggable` + `scrollBy` + 自建 fling | 可行（官方建议） | 中 | **鼠标**按住拖动也会变成滚动 → 抢走消息区的文本拖选；需按设备能力开关（有触摸屏才启用）或做成设置项 |
| 3. JNA 截 `WM_TOUCH` + `ComposeScene.sendPointerEvent(type = Touch)` 注入 | 理论可行 | 大 | `ComposeWindow` 不暴露 `ComposeScene`；社区实测 `TextField` 等按鼠标硬编码，注入 touch 会引入新的不一致；还要自己处理 DPI、多指、手势仲裁 |
| 4. 换 WebView / 换 UI 栈 | 否决 | — | 违反 AGENTS.md 非目标（不引 WebView），与"用 M3 原生组件"冲突 |

**不做路径 3**：收益只是手感，代价是自建输入层并与 Compose 内部假设打架 —— 为一处体验改动整个输入栈。

### 修复方向

| 方案 | 做法 | 说明 |
|---|---|---|
| A. `Modifier.draggable` 接管拖动（唯一可行） | 列表外层 `draggable(Vertical, startDragImmediately = true) { delta -> state.dispatchRawDelta(-delta) }`；`onDragStopped` 用 `splineBasedDecay` 补 fling | 实测有效（B 区连续滚 10 行）；方向已验证：向上拖（y 减小）→ `first` 增大 |
| B. 修吸底判定 | 不要只靠 `Scroll` 复位 `followTail`；改为「用户按下并拖动（`Move` + `pressed`）或离开底部即暂停吸底」，并在用户停止拖动 N 秒后才恢复 | 触摸拖动不产生 Scroll，现有判定永远看不到用户意图（实测 `followTail` 从未变 `false`） |
| C. 设备 / 设置开关 | 有触摸屏才启用 A，或提供设置项 | `PointerType` 无法区分触摸与鼠标，只能按设备能力兜底 |

必须一并处理的副作用：`draggable` 会吃掉鼠标左键拖动 → 消息区的 `SelectionContainer` 拖选失效。
三选一：按设备启用、做成设置项、或只在列表空白 / 滚动条区域启用。

**不做**：接管 `Scroll`（实测对触屏无效）；改 `LocalScrollConfig`（`internal`）；
自绘 `pointerInput` 手写惯性替换 `LazyColumn`（要自己处理嵌套滚动、吸底、选择链，得不偿失）。

### 验收口径

CMP 桌面拿不到 `PointerType.Touch`，但触摸拖动本身就是**连续的鼠标拖动**（实测 2.9 s 内
200+ 个 `DRAGGED`，位置逐帧变化），所以 `draggable` 方案**可以做到跟手**；
限制只剩"无法区分触摸与鼠标"，需要按设备 / 设置开关兜底。

### 验证

- 触屏缓慢持续滑动：`firstVisibleItemIndex` 单调变化、中途不停顿，与手指位移大致成比例；
- 轻划 10 次，越过目标行的次数 ≤ 1；
- 触屏上滑看历史时**不被吸底拉回**（吸底判定必须能感知拖动）；
- 鼠标滚轮 / 触控板行为不回归；鼠标拖选文本仍然可用（若改为按设备启用，需在无触摸屏机器上回归）。

## 2. 审批等待中且窗口不在前台时没有系统通知

**优先级** P1 ｜ **状态** 已定位

### 现象

Agent 触发需要确认的操作（命令审批）时，弹窗落在客户端窗口里。若用户此时在别的应用里，
完全收不到提示，经常错过 —— 后端审批超时（300s）后按拒绝处理，命令直接失败。

### 根因（已确认）

- 通知能力存在但**只接在"一轮结束"上**：`AppShell` 里 `chatViewModel.onTurnFinished`
  → `SystemNotifications.show(...)`，且带 `!AppFocus.isForeground` 判断。
- 审批走的是 server→client `approval` 请求，落点是 `ChatViewModel.awaitApprovalDecision(...)`：
  它只更新 `pendingApprovals`（给 UI 画卡片）并 `acknowledgeApproval`，**没有任何通知回调**。
- `SystemNotifications`（desktop）复用 `DesktopTray` 的 `TrayIcon.displayMessage`，已有可用实现，
  不需要新依赖。

### 修复要点

1. `ChatViewModel` 增加 `onApprovalRequested: ((PendingApproval) -> Unit)?`，在
   `pendingApprovals` 被写入后回调一次（补拉路径 `refreshPendingApprovals` 也要触发，
   否则"请求发出时本端不在线"的场景仍会漏）。
2. `AppShell` 接线：`preferences.notificationsEnabled && !AppFocus.isForeground && supported`
   → `SystemNotifications.show("… 等待确认", command 摘要)`。
   **不要**加"是否当前会话"的前置判断：审批是全局事实，用户可能正看着别的会话。
3. 去重：同一 `requestId` 只通知一次（重连补拉会重复拿到队列条目）。
4. 交互（可选，成本另算）：点通知直接切到对应会话并置顶窗口；若不做，正文里要写清是哪个会话。

### 已知限制（要写进用户可见说明，不要当 bug 再报）

`TrayIcon.displayMessage` 依赖托盘图标存在。窗口完全退出、托盘未安装、或系统通知被用户关掉时，
通知不会出现 —— 这是 Windows 侧的限制，不是漏接线。

### 验证

- 手动制造审批（例如让 agent 执行一条需要确认的命令），切到别的应用，确认出现系统通知；
- 窗口在前台时不弹（避免噪音）；
- 同一请求重连后不重复弹第二次；
- 关掉设置里的通知开关后完全不弹。

## 3. 多 profile / 多会话并行时回复流丢失，界面看起来像卡死

**优先级** P0 ｜ **状态** 需详细调查（主因已定位，并存路径待验证）

### 现象

同时有多个 profile、多个会话在跑时，切走后回来的对话不再吐字，看起来像卡死；点顶栏刷新
（force reload）能拿到完整回复。也就是说**服务端内容是全的，客户端丢了增量**。

### 已定位的主因：事件只服务"当前打开的那个会话"，切走即永久丢弃

`ChatViewModel` 是单例，事件消费是"当前会话独占"式的：

1. `gateway.events.collect(::handleGatewayEvent)` 一次订阅，`handleGatewayEvent` 第一行取
   `_state.value.key`（当前打开的会话）与 `runtimeIds[key]`，取不到就直接 `return`；
2. 接着 `if (event.sessionId != null && event.sessionId != runtimeId) return` ——
   **别的会话的 delta / tool / `message.complete` 全部丢弃**，没有按会话缓冲；
3. 用户切走 A → 打开 B：A 的事件在此后全被丢弃；A 若在此时完成，`message.complete` 也一并丢失；
4. 切回 A 时 `open()` 命中 `cache[key]` 分支：直接 `publish(key, loaded)`（**缓存里的旧 transcript**）
   + `resumeInBackground`，**不会重新拉取**；
5. `publish()` 用新的 `ChatState(...)` 覆盖，`streaming` / `sending` 归默认值（null / false）——
   UI 上"正在生成"的指示消失，正文停在切走那一刻，于是"看起来卡死"。

刷新按钮走 `open(..., force = true)`，跳过 cache 重新 `loadTranscript`，所以内容能补齐 ——
与用户描述完全一致。

### 待验证的并存路径（修复前必须逐条排掉）

这几条都会产生"当前会话也在丢字"的表现，需分别取证（在 `handleGatewayEvent` 与
`publishEvent` 加结构化日志，记录 `type / sessionId / runtimeId / 是否被丢弃`）：

1. **`runtimeIds[key]` 尚未建立时的早期事件**：新建会话 / 刚切回时 `session.resume` 还没回来，
   此时到达的 delta 全被第一行 `return` 丢掉。
2. **共享流缓冲溢出**：`GatewayClient._events` 是 `MutableSharedFlow(extraBufferCapacity = 512,
   onBufferOverflow = DROP_OLDEST)`，且无 replay。高频 delta（多会话 + 长回答）下是否真的丢过？
   丢的时候日志里不会有任何痕迹 —— 需要加丢弃计数才能证明或排除。
3. **订阅者缺席窗口**：`viewModelScope` 取消 / 重建期间，`tryEmit` 出去的事件无人接收即消失。
   需确认 `ChatViewModel` 在多 profile 切换时是否被重建。
4. **`sessionId` 缺失的事件**：现在 `event.sessionId != null` 才做过滤，`null` 一律接受。
   反向的问题也成立 —— 若后端某些事件带了不同命名空间的 id（stored vs runtime、subagent id），
   会被**误判为别的会话**而丢弃。要逐类事件核对 id 来源。
5. **`deltaBuffer` / `flushJob` 残留**：`appendDelta` 用 `if (flushJob?.isActive == true) return`
   合并 40ms 窗口；若 `flushJob` 被取消而缓冲未清，下一轮会把上一轮的残字混进来（表现为串字，
   与"卡死"是不同症状，一并验证）。

### 修复方向（三条路，按代价排序，需先定稿再动手）

| 方案 | 做法 | 代价 | 局限 |
|---|---|---|---|
| A. 切回时补拉 | `open()` 在 cache 命中前，先查 `session.active_list` / `session.status`；仍在跑或流已结束就强制 reload 或增量补 | 小 | 切走期间仍无实时感；若会话仍在跑，之后的事件仍被丢 |
| B. 按会话缓冲事件 | 新增一个事件分发器（按 `runtimeId` 收流式增量 + `message.complete`），切回时回放 | 中 | 需处理缓冲上限与内存；与现有缓存合并逻辑要理顺 |
| C. 增量补拉通道 | 用 `session.events.since`（常量已定义在 `RpcMethods`，**目前无任何调用**）从断开点补事件 | 中 | 要先确认后端该方法的游标语义与保留窗口 |

方案 A 能立刻消除"假装卡死"的观感，方案 B/C 才真正实现"后台会话持续累积"。
建议先做 A 止血、再按 B 或 C 补全；**不要**只做 A 就当作已修。

### 待澄清（实现前必须问清）

- 产品上是否要支持"多会话同时可见"（分屏 / 多窗口）？若近期不做，B 只需保证切回即完整，
  不需要保留实时增量。
- `session.active_list` 的 `session_key` 与 runtime id 的映射关系要实际抓一次响应确认。

### 验证

- 起两个 profile，各开一个会话同时发长任务；切走 A 再切回，A 必须显示已完成的完整回答（含工具段）；
- A 仍在跑时切回，应继续吐字且不串字；
- 用日志统计"被丢弃事件数"，修复后应为 0（或仅在明确不关心的类型上非 0）；
- 大回答（>2000 行代码）流式期间不丢尾段。

## 4. `clarify` 无法处理（不显示问题、无法作答）

**优先级** P1 ｜ **状态** 已定位

### 现象

Agent 调用 `clarify` 工具向用户提问时，客户端不展示问题，用户也无法选择或回答，只能等它失败。

### 根因（已确认）

`ChatViewModel.init` 只注册了 `approval` 一个 server→client handler：

```kotlin
gateway.onServerRequest(APPROVAL_REQUEST) { frameId, params -> awaitApprovalDecision(frameId, params) }
```

`GatewayClient.answerServerRequest` 对未注册的方法统一回 `-32601 method not supported`。
后端收到后按"该客户端不支持请求"处理，`clarify` 直接失败。

### 契约（只读，来源 `tui_gateway/contracts/server_requests.py`）

方法名 `clarify`，有单问与批量两种形状：

| 字段 | 类型 | 说明 |
|---|---|---|
| `question` | string? | 单问的题干 |
| `choices` | string[]? | 单问的选项；为空表示自由文本 |
| `multi_select` | bool? | 单问是否多选 |
| `questions` | `{qid, question, choices?, multi_select?}`[]? | 批量问 |
| `answers` | map<qid,string>? | **仅重连回放**时出现，表示服务端已锁定的答案 |

应答（`ClarifyResult`）：

- 单问：`{answer: "..."}`，空串 = 跳过；
- 批量：`{answers: {qid: "..."}}`；
- **两者都不给 = 取消全部**（这是唯一的"放弃"语义，不要自己发明字段）。

批量早锁走 RPC `clarify.lock`（`{request_id, question_id, answer, profile?}`，返回
`{status: ok|expired, remaining: [qid]}`）；客户端从未收到帧时可用 `request.answer`
（`{id, result, profile?}`）代为应答。这两条是**可选增强**，不是第一版必需。

### 修复要点

1. `ChatViewModel` 注册 `clarify` handler，与 `approval` 同一套骨架：解析 → 上屏 → 等用户作答 →
   回 `{answer}` / `{answers}` → finally 清卡片。超时策略参照 `approval`（后端超时 + 30s 兜底）。
2. 新增 `ClarifyCard`：
   - 单选：选项按钮列表 + 「其他」自由输入（`choices` 为空时直接是输入框）；
   - 多选：多选列表，确认后按后端约定拼成一个字符串（**拼法要实测**：需抓一次官方客户端的
     真实应答，确认是逗号分隔还是 JSON 数组字符串；契约只写了 `str`）；
   - 批量：逐题渲染，锁定时可走 `clarify.lock`；不实现锁就一次性提交全部 `answers`；
   - 「跳过」→ 空串；「取消」→ 回空结果（两边都不给）。
3. 与审批卡片一样，`pendingClarify` 不能因切会话被 `publish()` 清掉（`clarify` 同样是
   "后端正在等"的全局事实）。
4. 非当前会话的 `clarify`：与审批同理，现在 handler 不按 session 过滤，卡片会插到当前会话上。
   要么按 `runtimeSessionId` 路由到对应会话，要么至少在卡片上标明来源会话。
5. `restart` / 重连后：参照 `approval.pending` 的补拉，需要一个能取回"未完成的 clarify"的通道
   （契约里没有 `clarify.pending`；先确认后端重连回放 `answers` 的触发条件，再决定是否支持）。

### 待确认（实现前必须实测）

- 多选答案的字符串编码（逗号 / 换行 / JSON）——**必须抓真实应答**，不要猜；
- 批量 `questions` 在 UI 上是同屏一次问完，还是逐题（官方 TUI 的交互节奏）；
- `clarify` 的超时值（后端侧），决定本端兜底时长。

### 验证

- 让 agent 调用 `clarify` 问一个单选问题 → 卡片出现 → 选一项 → agent 收到答案继续；
- 自由文本问题能输入中文并送达；
- 多选与批量各验证一次；
- 点取消后 agent 得到"取消"而非报错；
- 切到别的会话再切回，未作答的 `clarify` 卡片仍在。
