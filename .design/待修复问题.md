#### B 组判定（中文排版为什么不做）

"等宽字体就能解决"是误解，这里其实是三件事：

| 名称 | 解决什么 | 谁来提供 |
|---|---|---|
| 等宽字体 | 字符宽度固定 → 代码/表格**对齐** | 字体本身 |
| 中西文自动间距（气口） | 阅读节奏，字与字间加 1/8–1/4 em | **排版引擎**（CSS `text-autospace`、InDesign） |
| 标点挤压 | 行首 `，。` 不占全幅 | **排版引擎**或字体 OpenType `palt`/`halt` |

Compose Desktop 的文本引擎（Skia Paragraph）不做后两者。只剩两条路，代价都不划算：

- 往 `AnnotatedString` 插 `U+2009`/`U+200A` → **污染复制与引用**，且本库大量用**偏移量**做 chip、脚注编号、行内定位，插字符会让所有偏移错位（与硬约束 6 的选择机制直接冲突）；
- `SpanStyle(fontFeatureSettings = "palt")` → 只能压标点宽度，做不到中西文之间加白。

另外原版 Electron 走 Chromium，`text-autospace` 也长期没默认开启 —— 不做**不会比原版差**。

**替代项（建议单独立项、未纳入本版）**：代码块换「中文正好 2 倍宽」的等宽字体（如 Sarasa Mono SC），
能根治含中文注释的代码块对齐歪斜；成本只有几行 `FontFamily` 改动 + 字体分发。

#### D 组更正：后端已剥离 ANSI，整组不做

初判「`ToolCallCard` 裸渲染 `ESC[32m` → 用户看到乱码」是**错的**。后端
`hermes-agent/tools/ansi_strip.py` 的 docstring 明确写着：

> Strip ANSI escape sequences from subprocess output **so they never reach the model's context**

且被 12 处调用，覆盖所有会产出终端样文本的路径：
`terminal_tool_result.py`（终端结果）、`process_registry.py`（进程输出）、`mcp_tool_content.py`/`mcp_tool_handlers.py`、
`code_execution_tool.py`/`code_kernel.py`、`read_extract.py`、`file_operations_lint.py`、`session_search_tool.py`。

所以工具结果到达前端时**已无 ANSI**，没有对象可着色；模型自己也不会产生 ESC 字节。
**D 组（ANSI / 日志级别 / emoji / 内联 svg / 图表 / 音视频 / PDF）全部不做。**
教训：判断「显示缺陷」前先确认数据在到达渲染层时是否已被上游清洗。

#### F 组的取证：`MdBlock.Image` 是死代码

- `MdBlockFactory` **从不产出** `MdBlock.Image`（只产 `TABLE`），
  `Formats.Image` 与 `BlockViewportConfig.formats` 里的 `"image.generic"` **永不命中**；
- 所以独占一行的 `![](url)` 实际走 `Paragraph` → 行内图片，**既无限高缩放也无点击**；
- 大截图（如 2000×3000 的报错图）被压到可用宽度后**无法看细节** —— 这才是「点击放大」的真实价值，不只是「点了没反应」。

#### 代码高亮引擎：四个候选的实测结论（2026-11-05 spike）

原方案是 `dev.snipme:highlights`（17 个枚举、无别名）+ 本库自写 9 组正则，
缺口是「很多语言没有词法器」。四个候选实测后**只接 SyntaxMP 的 tokenizer**：

| 库 | 许可 | 产物 | 实测结论 |
|---|---|---|---|
| **`com.gallatinapps.syntaxmp:syntaxmp-tokenizer`** | Apache-2.0 | 622 KB，**只依赖 kotlin-stdlib** | **采用**。54 个 label 命中；角色是点分路径（`keyword.control` / `variable.namespace` / `constant.builtin`），比原来 10 档 `TokenKind` 更细；PowerShell / Markdown / INI / Properties / Dotenv / GraphQL / Protobuf / Makefile / C# / SQL 方言都是真词法器 |
| `io.github.huarangmeng:codehighlight-parser`（CodeHigh） | MIT | 139 KB，零 Compose | 备选。28 个 lexer，**README 宣称的 C# 实际没有**；缺 PowerShell / Markdown / INI / Properties / CSV / GraphQL / Protobuf |
| `dev.snipme:kodeview` | Apache-2.0 | — | 排除。就是 `highlights` 的视图封装（我们已在用 Highlights），依赖 Compose **1.6.11**、2024-11 后停更 |
| `komodgn/compose-codeview` | 无 license 文件 | JitPack | 排除。源码目录只有 android / ios / js / wasm，**没有 JVM desktop target** |

实测数据（119,600 字符同一段样本 ×400）：

| | 冷 | 热 |
|---|---|---|
| SyntaxMP tokenizer | 146 ms | 38–53 ms |
| CodeHigh parser | 64 ms | 20 ms |

按本库 `MAX_CODE_LENGTH = 40_000` 折算，SyntaxMP 约 50 ms 冷 / 15 ms 热，可接受。

**落地形态**：只依赖 `syntaxmp-tokenizer`（**不带 Compose**，与 CMP 版本无关），

### #6 系统原生通知：多个审批只弹出一个（P1 · v0.4.2 必做）

- **优先级**：P1
- **涉及层**：`composeApp`（`platform/NativeNotifications.desktop.kt`）
- **现象**：同一个会话内连续来 2 个以上审批请求，系统通知（右下角 toast）**只显示最后一个**，
  之前的被顶掉；且被顶掉那条的「允许/拒绝」按钮点了没反应。
  非原生（自绘）通知已在 v0.4.1 修好（`NotificationInbox` 队列 + 最多 3 条堆叠），**本项只针对原生 toast**。

- **根因**（已定位到行）：
  - `NativeNotifications.desktop.kt:465-466` 把 `TAG = "hermes"` / `GROUP = "approval"` 写成**常量**，
    `show()` 每次都用同一对 `tag`+`group` 调 `WindowsNotificationCenter.show(...)`（`:331-334`）。
    WinRT 的语义是 **同 `tag`+`group` 的 toast 为"更新同一条"**，后发的直接替换先发的 → 只剩一个。
  - `:310` 处 `tokens.clear()` 每次 `show()` 都清空**全局** token 表，前一条的按钮回调被抹掉 →
    即使第一条还在，点它的按钮也是空转。

- **修法**：
  1. `tag` 改为按请求唯一：WinRT 限 16 字符，用 `requestId` 的稳定短哈希（如 SHA-1 前 8 字节的十六进制，
     共 16 字符）做 tag；`group` 保持常量 `"approval"`（同组才堆叠）。
  2. token 表按 tag 分桶：`ConcurrentHashMap<String, MutableMap<String, () -> Unit>>`；
     `show()` 只清**本 tag** 的桶，`onActivated(tag, …)` / `onDismissed(tag, …)` 按 tag 查/删对应桶。
  3. 无按钮的提示类 toast（"本轮完成"）可继续用固定 tag —— 同类重复替换是期望行为。

- **验收口径**：
  - 同一会话连发 3 个审批 → **3 条 toast 同时在通知中心并存**（不互相替换）；
  - 每条各自的「允许 / 拒绝」都能点，且对应到正确的那条请求（点第 2 条的"允许"不会误批第 3 条）；
  - 点掉某一条只清它自己（其余仍在），通知中心里也不残留已 dismiss 的条目；
  - 「本轮完成」类提示连续两条仍然只留最新一条（保持原行为）。

### #10 官方桌面端启动后要求"配置后端"（缺 REMOTE_URL / TOKEN）

- **优先级**：P1（用户实测缺陷）
- **涉及层**：`composeApp`（`OfficialDesktopLauncher` + `DesktopContainer`）；**不改后端**
- **现象**：从桌面端「设置 → 调试 → 官方桌面端」启动对照包后，它显示"配置后端"向导，
  不能直接连上我们已在跑的后端。
- **根因**：`OfficialDesktopLauncher.desktop.kt` 的 `officialDesktopEnv()` 只设了两个变量：

  ```kotlin
  "HERMES_DESKTOP_USER_DATA_DIR" to .../userdata
  "HERMES_HOME" to .../hermes-home
  ```

  而官方桌面（`electron-main.mjs`）的 `resolveDesktopRemoteRoute()` 要连已有后端**必须**同时拿到：

  ```js
  env: { token: process.env.HERMES_DESKTOP_REMOTE_TOKEN, url: process.env.HERMES_DESKTOP_REMOTE_URL }
  // 只给 url 不给 token 会直接抛错：
  // "HERMES_DESKTOP_REMOTE_URL is set but HERMES_DESKTOP_REMOTE_TOKEN is not.
  //  Both must be provided to connect to a remote Hermes backend."
  ```

  两个都没给时，它走"自己拉起后端"的本地路径，于是进入配置向导。

- **我们已经有的一半**：
  - 后端侧 `web_server.py:_resolve_session_token()`：`HERMES_DASHBOARD_SESSION_TOKEN` 优先，否则随机生成；
  - 我们拉起后端时已注入该变量：`core/backend/LocalBackendPlanner.kt:140`；
  - 桌面端 REST 已带 `X-Hermes-Session-Token`：`core/transport/RestClient.kt:181`。

  **缺的只是"把同一个 token 交给官方桌面"这一步。**

- **修法**：
  1. `BackendProvider` 暴露 `val sessionToken: String?`
     （LOCAL 返回 `LocalBackendProvider` 生成的那个 `randomHex(16)`，REMOTE 返回 `resolveToken(config)` 的结果）；
     注意 `DesktopContainer.buildBackend()` 里 token 目前是局部变量，需要存到 provider 上才拿得到。
  2. `OfficialDesktopLauncherImpl` 增加 `baseUrl` + `sessionToken` 两个参数
     （`baseUrl` 取 `config.backend.remote.baseUrl`，LOCAL 模式下即本机 `http://127.0.0.1:9119`）。
  3. `officialDesktopEnv(dataRoot, baseUrl, token)` 增加：

     ```kotlin
     "HERMES_DESKTOP_REMOTE_URL" to baseUrl,
     "HERMES_DESKTOP_REMOTE_TOKEN" to token,
     ```
  4. token 为空时**不设这两个变量**（宁可进入向导，也不要给空 token 让它抛异常）。

- **为什么不会被它自己的 profile 配置抢走**：`resolveDesktopRemoteRoute` 的优先级是
  `sshOverride` > `profileRemoteOverride` > `env`。前两者来自它自己的
  `desktop-connections` 配置，而我们的 `HERMES_DESKTOP_USER_DATA_DIR` 是**隔离目录**（空），所以 env 生效。

- **保留 `HERMES_HOME` 隔离**：remote 模式下它不再自己起后端，但隔离仍能阻止它读写用户的真实 hermes home。

- **验收口径**：
  - 启动后**不出现**配置后端向导，直接进入会话列表；
  - `data/official-desktop/official-desktop.log` 里没有 "another Hermes Desktop instance holds the single-instance lock"；
  - 官方桌面里看到的会话与我们客户端一致（同一个后端）；
  - 后端未启动时（REMOTE 但连不上）给出明确错误，而不是静默进向导。

- **注意**：本项属 debug-only 功能（ADR-045，约定 v1.0.0 随调试入口一起移除）。
  修它只是为了当前对照测试能用，不做长期投入。

### #9 浏览器可见窗口（headed）

- **优先级**：P1（用户明确需求）
- **涉及层**：`composeApp`（设置页 + 环境变量注入）；**不改后端**

#### 怎么实现（后端已有能力，不需要新写浏览器）

`agent-browser` 支持 `--headed`（`AGENT_BROWSER_HEADED` 环境变量同效），后端
`tools/browser_tool_cloud.py:_is_headed_mode()` 的判定是：

```python
headed = _browser_cfg("headed", False, ...)          # 后端 config 的 browser.headed
return headed or os.environ.get("AGENT_BROWSER_HEADED", "").strip().lower() in ("true","1","yes")
```

**已实测**：用 `AGENT_BROWSER_HEADED=1` + `AGENT_BROWSER_EXECUTABLE_PATH=<浏览器>` 跑
`agent-browser open <url>` → 真实可见窗口出现，`open` 返回页面标题，`close` 正常收尾。

#### 便携性已确认（不需要 `agent-browser install`）

| 事实 | 位置 |
|---|---|
| PM 包管理器把 Chromium 装在 payload 内 | `hermes/tools/chromium-1208/chrome-win64/chrome.exe`，**393.4 MB / 310 文件**，来自 `pm/lock.json` 的 `packages.chromium`（`cdn.playwright.dev/builds/cft/145.0.7632.6/win64/chrome-win64.zip`） |
| 后端每次调 agent-browser 都显式指定浏览器 | `tools/browser_tool_session.py:186-190` → `env["AGENT_BROWSER_EXECUTABLE_PATH"] = chromium_executable()` |
| `chromium_executable()` 的优先级 | `AGENT_BROWSER_EXECUTABLE_PATH` > `pm.installed_package("chromium").binary` |
| `agent-browser install` 的兜底位置 | `~/.agent-browser/browsers`（**不便携**，hermes 正常路径不走它；`doctor` 报"找不到 Chrome"是脱离 hermes 环境单独运行所致） |

所以**不做浏览器路径探测**——后端已处理。桌面包体积**不受影响**（Chromium 属 payload）。

#### 落地方式

| 步骤 | 做法 |
|---|---|
| 1 | 设置 → 桌面 → **浏览器**（新增 `SettingsPage.Browser`）：开关「显示浏览器窗口」 |
| 2 | 开关值存 `config.json`（客户端配置，重启生效），拉起后端子进程时由 `LocalBackendPlanner` 注入 `AGENT_BROWSER_HEADED=1` |
| 3 | 界面提示「需重启后端生效」+ 一键重启（复用现有 `BackendProcess` 能力），不让用户以为开关失效 |
| 4 | 可选：「打开测试页」按钮 → 让 agent 打开一个 URL，用于确认窗口真的出现 |

**为什么用环境变量而不是改后端 `config.yaml`**：`PUT /api/config/raw` 是**整篇 YAML 替换**
（"Full-document replacement … never merge omitted sections back from disk"，见 `web_routers/analytics.py:53`），
一旦我们写坏就毁掉用户整份后端配置。环境变量是进程级的，出问题只影响本次启动。

#### 不做（本版）

| 项 | 理由 |
|---|---|
| 应用内**内嵌**浏览器（WebView2 + CDP） | Compose 无原生 WebView，需 JNA 封装 WebView2 COM（400–600 行）+ 未验证 CDP 端口能否被外部接管。**单独立项 spike**，先只验 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9333` 能否被 `agent-browser --cdp 9333` 接管 |
| 重加 JCEF 做内嵌 | v0.4.1 刚删（`cef/` 310 MB），且适配层与 `jcef-api` 契约不符 |
| 用 Win32 `SetParent` 把 Chrome 窗口塞进应用窗口 | Chrome 多进程窗口重绘 / DPI / resize 同步都不稳，维护成本远高于收益 |

### #8 外部编辑器唤起（文件查看/编辑）

- **优先级**：P1（用户明确需求）
- **涉及层**：`composeApp`（设置页 + 工具卡片 + 平台启动器）；**不改后端**
- **符合既定方向**：ADR-005「不做内置编辑器，跳转外部 VSCode / IDEA」——本项是它的落地

#### 目标

AI 修改/创建文件后，工具卡片旁出现按钮，可用**用户配置的外部编辑器**打开
文件 / 所在文件夹 / 项目；多个编辑器配置时可选。为不同打开类型配置不同命令行参数，
某类型关闭时回退为「单文件打开」。

#### 数据模型（落 `config/options.json`，热生效）

```kotlin
@Serializable
data class EditorsOptions(
    @SerialName("default_id") val defaultId: String? = null,
    val profiles: List<EditorProfile> = emptyList(),
)

@Serializable
data class EditorProfile(
    val id: String,                                     // 稳定 id，如 "vscode"
    val name: String,                                   // 显示名
    @SerialName("exe_path") val exePath: String,
    @SerialName("open_file") val openFile: EditorAction = EditorAction(),
    @SerialName("open_file_at_line") val openFileAtLine: EditorAction = EditorAction(),
    @SerialName("open_folder") val openFolder: EditorAction = EditorAction(),
    @SerialName("open_project") val openProject: EditorAction = EditorAction(),
    @SerialName("open_diff") val openDiff: EditorAction = EditorAction(),
)

@Serializable
data class EditorAction(
    val enabled: Boolean = true,
    /** 参数模板；空串 = 用内置默认。占位符见下表。 */
    val args: String = "",
)
```

**为什么用五个具名字段而不是 `Map<动作, 配置>`**：kotlinx-serialization 对 enum 作 map key
需要额外配置；具名字段还能在加新动作时保持旧 `options.json` 兼容（缺字段走默认）。

#### 五种动作与占位符

| 动作 | 占位符 | VSCode 默认模板 |
|---|---|---|
| `open_file` | `{path}` | `{path}` |
| `open_file_at_line` | `{path}` `{line}` | `--goto {path}:{line}` |
| `open_folder` | `{dir}` | `{dir}` |
| `open_project` | `{dir}`（会话 cwd） | `{dir}` |
| `open_diff` | `{file1}` `{file2}` | `--diff {file1} {file2}` |

**解析规则**（纯函数，可单测）：
1. 模板按空白切分成参数；支持双引号包裹一段（`--goto "{path}:{line}"`）。
2. 替换占位符。
3. **若某参数引用了取不到值的占位符，整个参数被丢弃**
   —— 这样 `open_file` 默认模板可写成 `--goto {path}:{line} {path}`：有行号时两者都生效
   （VSCode 取最后一个匹配），无行号时第一个参数整体丢弃。
4. **占位符值以 `-` 开头时该参数被丢弃**（防止模型把 `path` 写成 `--dangerous-flag` 造成参数注入）。

#### 回退规则

- `open_folder` 关闭 → 点「打开所在文件夹」时改用 `open_file`（打开文件本身）。
- `open_file` 与 `open_file_at_line` 都关闭 → 「打开文件」菜单项**不显示**。
- 某编辑器的全部动作都关闭 → 该配置在菜单里不出现。

#### 路径来源（纯函数，可单测）

从工具名 + `arguments` JSON 提取，覆盖后端实际工具名（`tools/file_tools.py`）：

| 工具 | 提取 |
|---|---|
| `write_file` / `read_file` | `path` |
| `patch`（`mode=replace`） | `path` |
| `patch`（`mode=patch`，V4A） | `patch` 文本里 `*** Update File:` / `*** Add File:` / `*** Delete File:` 后面的路径（可多文件） |

归一化：
- `~/x` → 用户主目录；
- 相对路径 → 拼**会话 cwd**（`ChatViewModel.cwds` 已有，`session.resume` 响应的 `cwd` 字段）；
- 既无 cwd 又是相对路径 → 不显示按钮（不猜）；
- 解析失败 / 非文件类工具 → 不显示按钮。

#### 启动（desktop）

```kotlin
ProcessBuilder(listOf(exePath) + args)   // 不经过 shell，杜绝命令注入
```
- **不 `waitFor()`、不重定向输出**：编辑器是独立进程，等它会卡住 UI 线程。
- `.cmd` / `.bat`（如 VSCode 的 `bin/code.cmd`）必须经 `cmd.exe /c` 包装，JVM 无法直接执行批处理。
  预置项优先填 `Code.exe`。
- exe 不存在 / 启动抛异常 → 提示「未找到编辑器 X 的可执行文件」，不静默失败。

#### UI 落点

1. **设置 → 桌面 → 外部编辑器**（`SettingsPage.Editors`）
   - 配置列表（名称 / exe / 已启用动作数 / 编辑 / 删除 / 设为默认）
   - 编辑对话框：名称、exe 路径 + 「浏览…」（AWT `FileDialog`）、五个动作（开关 + 模板输入 + 「恢复默认」）、「测试打开」
2. **工具卡片**（`ToolCallCard`）：`write_file` / `patch` / `read_file` 且提取到路径时，
   标题行右侧出现「打开」按钮。
   - 单一配置 → 直接按 `defaultId`（或唯一配置）执行 `open_file`。
   - 多配置 → `DropdownMenu` 列出 `编辑器 · 动作`（如 `VS Code · 打开文件`、`IntelliJ · 打开所在文件夹`）。
3. **会话级入口**（可选）：会话菜单「在编辑器中打开项目」→ `open_project`。

| 风险 | 对策 |
|---|---|
| 参数注入（模型控制的路径被当开关） | 值以 `-` 开头即丢弃该参数；**永远不经过 shell** |
| 路径带空格/中文 | `ProcessBuilder` 用参数列表，天然不需要引号；模板解析要正确处理引号 |
| VSCode 需要「已在运行」才会即时响应 | `Code.exe` 会转发给已有实例，无需特殊处理；实测确认 |
| 设置页改配置后要立刻生效 | 走 `AppOptions` 热生效链路（`AppOptionsHolder.state`） |
| 工具卡片多一个按钮会挤压布局 | 只在有路径时渲染；用 icon button + tooltip 而非文字按钮 |
| 会话 cwd 未就绪（刚打开会话） | 隐藏「打开项目」；文件绝对路径仍可直接打开 |
