### #2 内置编辑器：Aardink 接入 spike

- **优先级**：P2
- **涉及层**：UI（编辑器）/ 产品范围（ADR-005）
- **前置**：ADR-005「不做文件树 / 内置编辑器」仍是当前非目标 —— **先改产品决策，再谈实现**。

**候选排序**：`Aardink` > `SweetEditor` > `JCEF + Monaco` > `BossEditor`（后者被 IME 硬伤排除：只认 `event.utf16CodePoint`，微软拼音打不出字）。

**推荐接入**：Maven 依赖 `com.aardarch:aardink:0.8.0`（Apache-2.0，Compose 1.12.2 / Kotlin 2.4.21 与本仓库逐项相同，纯 Kotlin 无 native）。
**不 fork**：它有 `editor/api/editor.klib.api` 做 API 锁定，主题/命令/语言接入都走公开扩展点。
**出现上游阻塞才 fork**：fork 时只留 `:editor` + `:languages`，移除 android / wasmJs target（否则要 Android SDK 与 Node 下载），`.gitmodules` 加 `ignore = untracked`。

**spike 判据**：

1. 在 1.12.2 / 2.4.21 工程里能编译运行；
2. 微软拼音端到端（候选窗跟随光标、上屏、撤销、保存重开）；
3. 150–200% DPI 下光标与候选窗位置；
4. 提权进程里正常工作；
5. 体积增量（预计 < 2 MB）；
6. 与 `LazyColumn` 的滚动关系 —— 编辑器自身是滚动容器，必须放独立 pane，不能塞进消息流。

**风险**：2★、0.8.0（2026-11-01）、contributors 4（主力 1 人）—— 采用前观察 1–2 个版本。

### #13 残留 gateway 占着 host，新后端无法启动（exit 75）

- **优先级**：P1（本地模式完全不可用：REST / RPC 都连不上）
- **涉及层**：`core/backend/GatewayEnsure.kt` / `GatewayAttachBackendProvider.kt` / `core/backend/WindowsJobObject.kt`；
  后端 `gateway.lock` 的生命周期
- **记录日期**：2026-11-10（用户报「本地的 hermes 后端启动不了了」）

**现象**：客户端能启动、窗口正常，但后端 attach 失败，界面里所有数据都需要后端：
`desktop.log` 报

```
10:41:12.320 ERROR gateway attach: 无法访问后端运行时 — reason=runtime_exited —
  the gateway exited with status 75 before it could serve:
  ⏳ A gateway already owns this host and has not published its served set yet.
     PID 21608 (launched by profile 'default'; serves: not published yet (its control socket has not answered))
     ... Take the host over (only from the home that launched it):  hermes gateway run --replace
```

**根因**（已确认）：

1. 上一轮 gateway（`data/agent/gateway.lock` 里 `pid=21608`，2026-11-09 17:53 启动）在父进程
   （昨晚被结束的客户端）死后，今天 10:40:15 才收到关闭信号并完成 teardown —— `data/agent/logs/gateway.log`
   有完整的 `Shutdown phase … Gateway stopped (total teardown 5.50s)`，**但进程没退出**，仍绑着
   57927/57928 等端口；
2. `data/agent/logs/gateway-stdio.log` 里有
   `asyncio.exceptions.CancelledError: Task cancelled, timeout graceful shutdown exceeded`
   —— 即优雅关闭超时被取消，进程停在半死状态；
3. 新客户端 `gateway ensure` 读到 lock 里的 PID 仍存活、但 control socket 不响应，判定
   「host 可能被占用、启动第二个会双重绑定」，于是**主动不启动**并以 75 退出；
4. 客户端只把这条错误展示给用户，**没有接管手段**（后端明确提供了 `gateway run --replace`）。

**本次处置（10:43）**：`Stop-Process -Id 21608 -Force` → 重启客户端 → ensure 发现旧 PID 已死、
正常拉起新 gateway（PID 36284，端口 61158），日志 `gateway attached: http://127.0.0.1:61158`，
随后 `sessions loaded: profile=ops count=25` 正常。

**注意**：`mode=local` 下 REST 走 **ensure 出来的 `apiOrigin`**（随机端口，如 61158），
不是配置里那个 `127.0.0.1:9119`；日志开头打印的 9119 只是配置值，探测它不通**不代表**后端起不来。

**待修（v0.5.6 候选）**：

1. `GatewayEnsure` 收到 `runtime_exited` + `exit 75` + 「未发布 served set / control socket 未应答」时，
   自动走一次 `hermes gateway run --replace`（后端文档给的就是这条接管路径），成功则继续 attach；
2. 只有替换也失败才提示用户，并在 UI 给「一键接管后端」入口（而不是只显示一段英文说明）；
3. 顺带收敛「强杀客户端 → 后端子进程留孤儿」：`WindowsJobObject` 的注释已承认这是唯一会留孤儿的情形，
   但这次留下的是**卡死的半死进程**，比"仍在跑"更糟 —— 需要 kill-on-job-close 或启动时清理僵尸。

**验证口径**：

- 构造 stale lock（保留 `gateway.lock` 指向一个已 stopped 但未退出的 gateway 进程）→ 启动客户端 →
  日志出现接管记录、`gateway attached` 成功、`sessions loaded` 有数据，无需用户手工杀进程；
- 后台真死（PID 不存在）时行为不变（ensure 直接启动新 gateway）。

### #14 后端端口漂移 + 换端口后不回连 → 发消息静默无反应

- **优先级**：P1（主流程受损，且**没有任何界面反馈**，用户只能强杀重启）
- **涉及层**：`core/transport/GatewayClient.kt`（重连目标解析）/ `core/backend/LocalBackendProvider.kt` /
  `feature/chat/ChatViewModel.kt`（发送失败提示）
- **记录日期**：2026-11-10（用户报：本轮强制重启前「无论怎么发消息都没有反应」，重启后才发现后端起不来）

#### 时间线（全部来自日志，可复核）

| 时间 | 事实 | 出处 |
|---|---|---|
| 00:03–00:32 | 客户端多次 `gateway attached: http://127.0.0.1:65099`，短间隔重连 5 次 | `data/logs/desktop.log` |
| 10:10:55 | `heartbeat deadline exceeded (387760ms); dropping socket` → 立即重连 `49379` | `data/logs/gateway.log:321` |
| 10:20:29–10:20:36 | 连续 4 次 `gateway session ended: backend unreachable`（`Connection refused`） | 同上 `:324-370` |
| 10:20:33 | 客户端**自己拉起了一个新后端**：`Skipping web UI build` → `HERMES_DASHBOARD_READY port=64700` | 同上 `:369-385` |

```
10:13:47 → 10:16:33  time=166.1s api_calls=8  response=66 chars
10:16:45 → 10:19:25  time=160.4s api_calls=1  response=67 chars

10:29:45 → 10:29:53  time=7.6s   api_calls=1  response=65 chars
10:31:42 → 10:36:32  time=289.9s api_calls=17 response=196 chars
```

同时段 `errors.log` 里的上游故障（**不是我们造成的，但直接吃掉了响应**）：

```
agent.conversation_loop: API call failed ... provider=custom base_url=https://new-api.svc.nb.self/v1
  model=deepseek-v4-pro summary=peer closed connection without sending complete message body
  (incomplete chunked read)  →  Retrying API call in 2.5s (attempt 1/3)

  resending payload unchanged (serialized_input_bytes=468228)
codex_responses_adapter: Dropping reasoning item minted by other:.../deepseek-v4-pro
  while calling other:.../cc:deepseek-flash — ... This happens when a session switches model mid-conversation.
Auxiliary title generation failed: HTTP 400 ... does not have a valid CodingPlan subscription
```

#### 判定：两个独立问题叠在一起

**A. 后端端口漂移 + 客户端不回连（我们这边的缺陷）**

`gateway.log` 今天出现 **5 个不同端口**（`49379` → `64700` → `65099` → `64173` → `61158`）。
`65099` 是 00:03–00:32 就一直用的端口，10:32 又出现；`64700` 是 10:20 客户端自己拉起的；
`64173` 是 10:37 的。也就是说：**后端被反复重启，每次端口都变，而客户端只在收到
`Connection refused` 时才重连到“当时的目标”；一旦目标端口背后换了实例，客户端并不知道。**

关键盲点：`desktop.log` 里 **`re-resuming` 一次都没有**（全文件 0 次）。
`ChatViewModel:161` 那行 `gateway reconnected; re-resuming …` 从未打印，说明
`wasConnected` 的复位路径没有走到我们要的分支，或者 `Connected` 状态根本没再发过一次
（`openSession` 只在成功握手时置 `Connected`，`runLoop` 每轮都 `Connecting`）。
后果是：**transport 认为“连着”，会话订阅其实已经作废** —— 后端把事件推给旧订阅，
客户端收不到；用户发消息 → `prompt.submit` 发出去 → ack 可能拿到（走的是新连接），
但**事件流不回来**，界面上就是“转圈/没反应”，且**没有任何错误提示**。

**B. 上游模型服务不可用（外部原因，放大了症状）**

`10:19:56` 那一轮 `time=589.3s response=0 chars`：后端跑了 9 分 49 秒、23 次 API 调用，
**返回正文 0 字符**。原因在 `errors.log`：
- `peer closed connection without sending complete message body (incomplete chunked read)`
  → `new-api.svc.nb.self` 上游断流；
- `volcengine-coding-plan` 的 CodingPlan 订阅 400，触发 `Model fallback: deepseek-v4.1-flash → deepseek-flash`；
- 切模型后 `Dropping reasoning item minted by other:.../deepseek-v4-pro`（加密推理项跨模型作废）。

所以用户看到的“怎么发都没反应”，至少有一部分是**后端在等上游、最后交回 0 字符**。

#### 待修（按性价比排序）

1. **发送链路必须有可见反馈**（最要紧）：`prompt.submit` 的 ack 超时是 1800s（硬约束 3），
   但这不代表 3 分钟没事件就该静默。现有看门狗（`TURN_SILENCE_TIMEOUT_MS = 90s`）
   只在**有响应**时触发对账；需要在「已发出 + 该会话 90s 内无任何事件」时给出
   「后端长时间无输出，可能连接已失效」的横幅 + 「重连并重试」按钮。
2. **`Connected` 之后必须验证会话订阅**：`wasConnected` 的复位只覆盖
   `Idle/Closed/Reconnecting/Disconnected`，而 `runLoop` 每轮先置 `Connecting`、成功后置
   `Connected` —— 理论上会触发 re-resume，但今天 0 次记录。需要加一条断言日志
   （`Connected` 时打 `reconnected marker`），并补一条单测：`Connecting → Connected`
   必须发起 re-resume（当前行为无测试覆盖）。
3. **重连不要盲目回到旧 URL**：`targetProvider()` 每轮重新取目标（`gateway ensure` 的
   `apiOrigin`），但日志显示客户端会连回 `65099` 这种旧端口。需要确认 `runLoop` 里
   `openSession(targetProvider())` 在每次 attempt 都重新 ensure；失败次数 > N 时强制重新
   `ensure` 并接受端口变化。
4. **后端 0 字符响应要显式提示**：`response=0 chars` 的轮次在界面上应显示
   「本轮未返回内容（上游中断）」，而不是让用户以为界面卡住。
5. 顺带记录上游问题（不改客户端）：`new-api.svc.nb.self` 的 `deepseek-v4-pro`
   chunked 断流、`volcengine-coding-plan` 订阅 400 —— 这是模型网关侧，属于环境问题。

#### 验证口径

- 构造端口漂移（重启后端让端口变）→ 客户端应在 90s 内通过看门狗发现并重新 attach，
  日志出现 `gateway reconnected; re-resuming`；
- 断开后端但保持 socket → 90s 内出现「后端长时间无输出」横幅，点「重连并重试」可恢复；
- 后端返回 0 字符（可用 mock）→ 界面显示「本轮未返回内容」而非静默；
- 复跑今天 10:19 那一轮耗时场景：界面必须持续有状态（转圈 + 耗时），不能无反应。

### #15 后端管理入口（手动启停 + 自动跟随新端口）
- **优先级**：P1
- **涉及层**：UI（设置页 / 状态栏）/ 平台集成（`GatewayAttachBackendProvider`）/ 传输层（`GatewayClient` 目标解析）
- **提出日期**：2026-11-10（用户提出；与 #13 / #14 同源）

**需求**：现在后端一旦出问题，用户能做的只有「重启整个客户端」甚至「手工杀进程」。需要一个
**后端管理的地方**：

1. **手动启停**：启动 / 停止 / 重启后端，不用退出客户端；
2. **状态可见**：当前是运行中 / 已停止 / 启动失败，以及失败原因（`ensure` 的 `state` / `reason_code`）；
3. **端口显示 + 自动跟随新端口**：显示当前 `api_origin`；后端重启换了端口后客户端
   **自动重连到新端口**，不需要用户干预；
4. **服务形态之后退**：不需要装 SCM 服务、不需要管理员（见文末「已否决」）。

**现状（缺什么）**：

| 能力 | 现状 |
|---|---|
| 启停 | `BackendProvider` 有 `start()` / `stop()`，但 **UI 上没有入口**（只有错误横幅，没有按钮） |
| 状态 | `BackendBootState`（Idle / Starting / Ready / Failed）已经有了，状态栏也在显示，但**没有集中管理页** |
| 端口 | `gateway attached: <api_origin>` 只写日志；UI 不显示；后端换端口后客户端**不会**主动重连（= #14） |

**设计要点**：

- 复用现有 `BackendProvider`（`GatewayAttachBackendProvider` 已实现 `start` / `stop` / `state`），
  不新造抽象；
- 重启 = `stop()` → `start()`；`stopDetached()` 已限本 home（`gateway stop -y`，绝不 `--all`）；
- 端口跟随的关键是**重启后让 `GatewayClient` 重新取目标**：`targetProvider = { backend.currentTarget() }`
  （[DesktopContainer.kt:105](S:/mine/project/hermes-compose/composeApp/src/desktopMain/kotlin/dev/shinglem/hermes/di/DesktopContainer.kt:105)

  `ConnectionState` 推回 `Disconnected/Connecting` 就能自然重连 —— **不需要额外记录端口**；
- 与 #14 合并实现：重连逻辑 + 管理页是同一件事的两面（一个自动、一个手动）。

**放在哪**：

| 位置 | 内容 |
|---|---|
| 设置 → 桌面 → 后端（新页）或状态栏后端项点开 | 状态（含 `reason_code` / 端口 / instance id）、启动 / 停止 / 重启、日志尾（`BackendLogBuffer` 已有）、「复制诊断信息」 |
| 状态栏 | 保持现有「本地后端：就绪 (:port)」，点开进管理页 |

**验收口径**：

- 后端运行中点「重启」→ 日志出现 stop + ensure + attach，状态栏端口更新，**会话不丢**（重连后自动 re-resume，#14）；
- 后端被外部杀掉 → 管理页状态变「已停止」，点「启动」能起来；
- 后端在别处重启换了端口 → 客户端 90s 内自动连上新端口，无需点击；
- 端口号在管理页与状态栏都能看到，且与实际 `api_origin` 一致；
- **全程不需要管理员权限**。

### #16 进历史会话时模型 pill 显示「选择模型」（实际有模型在生效）
- **优先级**：P1（功能本身没坏，但**用户无法知道自己在用哪个模型**，也容易误以为配置丢了）
- **涉及层**：UI（`composer/ModelPill.kt`）/ 状态层（`feature/chat/ChatViewModel.kt` 的
  `seedModelInfo` / `publish` / `resumeInBackground`）
- **记录日期**：2026-11-10（用户报：进历史对话，模型处显示「选择模型」，但可以正常对话，
  不清楚用的是默认模型还是别的）

**现象**：打开一条历史会话，输入框上方 pill 显示「选择模型」（`model_pill_select`），
但发消息能正常得到回复 —— 说明后端确实有模型在跑，只是界面没显示出来。

**已定位（读代码得出，三处都会导致这个表现）**：

1. **`publish()` 会清空 model**（[ChatViewModel.kt:1917](S:/mine/project/hermes-compose/composeApp/src/commonMain/kotlin/dev/shinglem/hermes/feature/chat/ChatViewModel.kt:1917)）：

   ```kotlin
   model = if (sameSession) previous.model else null,
   provider = if (sameSession) previous.provider else null,
   ```

   打开**另一条**历史会话时 `sameSession == false` → model 被置 null。

2. **`RELOAD` 路径里两个协程在赛跑**（`:229` 与 `:236`）：

   ```kotlin
   viewModelScope.launch { seedModelInfo(profile) }   // ① 拉 REST /api/model/info
   loadJob = viewModelScope.launch {
       _state.value = ChatState(key = key, load = Loadable.Loading)   // ② 整个状态替换
       …
       publish(key, loaded)      // 这里又把 model 置 null
       resumeInBackground(key)   // ③ 真正带模型的是 session.resume
   }
   ```

   若 ① 在 ② 之前完成写入了 model，② 会把它整个冲掉；`publish()` 再置 null。
   ③ 的 `resumeInBackground` 里才写会话级真值（`:1238` `model = resumed.model ?: current.model`），
   但那条是**异步**的，且 `resumeInBackground` 开头有 `if (runtimeIds[key] != null) return`
   —— 该会话的 runtime 已在本进程存活时**直接返回，不会再刷新 model**。

3. **`USE_CACHE` / `RESTORE_SNAPSHOT` 路径不补**（`:204-221`）：这两条分支走
   `publish()`（同样的 null 清空）或恢复快照，**都不会调 `seedModelInfo`**。
   从别的会话切回来时如果 `sameSession == false`（中间切过会话，`_state.key` 已变），
   model 就没了，且没有任何补偿路径。

**所以"到底用的哪个模型"当前是查不到的** —— 三种可能并存：会话级 override（只有
`session.resume` 的 `info.model` 知道）、profile 默认（`/api/model/info`）、后端自己的 fallback
（今天日志里就有 `Model fallback: deepseek-v4.1-flash → deepseek-flash`）。

**修复方向**：

1. `publish()` 不要无条件清 model：只要 `key` 与 `previous.key` 相同就保留；
   切到新会话时**不要清**，改为「保留旧值 + 标记 `modelStale = true`」，等 resume/info 覆盖 ——
   显示上一次的模型也远好过显示「选择模型」。
2. `seedModelInfo` 的写入要能抵抗状态替换：改成 `_state.update { it.copy(...) }` 无条件写入
   （当前已是），但要放在 `publish()` **之后**触发，或直接用 `seedModelInfo` 的结果覆盖；
   更稳的做法是按 key 存储（`models[key]`），与 `revisions`/`generations` 同构。
3. `resumeInBackground` 的早退（`runtimeIds[key] != null`）要拆开：runtime 可复用，
   但**模型仍应刷新一次**（或至少标记不需要刷新）。
4. `USE_CACHE` / `RESTORE_SNAPSHOT` 也补一次 `seedModelInfo`（幂等，已有值就跳过）。
5. **pointer 的实质性修正**：pill 显示「选择模型」时，语义应是「还没读到模型」而不是
   「没有模型可用」。当前用户无法区分这两者 —— 建议在 pill 上加 tooltip 或换成
   「模型未知（点击查看）」并在菜单里标出当前生效项。

**验证口径**：

- 冷启动 → 打开历史会话：pill 在 2s 内显示具体模型名（不是「选择模型」）；
- A 会话 → B 会话 → 切回 A：pill 始终有模型名，且与该会话后端实际一致（用
  `session.resume` 日志的 `info.model` 对照）；
- 后端发生 model fallback 后（`⚠️ Model fallback` 出现在 `errors.log`），pill 应跟随到实际使用的模型；
- 未配置任何 provider 时，pill 才显示「选择模型」/「没有可用 provider」。

### 已否决：后端改用 Windows 服务（SCM）托管（2026-11-10）

> 记录原因见 `AGENTS.md` §「不做清单和做清单同等重要」—— 不写下来，下一个 agent 会重新提议。

**原提案**：写一个 daemon 注册成 Windows 服务托管后端；新装时索要 UAC 创建服务；桌面端做服务管理；
后端由 SCM 自启、前端用普通自启；顺带让通知不再依赖开始菜单快捷方式。

**否决理由**（逐条核实后）：

| 提案想达到的目的 | 结论 |
|---|---|
| 后端独立于前端 | **已达成**，不需要服务：`gateway` 路线的 daemon 用 `CREATE_BREAKAWAY_FROM_JOB` 脱离我们的 Job Object |
| 登录自启不弹 UAC | **已达成**：计划任务 `RunLevel=HighestAvailable`（本机任务 XML 实测） |
| 日常不提权 | 真需求，但**不需要服务**：`app.elevate=never` + `HKCU\...\Run` 自启即可，更干净 |
| 开机即启动（不登录） | SCM 唯一独有的能力，但**对我们无价值** —— 服务在 Session 0，没有交互式桌面 |

**致命冲突：Session 0 无交互桌面。** 后端要跑在**用户的交互会话**里才能：

- `computer_use` 模拟键鼠操作真实窗口（上游 `hermes_cli/tools_config_cua.py:200` 自己写着
  「needed when driving Windows over SSH (**Session 0 has no interactive desktop**)」）；
- `browser.headed` 弹出可见浏览器窗口（本机 `config_custom.json` 就是 `headed: true`）。

也就是说「登录后才启动」恰好是**需要的**，而不是待消除的限制。
[`07-提权与自启动.md`](详细设计/工程与代码/07-提权与自启动.md) §2.1 早已论证并否掉过这条路。

**另外两条不成立的理由**：

- 上游**没有** Windows SCM 服务安装入口：`hermes gateway install` 在 Windows 上装的是
  **计划任务**（`hermes_cli/gateway.py:5542`）。`WindowsGatewayService` 与
  `hermes_owns_windows_service` 只用于**检测**归属（更新器判定「这是不是我自己的服务」，
  `gateway_windows.py:136`），`gateway-service/` 目录里放的是 `.vbs`/`.cmd` 启动器，不是 SCM 服务。
  做服务化等于与上游分叉。
- #13 / #14 的根因都不在后端形态：#13 是上游优雅关闭超时被取消后半死；#14 是客户端换端口后
  没重建会话订阅。服务化修不了这两条，还会把 `gateway.lock` 语义与 SCM 进程身份叠在一起，更难排障。

**替代方案**（已采纳方向，见 #15）：

1. `app.elevate` 默认 `never`，客户端全程普通权限；
2. `app.autostart` 增加 `run` 选项（`HKCU\...\Run`，无需 UAC、零系统对象），`task` 保留给确实需要时刻提权的用户；
3. 需要操作管理员窗口时，按需 `runas` 拉起**一次性**提权动作，主进程不动；
4. 后端管理与端口跟随按 #15 做。

**关于通知不绑快捷方式**：与后端形态无关，是 Windows Shell 层硬限制 —— toast 归属只认开始菜单
`.lnk`（[`12-通知窗.md`](详细设计/工程与代码/12-通知窗.md) §1 的四组实测已排除桌面 `.lnk`、
注册表、`App Paths`、COM activator 等全部替代）。真要摆脱快捷方式，只能**放弃原生 toast、
只用自绘通知窗** —— 这是产品决策，随时可单独重开。
