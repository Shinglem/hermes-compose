## 条目

### #1 原生集成能否改用 Nucleus 生态（托盘 / WebView / 打包）

- **类型**：改进（技术调研，非缺陷）
- **优先级**：P2
- **涉及层**：平台集成（托盘 / 通知 / 单实例 / 自启 / 提权）、打包链
- **调研日期**：2026-11-04，基线 v0.4.0（commit `f04da8b`）

**结论**：
1. **托盘可换**（L1.5 试点，独立依赖、不拉 Tao）。
2. **WebView 有第二个用途**：不是替换 Markdown 渲染，而是**给 hermes 的浏览器操作能力做界面**（整窗口浏览器面板）。这条路可行，但前提是整个窗口壳迁到 Nucleus Tao，属 L1.5 大改；消息内嵌 HTML 仍走 JCEF OSR，两者互补。
3. **单实例 / 自启 / 提权不换**：Nucleus 的计划任务明确用 `TASK_RUNLEVEL_LUA`（普通权限），做不到我们"最高权限 + 无 UAC"；提权重启无对应模块；单实例能互斥但语义不同（见下）。
4. **打包不换**：Nucleus packaging 解决"生成安装包"，我们自研的是"纯外壳 + payload 分离 + toolchain 版本化解耦 + 计划任务安装"，不在同一层。

#### 托盘为什么可换

- 它绕开了我们自绘的**同一个理由**：`UnicodeTrayDemo` 明确验证"UTF-8 → UTF-16"（法语 / 中文 + 特殊标点），Windows 走自家 native 桥（`WindowsNativeBridge.nativeCreateTray(iconPath, tooltip)`），不是 AWT `PopupMenu` 的 ANSI 转换路径 —— 即 CMP-1936 的成因。
- 白送的能力：HDPI 修复、`primaryAction`（左键）、勾选 / 子菜单 / 分隔线、托盘位置探测、菜单随 Compose 重组刷新。
- 依赖面小：只引 `composenativetray`，**不**拉 `decorated-window-tao`（2.1.0 按 issue #418 拆包）；要求 CMP 1.12.0（我们一致）、JDK 17+（我们 Temurin 27）、Gradle 9.0+。

#### WebView 接入 hermes 浏览器能力：可行，但要先迁 Tao

**hermes 侧能力（已核实）**：
- `tools/browser_tool_cdp.py:14 _resolve_cdp_override(cdp_url)`：接受 `http://host:port`、`ws://…`、完整 `/devtools/browser/…`；给 HTTP 根时去 `/json/version` 取 `webSocketDebuggerUrl`。
- 入口两处：`browser.cdp_url`（config.yaml）与 `/browser connect`（会话内，按 profile 隔离 —— 同文件 `_live_overrides`）。
- 结论：**不改后端**，把 `browser.cdp_url` 指向我们的 WebView2，它就能操作并复用页面。
- payload 另有 browser_use / browserbase（云 CDP）、firecrawl（抓取）、agent-browser（自带 Chromium）。

**WebView2 侧（已核实）**：
- `composewebview` 桌面 = Tao `NativeView` + WebView2 `CreateCoreWebView2CompositionController`（DirectComposition 合成）→ 适合**整窗口**，不适合嵌进 LazyColumn（无 OSR）。
- 库已暴露 `enableDevtools` / `openDevTools()` / `closeDevTools()`；native 走 `CreateCoreWebView2EnvironmentWithOptions`。
- 未暴露 `AdditionalBrowserArguments`；但 WebView2 支持进程级 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS`（微软文档用它传 Chromium 开关），`--remote-debugging-port=<port>` 可试 —— **必须实测**。
- 体积与性能现状：`cef/` 是随包 **310.4 MB** 的 Chromium 135；系统 WebView2 Runtime 是 `156.0.4314.58`（随 Edge 更新）。分发体积与冷启动 WebView2 占优；代价是版本随系统漂移。

**接入形态（spike 目标）**：

```text
nucleusApplication(backend = Tao, enableSingleInstance = false)   // 保留自研单实例
  └ 窗口内 WebView2 面板
启动前设 WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=<随机端口>
browser.cdp_url = http://127.0.0.1:<端口>                          // 用户配置，不改后端
```

**必须先验的四点**：

1. WebView2 是否真的监听该端口并提供 `/json/version`（不支持就退化成分叉 native 暴露 `CallDevToolsProtocolMethod`，成本陡增）。
2. hermes 常用动作在该 WebView2 上是否完整：`Input.*` 点击/键入、`Page.captureScreenshot`、多标签 `Target`。
3. 安全：CDP 端口等于完整浏览器控制权（含 cookie），只能绑 `127.0.0.1`、随机端口、用完即关；且宿主进程是管理员（我们的提权形态）。
4. Tao 迁移回归面：[Main.kt](../composeApp/src/desktopMain/kotlin/dev/shinglem/hermes/Main.kt)（396 行）的窗口创建、自研单实例、托盘、提权、自启都要重新对齐；Tao 把触摸降为 `Pan` 事件，`touchDragScroll` 需重测。

#### 单实例 / 自启 / 提权：不用的具体理由

- **自启（硬理由）**：Nucleus `scheduler` 的 Windows 原生实现是
  `principal->put_LogonType(TASK_LOGON_INTERACTIVE_TOKEN)` + `principal->put_RunLevel(TASK_RUNLEVEL_LUA)`
  （`scheduler/src/main/native/windows/nucleus_scheduler.cpp`）—— **LUA = 普通权限**。
  我们 [ScheduledAutostart.kt](../composeApp/src/desktopMain/kotlin/dev/shinglem/hermes/core/app/ScheduledAutostart.kt) 写的是
  `<RunLevel>HighestAvailable</RunLevel>`（:295）+ `InteractiveToken`（:294）+ `<Arguments>--silent</Arguments>`（:310），
  注释还解释了为什么不用 `RequireHighest`（非管理员用户会直接失败）与 `S4U`（无 UI 会话加不上托盘）。
  换过去 = 登录后只有普通权限：要么每次 UAC 弹窗，要么托盘进程无权做需要管理员的事。
  `autolaunch` 更远：Windows 只有 `Win32RegistryBackend`（HKCU Run）与 `MsixStartupTaskBackend`（MSIX），做不到提权。
- **提权**：Nucleus 的 40+ 模块里没有"以管理员重启/提权"对应物，[Elevation.kt](../composeApp/src/desktopMain/kotlin/dev/shinglem/hermes/core/app/Elevation.kt) + [ElevationRelaunch.kt](../composeApp/src/desktopMain/kotlin/dev/shinglem/hermes/core/app/ElevationRelaunch.kt)（326 行）只能自研。
- **单实例**：Nucleus `SingleInstanceManager` 用**文件锁**（`FileChannel.lock` + `WatchService`）；我们的 [SingleInstance.kt](../composeApp/src/desktopMain/kotlin/dev/shinglem/hermes/core/app/SingleInstance.kt) 用 **`CreateMutexW`**，且 `Main.kt:84-90` 有"`--silent` 的第二次触发只记录、不抢前台"的语义。
  技术上可换，但我们会传 `enableSingleInstance = false`（Tao 迁移时同样），因为它给不了这条语义 —— 换它没有收益。

#### 打包：覆盖到哪一层

| 我们依赖的 | 位置 | Nucleus packaging 能否覆盖 |
|---|---|---|
| 出安装包（MSI / exe / DMG …） | — | ✅ 能（`AbstractJPackageTask` / `AbstractElectronBuilderPackageTask`） |
| 纯外壳、**不含 payload**（用户自备 `hermes/`） | `desktop-release.yml:152-154` 显式校验 `release-test\hermes` 不存在 | ❌ 不涉及（它默认打完整应用目录） |
| 启动器 + 裁剪运行时**独立版本化**（`toolchain-v1`，只增不改） | `toolchain-windows.yml` → `launcher-*.zip` / `runtime-*.zip` | ❌ 不涉及（运行时打进应用） |
| `--silent` 启动器契约、`app/*.cfg`、`startup.log` | `packaging/App.bat`、自写 launcher | ❌ 不涉及 |
| 计划任务安装/对账、提权重启 | `ScheduledAutostart.kt` / `Elevation*` | ❌ 不涉及 |
| 7z 分卷 + SHA256SUMS + Release 上传 | `desktop-release.yml:182-209` | ⚠️ 有 updater，形态不同 |

结论：它解决"打包器"那一层；我们换不起的是**流程层**（两段式 CI + toolchain 版本化解耦 + 纯外壳 + payload 分离）。只发 Windows 便携 7z、不做商店签名分发的前提下收益接近 0，不换。

### #2 内置文件查看/编辑能否直接用 BossConsole 的编辑器

- **类型**：改进（能力评估，触发产品范围决策）
- **优先级**：P2
- **涉及层**：UI（编辑器）/ 产品范围（ADR-005「不做内置编辑器」）
- **调研日期**：2026-11-04

**先澄清对象**（链接里的那个模块不是编辑器）：

- [`modules/boss-app-editor`](https://github.com/risa-labs-inc/BossConsole/tree/main/modules/boss-app-editor) 是**独立进程的 gRPC 服务**：`EditorServiceImpl`（477 行）只做 `open_file` / `write_file` / `detect_main_functions`，依赖 `:boss-ipc` 的 protobuf 契约；真正的「BossEditor + LSP + PSI」在 composeApp 里（其注释原文："GetTokens / NavigateToDefinition: require PSI (in composeApp)"）。
- 真正的编辑器是另一个仓库的制品：**`com.risaboss:bosseditor-compose-desktop:1.0.26`**（Maven Central 有 `jar` / `sources.jar` / `javadoc.jar` + `.asc` 签名，Apache-2.0，最近发布 2026-09-17）。
- 但 `github.com/risa-labs-inc/BossEditor` 现在返回 **404**（无公开 issue / 文档渠道，只有制品可查）。

**为什么不能直接用（硬伤）**：

- 主编辑区是**自绘 Canvas**：`rendering/EditorCanvas.kt`（39.9 KB）、`rendering/EditorCanvasRenderer.kt`（62.7 KB）。
- 文本输入靠按键码：`input/EditorInputHandler.kt:417` `val codePoint = event.utf16CodePoint; val char = codePoint.toChar()` —— 这是**唯一**的字符输入路径（全仓只有这一处 `utf16CodePoint`）。
- Compose Desktop 上，**输入法组合态不走 KeyEvent**（走 `TextInputService` / `BasicTextField` 的 IME 通道）；`utf16CodePoint` 只对物理按键直接映射的字符有效。
- 后果：**中文输入法打不出字**（连注释、搜索框里的中文都不行），且 `toChar()` 只取 BMP —— 代理对（emoji 等）也会坏。对中文优先的应用是致命项。
- 对照：`LargeFileViewer.kt:358` 用的是 `BasicTextField`（只读查看器），说明作者知道两种输入方式的差别，主编辑器选了自绘。

**其他适配成本**（就算 IME 能接受）：

| 项 | BossEditor 1.0.26 | 我们 | 风险 |
|---|---|---|---|
| Compose | 1.9.3（material3 1.9.0） | 1.12.2 | 跨三个小版本的 runtime/ui |
| Kotlin | 2.1.21 | 2.4.21 | 元数据一般向后兼容，但下面那条不是元数据问题 |
| PSI | `kotlin-compiler-embeddable 2.1.21`（go-to-definition） | 项目 Kotlin 2.4.21 | 同一 classpath 出现两代 `org.jetbrains.kotlin.*`，冲突面大；体积再涨 |
| 桌面包 | POM 只声明 `desktop-jvm-linux-x64` 为 runtime | Windows | 需要在 Windows 上实测解析变体 |
| 维护 | 仓库 404，仅 Central 制品 | — | 出问题没有反馈渠道 |

**如果确实要做内置编辑**（需先改 ADR-005 的产品决策）：

1. **JCEF + Monaco / CodeMirror**：我们已有 CEF OSR（`cef/` 310 MB 随包，`CefBrowserOsrWithHandler`），Chromium 自己处理 IME（中文天然可用），JS↔Kotlin 桥在 markdown-one 里已有先例。
2. **只读查看**：用 markdown-one 的代码块渲染 + `SelectionContainer`（现成），不引编辑器。
3. **保持 ADR-005**：跳外部 VSCode / IDEA 打开（当前做法）。

**验收口径**（任何编辑器方案的第一条）：在编辑器里用微软拼音输入「中文内容」→ 保存 → 重新打开，内容不丢、不乱序、光标位置正确。

### #3 WebView2 的定位：能否替代 JCEF、能否做文件编辑器

- **类型**：改进（技术路线评估）
- **优先级**：P2
- **涉及层**：UI 渲染 / 打包体积 / 产品范围（ADR-005）
- **调研日期**：2026-11-04

#### 别人的 webview 实现有多复杂

- 可直接参考的是 ComposeNativeWebview 的 Windows 实现（`webview-compose/src/jvmMain/native/windows` + `.../web/windows`）：

|---|---|

| `view_signals.cpp` | 155 |

即 **≈ 2000 行**，且不含 Tao 提供的窗口与输入。

#### 关键限制：WebView2 没有离屏渲染

- `ICoreWebView2CompositionController` 是 DComp 视觉，输入要**手动转发**（`view_input.cpp` 通篇是 `SendMouseInput`）。
- 唯一的"像素"能力是 `CapturePreview`（一次性 PNG，见 `screenshot.cpp`），不是帧流。
- 官方 issue **#547 "Off-screen rendering with webview2" 至今 open**（138 条评论）。
- → **不能替代 JCEF 做消息内嵌**：我们用的是 `CefBrowserOsrWithHandler` + `windowless_rendering_enabled=true`，帧进 Compose 图元，可随 LazyColumn 裁剪。

#### 自研 WebView2 组件（只做整窗口/固定面板）可行

| 路线 | 关键 API | 估量 | 风险 |
|---|---|---|---|
| **HWND 子窗口**（推荐） | JNA `CreateWindowEx` + `SetWindowPos` + WebView2 `put_ParentWindow` | 600-900 行 Kotlin/JNA，**无 C++** | 原生子窗口永远压在 Compose 之上：裁剪、圆角、滚动、弹层遮挡只能靠布局规避 |
| DComp 合成 | C++ + `CreateCoreWebView2CompositionController` + 手动输入转发 | 1500-2000 行 | 与 AWT/Skia 抢 Z 序；Nucleus 敢走是因为有 Tao 窗口 |
| Tao（现成） | 直接用 `composewebview` | 0 行 | 换整个窗口壳（见 #1） |

#### 用 WebView2 做文件编辑器：可行，但不是必需

- 形态：WebView2 加载 Monaco / CodeMirror，IME 由 Chromium 处理（中文没问题），文件 I/O 走 JS bridge。
- 但**同一套前端在 JCEF 上也能跑**，而我们已有 `cef/`（310 MB）与 OSR —— 编辑器面板直接用 JCEF，**零新增 native 代码**。
- WebView2 唯一优势是省掉 310 MB 随包体积（系统已有 WebView2 `156.x`），代价是 600+ 行自研 + 失去 OSR（不能叠在 Compose 内容里，只能是固定矩形）。
- 结论：**保持 JCEF 时编辑器成本最低；只有确定要砍掉 `cef/` 310 MB 才值得自研 WebView2。**
- 两者都触碰 ADR-005（"不做内置编辑器"），需先改产品决策。

#### 建议顺序

1. 近期要做"浏览器面板"：先用 **JCEF 全窗口**（零新增）验证 `browser.cdp_url` 链路与交互 —— 同时服务 #1 的 spike 6-7。
2. 面板验证通过且确需省体积：再做 HWND 版 WebView2 spike（先只做 navigate + JS bridge，不含 cookie/截图）。
3. 文件编辑器：等 ADR-005 改完再评估，优先 JCEF + Monaco。

#### 验证口径

- 自研 WebView2 的最小验收：窗口缩放时视图跟随不错位、输入框能用微软拼音打中文、`Ctrl+C/V` 生效、关闭面板不泄漏进程。
- **"替代 JCEF"没有验收路径**：要求"把一帧 HTML 贴进 LazyColumn item 并随滚动裁剪"，而 WebView2 不具备该能力（issue #547）。

#### 启用托底的接线（修完适配层之后）

1. **先修适配层**：`CefBrowserOsr` 五参构造 + `addOnPaintListener` 取帧，在 **135** 上跑通"出帧"。
2. 再升 **152**（改两行版本号），核对启动日志 `cef native dir=...`、子进程与帧率。
3. 最后接线 `webFallback = Jcef` + `webDocument` 资源注入，并决定是否默认开启。

#### LaTeX 引擎覆盖面对比（能否替换现有 latex-renderer）

| | `latex-renderer 1.6.3`（在用） | `RaTeX 0.1.15` |
|---|---|---|
| 引擎 | 纯 Kotlin（矢量绘制 + KaTeX 字体包） | **Rust 核心**（自述 >99.5% KaTeX 语法）+ FFI |
| 分发 | 无 native | **必须随包 `ratex-native-windows-x86-64` dll** |
| 环境 | **21 类**：equation / align / aligned / flalign / alignat / gather / cases / dcases / rcases / split / multline / eqnarray / subequations / tabular / matrix 族（含 starred + array/subarray） | 未逐项列出；以 KaTeX 语法集为准 |
| 高级特性 | 450+：`\overbrace` / `\cancel` / `\xrightarrow` / `\overset` / `\operatorname` / `\bmod` / `\pmod` / big 尺寸 / 17 字体 / 10 字号 / `\displaystyle` 切换 / 间距 | 同属 KaTeX 族，覆盖点相近 |
| 额外能力 | `InlineTextContent`、PNG/SVG 导出、MathML、8 类诊断、RTL、高亮、动画 | C ABI（服务端 / PNG / SVG）、MathML 待确认 |
| 风险 | 无 native；已集成 | 新增 dll 分发 + 33★ 封装 |

**两者都不支持**：`mhchem`（`\ce{}` 化学式）、`siunitx`（`\SI`）—— 这属于 KaTeX 扩展包，默认都不在。

**结论：先不替换**。现有 `latex-renderer` 的 450+ 特性 / 21 环境已覆盖 AI 数学输出绝大多数情况，且无 native 分发负担（与 #4 的 `cef/` 体积问题叠加会更糟）。RaTeX 留作两条后路：

1. 遇到具体公式在 `latex-renderer` 上渲染错误时，做同一批公式的 A/B 对比（含性能）；
2. 需要**服务端/离线导出**（PNG/SVG/MathML）时，它的 C ABI 比在 Compose 里截图更合适。
