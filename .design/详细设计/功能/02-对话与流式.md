| 推理 / 思考块 | ✅ 流式 | `reasoning.delta` 累积成**独立段**（`StreamSegment.Reasoning`），**默认展开**（用户要直接看到在想什么），点标题折叠；流式期间是**纯文本**（逐 token 重解析不划算），一轮结束后落成 `ChatItem.Reasoning` 并用 Markdown 渲染；展开态限高 320dp 内部滚动。后端不落库，重开历史看不到 |
| 跨消息选择 | ❌ 明确不支持 | 选区由 markdown-one 在渲染层内包一层 `SelectionContainer`（硬约束 6）：LazyColumn 回收会断选择链 |

**未实现**：`session.title` 推送不写入状态（标题仍取 `SessionSummary`）；无「删除单条」；
历史行里的附件图片不渲染（见 roadmap v0.3.0 的缺口表）。

错误留痕有三处（都在实现里）：
① 发送/中断/轮次失败 → 顶部 `ErrorBanner`；
② 实时失败（`message.complete(failed=true)`）→ 列表末尾追加 `Notice`「本轮失败：…」，滚动回来看历史也看得到；
③ 历史里 `finish_reason` 为 `length` / `content_filter` / `incomplete` 的 assistant 行 → 补一条中文 `Notice`（否则重开对话就是"回答莫名其妙断了"）。

## 2. 状态字段

```kotlin
// ChatState.kt
data class ChatState(
    val key: SessionKey?,                     // (profile, sessionId)：缓存与事件过滤的键
    val load: Loadable<List<ChatItem>>,
    val truncated: Boolean,                   // 只取了最近一页
    val streaming: StreamingState?,           // 非 null = 生成中（segments + startedAt）
    val sending: Boolean,                     // prompt.submit 在途
    val stopping: Boolean,
    val pendingApprovals: List<PendingApproval>,
    val backgroundTasks: List<BackgroundTask>,  // 见 §4「后台任务」
    val killingTaskId: String?,
    val sendError: AppError?,
    val lastUsageTotal: Int?,
    val model: String?, val provider: String?, val reasoningEffort: String?,
    val modelCatalog: ModelCatalog?, val modelCatalogLoading: Boolean,
    val modelSwitching: Boolean, val modelConfirm: ModelConfirm?, val modelError: AppError?,
)
// 派生：items / error / isLoading / isBusy(=streaming != null) / hasApproval
```

**流式必须分段，不能分字段**。一轮里思考 / 工具 / 正文会交替出现
（思考A → 工具A1 → 工具A2 → 回复A → 思考B → 工具B1 → 回复B），
按类型堆成 `text` / `tools` / `reasoning` 三个字段就丢了顺序，表现为
"所有思考挤在最上面、所有正文挤在中间、工具全在最后"。

```kotlin
// ChatState.kt
data class StreamingState(val segments: List<StreamSegment>, val startedAt: Instant?)

sealed interface StreamSegment {                 // 按到达顺序
    data class Reasoning(val text: String)
    data class Answer(val text: String, val sealed: Boolean = false)
    data class Tool(val item: ChatItem.Tool)
}
```

合并规则（`StreamSegments.kt`，纯函数、有单测）：

| 事件 | 落点 |
|---|---|
| `reasoning.delta` | 尾部是思考段就续写，否则另起一段 |
| `message.delta` | 尾部是**未封段**的正文就续写，否则另起一段 |
| `message.interim` | 把尾部正文**封段**（`sealed=true`），`text` 非空时用它校正文本；之后再来的 delta 另起一段 |
| `tool.start` / `tool.complete` | 各自成段；完成时按 `tool_id` 回填结果 |
| `message.complete` | 只替换**尾部未封段**的正文；已封段与前面几段一律不动，整轮文本已出现过则不重复追加 |

工具段之前必须先 flush 正文缓冲，否则 40ms 内的增量会被排到工具之后。

渲染条目 `ChatItem`（sealed）：`UserMessage(id, timestamp, text)`、`AssistantMessage(id, timestamp, markdown)`、
`Tool(id, timestamp, name, label, arguments, result, failed, pairedWithCall)`、`Notice(id, timestamp, text)`、
`Reasoning(id, timestamp, text)`（一轮结束时的思考段落地）。

事件订阅：`message.start / message.delta / message.interim / message.complete / tool.start / tool.complete /
reasoning.delta / request.cancel / agent.terminal.output / session.info / session.title / session.usage / error`，
外加 server→client 请求 `approval`（窗口应答）。

### 审批链路（必须三层都做，缺一条命令就会被判 BLOCKED）

1. **能力声明**：每条 WebSocket 连接收到 `gateway.ready` 后立刻发
   `client.capabilities {server_requests: true}`。后端按 transport 记录这个声明；
   没声明时 `server_requests._unanswerable` 认为本端是"早于 server→client 请求"的旧客户端，
   审批请求**根本不会发出来**，命令直接按"客户端无法应答"撤回。
2. **应答**：收到 `approval` 请求 → 卡片上屏 → 发 `approval.received`（后端超时时钟起点）→
   用户点选后回**响应帧** `{"choice": "once|session|always|deny"}`。
3. **补偿**：`session.resume` 之后调 `approval.pending` 补拉仍然挂着的审批
   （请求发出时本端不在线，那个响应帧永远收不到），这类卡片用 `approval.respond`
   （`{session_id, request_id, choice}`）交付决策。
4. **撤回**：`request.cancel {id, method: "approval", reason}` 到达时移除卡片，
   挂起的响应帧按 `deny` 收尾 —— 后端对已撤回的请求返回 0，是空操作。

本端兜底超时 330s（后端是 300s，必须比它长，否则会在后端还在等的时候先替用户拒绝）。

### 后台任务（composer 上方的状态条）

agent 用 `terminal(background=true)` 起的进程没有"事件化的状态"——只有输出增量有事件，
**进程是否存在 / 退出码只能轮询**：

| 来源 | 用途 |
|---|---|
| `process.list {session_id}`（5s 一次） | 本会话的进程快照：`command` / `status` / `exit_code` / `uptime_seconds` / `output_tail` |
| `process.kill {session_id, process_id}` | 终止单个进程（后端按 `session_key` 校验归属） |
| 事件 `agent.terminal.output {process_id, chunk}` | 输出增量：接到任务行上，详情节实时滚动 |

数据模型 `BackgroundTask`（`session_id` 字段放的是**进程 id**）、合并规则 `reconcileBackgroundTasks`：

- 已有的行**原地更新、不重排**（重排会让列表抽动）；
- 只追加新进程；用户隐藏过的 id 不再出现，直到 registry 也不再报告它；
- 输出以本地累积为准，轮询的 4000 字符快照只在首次出现时用来初始化（否则会把实时增量覆盖回去）；
- 会话被回收（4001/4044）就停止轮询，不要一直撞同一个错。

UI 在 `ApprovalCard` 与 composer 之间：折叠头「N 个后台任务 · M 个运行中」，
展开后每行是状态点 + 命令第一个非空行 + 运行时长/退出码，可就地点开输出（等宽、限高滚动）、
终止（`process.kill`）或隐藏已结束的行。终止动作**不用** `process.stop`——那是 registry 全局 kill_all，
会连别的会话的进程一起杀。

## 5. 空 / 错 / 载入

| 情形 | 表现 |
|---|---|
| 未选会话 | 居中 `EmptyState` |
| 历史加载中 | 居中 `CircularProgressIndicator` + 「加载中」 |
| 历史加载失败 | 居中 `ErrorBanner(onRetry)` |
| 会话为空且无流式 | 空态文案（引导发第一条消息） |
| 只加载了最近一页 | 列表顶部一行提示 + `ChatRepository.MAX_LIMIT` |
| 发送 / 模型切换失败 | composer 上方 `ErrorBanner`（不清空输入） |
| 审批超时 | 后端 300s 后撤回（`request.cancel`），卡片随之移除；本端 330s 兜底按 `deny` 收尾 |
| 用量条无数据 | 整条不渲染（空进度条比没有更困惑）；打开会话会补一次 `session.resume` 再拉 `session.usage` |

## 6. 验收条目

- C1 发一条消息：本地先出现 user 行 → 流式出现 → 完成后成为正式 `AssistantMessage`，无重复行。
- C1b 分段顺序：一轮里「思考 → 工具 → 正文 → 再思考」按到达顺序排开，
  不能出现"所有思考挤在一处、工具全堆到最后"，也不能在 `message.complete` 后重复整段正文。
- C2 工具调用：`tool.start` 出现折叠卡片（转圈）→ `tool.complete` 回填结果；失败卡片有失败标记；
  结果超 20000 字符时显示「显示全部（N 字符）」，点开看全文、再点收起。
- C3 审批：后端请求审批时卡片出现在底部（说明本端已发过 `client.capabilities`），
  选任一项后应答，卡片消失、对话继续；断开期间发出的审批在 resume 后靠 `approval.pending` 恢复。
- C3b 后台任务：agent 起一个 `background=true` 的长命令后，composer 上方出现「1 个后台任务」，
  命令、运行时长可见；点行能就地看输出并持续增长；点「终止」后进程结束，状态变成「已退出（退出码 …）」。`/stop` 之外的路径不会误杀别的会话的进程。
- C4 长回答滚动：贴底时自动跟随（含流式中后段）；用户一向上滚就交还滚动权并显示吸底按钮，
  点它回到底部；用户向下滚回底部自动恢复跟随（补滚自己造成的"贴底"不算恢复依据）；展开历史卡片不触发补滚。
- C4b 思考块默认展开，流式期间按纯文本、结束后按 Markdown 渲染；折叠/展开不改变滚动位置。
- C5 复制整条：hover 出现按钮，复制的是该条纯文本（工具卡片复制参数+结果）。
- C5b 引用：hover 点「引用」→ 输入框追加 `> ` 引用块（原有草稿保留、空行丢弃、超长行截断加 `…`、最多 20 行）。
- C6 图表：非流式时渲染出图（Mermaid / PlantUML / DOT）；语法错误时显示源码 + 一行提示，不崩。
- C7 断线重连：流式中断开 → 状态条报错、`ErrorBanner` 有可读原因、**列表末尾留下「本轮失败：…」提示**；重连后历史仍完整。
- C8 截断提示：历史里 `finish_reason=length` 的回答后面能看到「回答达到输出长度上限，被截断了。」

## 7. 坑

| 坑 | 说明 |
|---|---|
| `prompt.submit` 的 ack 超时必须 1800s | 一轮对话完成靠事件通知，不靠 RPC 返回；30s 会把长回答误判成超时（硬约束 3） |
| LazyColumn 里不能嵌 LazyColumn | 单条消息内部一律普通 `Column`，否则无界高度约束下崩（硬约束 5） |
| 流式期间不要包 `SelectionContainer` | 每帧重建选择容器会导致选中被打断、界面闪 |
| `message.complete` 的 `text` 可能为空 | 为空时用累积的流式文本收口，否则回答凭空消失 |
| 工具失败判定是**启发式** | `looksLikeFailure` 只看文本特征，"宁可漏判也不误报"；要做准确判定得等后端给结构化状态 |
| 工具结果「显示全部」有硬上限 | 超过 200000 字符仍只截断显示；一次性把几十万字符塞进 `Text` 会把滚动拖死（大会话尤其明显） |
| `session.info` 是模型显示的唯一真相源 | 别用发送时的 provider/model 覆盖它，否则切模型后显示不同步 |
| 增量合并窗口注释与常量不一致 | 注释写 24ms，实际 `STREAM_FLUSH_INTERVAL_MS = 40L`；改这个值要同时看滚动跟随的防抖 |
| 图表流式不渲染 | 每次 delta 都重排版会闪且贵，流式中只显示占位，完成后再画 |
| 历史缓存无淘汰 | `cache: Map<SessionKey, TranscriptPage>` 常驻；会话开得多会一直涨（目前可接受） |
| 吸底按钮条件曾用 `sending` | 流式中后段（`sending=false, streaming!=null`）按钮不出现 —— v0.5.2 已修 |
| 吸底按钮跟着补滚闪 | 判据用「是否贴底」时，逐帧补滚动画中列表每一步都"没贴底"，按钮就一帧显示一帧隐藏地闪。改成只看 `followTail`（用户是否接管滚动） |
| 跟随逻辑不能直接读 `state` | `ChatState` 每来一段输出就换新实例，`LaunchedEffect(state.key)` 的 block 只捕获**首次组合**那一个 —— 在里面判 `state.streaming` 永远是 `null`，跟随失效（点「回到最新」也不跟）。要用 `rememberUpdatedState` 取实时值；`followTail` 是 `MutableState`，不受此影响 |
| collect 里不能 await 滚动 | `scrollBy` / `scrollToItem` 都要排 `MutatorMutex`；撞上手势（滚轮的惯性动画）或另一个 `scrollToItem` 时会一直挂起，`snapshotFlow` 的 collect 就此卡死、后续 emission 被 conflate 丢掉 —— 症状是「点了回到最新之后再也不跟随」。改成 `trySend` 到一个 `Channel(CONFLATED)`，由独立 `LaunchedEffect` 循环执行 `requestScrollToItem`（同步、不排互斥量） |
| 「距底距离」不能只看最后可见项 | 列表停在中间时，最后**可见**项的底部正贴着视口底，按它算出的距离是 0 —— 跟随逻辑便认为已经到底、不再补滚。`contentEndGapPx` 在「最后一项还没进视口」时按「至少一屏」返回（`ScrollFollowTest.offscreenItemsAreNeverTreatedAsBottom` 钉住） |
| 补滚不能整块瞬移 | 用 `requestScrollToItem(last, Int.MAX_VALUE)` 补滚时，每一帧都要按条目下标重新锚定 + `forceRemeasure`，并且**一帧内瞬移**整段差距（实测 53–224px）—— 流式时看起来就是「一帧跳一下」的闪烁，工具调用（内容一次涨得多）尤其明显。改成 `animateScrollBy(gap, tween(40..160ms))`，只挪视口不动锚点；`ChatPaneTest.流式增长时补滚逐帧平滑，不会整块瞬移` 钉住「单帧位移 ≤ 40px」 |
| 恢复跟随要由用户动作「武装」 | 只看 `distance <= 8` 就恢复，会把**补滚自己造成的贴底**当成用户回到底部：用户滚一格 → 被拉回 → 判成回底 → 恢复跟随 → 再滚又被拉回，滚轮向上时一直闪。现在只有用户**向下滚**（`resumeArmed`）才允许恢复（`ScrollFollowTest.anyUpwardScrollHandsControlBack` / `ChatPaneTest.流式输出时向上滚一次就接管滚动` 钉住）|
| 引用是**追加**不是替换 | 用户可能已经在写东西，引用只往草稿后面加 `> …` 块；空行丢弃、超长行截断，避免一条长回答把输入框撑成几千行 |
