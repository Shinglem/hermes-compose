# 08 · 浏览器侧栏（v0.6.1）

> 覆盖 `browser` 面板：**把 agent 正在操作的那只 Chromium 嵌进应用右侧的可收起抽屉**。
> 决策与实测见 [ADR-082](../草案/07-decisions.md)；本条只写怎么落。
>
> **状态：设计定稿（2026-11-16），前置四项实测已通过。**
> 前置：ADR-063（`NativeView` 机制）已被 ADR-082 修订为 "attach agent 的浏览器"。

---

## 0. 一句话边界

| 做 | 不做 |
|---|---|
| 嵌入 agent 已拉起的 Chromium，实时看它点哪、去哪 | 自己拉起第二只浏览器 |
| 右侧可收起抽屉（默认收起） | 独立窗口、底部 tab |
| 显示当前页 / 刷新 / 在系统浏览器打开 / 重新连接 | 地址栏导航（那是 agent 的浏览行为，不是用户的） |
| 抽屉内容做成**可扩展容器**（以后放别的侧栏内容） | 插件宿主骨架（**本版不做**，ADR-064 推后） |

**为什么不做地址栏**：面板是"观察窗"，不是"第二个浏览器"。给用户一个能自己导航的地址栏会
和 agent 的页面状态打架（它下一步的点击目标是基于当前页的）。要自己浏览请用"在系统浏览器打开"。

## 1. 形态：右侧可收起抽屉

```
┌──────┬──────────────┬──────────────────────────┬─────────────┐
│      │              │ 顶栏                      │             │
│ rail │  会话列表     ├──────────────────────────┤  浏览器抽屉  │
│      │              │ 对话                      │  360dp      │
│      │              │                          │  （可收起）  │
│      │              ├──────────────────────────┤             │
│      │              │ composer                 │  ┌────────┐ │
│      │              ├──────────────────────────┤  │Chromium│ │
│      │              │ ▸ 终端                    │  │ 画面   │ │
└──────┴──────────────┴──────────────────────────┴─────────────┘
```

- 抽屉在详情栏**右侧**，与详情栏同高（含状态条以上区域）。
- 默认**收起**。收起时是一条 40dp 图标条（或完全隐藏，由 `app.browser.panelOpen` 记忆）。
- 展开态宽度默认 **360dp**，可拖拽调整（记到 `app.browser.panelWidth`），上限窗口宽度 60%。
- 窗口窄于 `RailCompactBreakpoint`（960dp）时抽屉**自动收起**且不可展开，
  展开按钮点击给出「窗口太窄」提示 —— 不给一个挤死对话区的抽屉。

### 1.1 为什么是抽屉，不是底部 tab

终端已经在详情栏底部（`04-ui-spec.md` §3.3），再塞一个 tab 会让底部同时承载两类完全不同的东西：
终端是"我给 agent 敲命令"，浏览器是"我看 agent 在干什么"。前者是输入区的一部分，
后者是观察区。语义不同就不该争同一块地方。

抽屉还解决了一个后续问题：它是**容器**，以后要放别的东西（文件树、diff、子代理详情）
不用再改布局。

## 2. 两条**正交**的轴：纳管 与 展示

> 上一节讲形态，这一节讲**语义**。这是本设计最容易做错的地方。

| 轴 | 由什么驱动 | 状态字段 | 效果 |
|---|---|---|---|
| **纳管** | agent 第一次调 `browser_*` 工具（`tool.start`） | `phase = TakenOver` | 窗口 `SetParent` 收进本进程，**不显示** |
| **展示** | 用户点侧栏按钮 | `panelOpen = true` | 抽屉展开，复用已纳管的窗口 |

**纳管绝不能顺手打开抽屉。** 用户明确要求：「抽屉默认关闭，仅纳管不展示，点侧边工具栏时再展示」。

### 2.1 为什么纳管要一直保持（不能收起就解挂）

`NativeView` 销毁槽位时会 `SetParent(NULL)` 把窗口还原成**独立顶层窗口**。如果"收起抽屉 = 销毁槽位"，
每次收起/展开都会：解挂 → 变独立窗口 → 再收进来。用户看到的就是
「一会儿被纳管、一会儿又成了独立窗口」（实测反馈，已修）。

所以：**槽位常驻组合树**，收起时只是挪出可视区（见 §7.2）。

### 2.2 跳变的真正根因

第一版实现里心跳用 `discover()` 判活。而 `discover()` 只枚举**顶层窗口**；
窗口被 `SetParent` 收进本进程后不在顶层链里了 → 心跳误判"浏览器消失" → 销毁槽位
→ 窗口变回独立窗口 → 下一轮又发现 → **无限重挂**。

修法：判活只调 `gateway.isSlotAlive(hwnd, pid)`（`IsWindow` + `GetWindowThreadProcessId`），
**已纳管时永不**调 `discover()`。实测（`browserLayoutProbe`）：15 秒 × 30 次采样，解挂 **0 次**。

**依赖方向**：`feature/browser`（UI）→ `component/browser`（状态）→ `BrowserGateway`（接口）。

### 3.1 为什么 `BrowserProcess` 这个类**不存在**

ADR-063 原方案里它会"起 Chromium、写 `cdp_url`、关面板杀进程树"。ADR-082 之后这三件事**全不做**：

- 起浏览器 → 不归我们；
- 写 `cdp_url` → 不改 agent 的连接方式；
- 杀进程树 → 会误杀 agent 正在用的浏览器。

只有两个类：**`BrowserDiscovery`（找到它）** 与 **`BrowserSlot`（显示它）**。
看到有人往这里加 `kill()` / `launch()`，那是回退到旧方案，先看 ADR-082。

## 4. 发现：怎么找到 agent 那只浏览器

### 4.1 数据源（实测确认，优先用这个）

**launch record**：`<HERMES_HOME>/cache/browser/chromium-records/*.json`

```json
{"owner_pid": 27900, "owner_start_time": 179483178320,
 "pid": 24976, "start_time": 179483178395,
 "user_data_dir": "…/cache/browser/chromium/<digest>",
 "home_key": "…/hermes-home",
 "ephemeral": true, "ns": null,
 "devtools": "/devtools/browser/97e2d58d-…"}
```

- **ephemeral 与持久 profile 都写**（实测两种形态都有）；
- `owner_pid` + `owner_start_time` 用来判"这个 record 还有效"（owner 已死 = 陈旧 record）；
- `devtools` 是 CDP 的 browser 级 id，不是完整 URL。

**端口**：上面 `user_data_dir/DevToolsActivePort` 第一行（实测 `50619`），第二行是 `devtools` 路径。

**HWND**：`pid` → `Get-Process -Id` 的 `MainWindowHandle` 等价物（见 §3.3）。

### 4.2 为什么不用 `browser.cdp_url`

只有用户手配或 `/browser connect` 才有值；**agent 默认的临时实例不写它**。
`BrowserArgsReconciler` 里那套 `cdp_url` 自愈逻辑处理的是另一种故障（死地址），保持不变。

### 4.3 pid → 顶层 HWND（FFM，不用 AWT）

`java.awt` 的 `Window` 在 Tao 进程里没有对应物（ADR-075 之后业务代码零 AWT）。用 FFM：

```
EnumWindows(callback, lParam)
  → GetWindowThreadProcessId(hwnd, &pid)
  → pid == target 且 IsWindowVisible(hwnd) 且 GetWindow(hwnd, GW_OWNER) == NULL
  → GetWindowTextLength(hwnd) > 0（Chrome 的顶层窗口有标题）
```

或者更简单：`GetWindow(GW_HWNDNEXT)` 遍历，判 `WS_CAPTION`。**实测**：Chromium 主进程
只有一个可见顶层窗口，其余（GPU / renderer / utility）都是不可见的 message-only 窗口。

> 为什么不用 `MainWindowHandle`：那是 .NET `Process` 的便利属性，JVM 没有等价物。
> FFI 走 `user32` 的 `EnumWindows` 是唯一稳的路径，也不需要 `jna`（项目已有 FFM 惯例）。

### 4.4 刷新策略

| 触发 | 动作 |
|---|---|
| 面板展开 | 立刻发现一次 |
| 每 5s（仅面板展开期间） | 重读 record 列表；`pid` 变了就重挂槽位 |
| 用户点「重新连接」 | 立即发现 |
| 槽位失效（`IsWindow` 返回 false） | 显示「浏览器已关闭」+ 重新连接按钮 |

**不做**文件系统监听（`nucleus.fs-watcher` 有，但这里收益不抵复杂度；5s 轮询只在面板可见时跑）。

## 5. `BrowserState`

```kotlin
data class BrowserState(
    val panelOpen: Boolean = false,
    val panelWidthDp: Int = 360,
    val target: BrowserTarget? = null,       // 找到的浏览器
    val phase: Phase = Phase.Idle,
    val lastError: String? = null,
)

sealed interface Phase {
    data object Idle : Phase                 // 面板收起
    data object Searching : Phase            // 正在发现
    data object NoBrowser : Phase            // 没有运行中的浏览器
    data object Headless : Phase             // 找到了但是 headless（没有 HWND）
    data class Attached(val pid: Long, val hwnd: Long) : Phase
    data class Failed(val reason: String) : Phase
}

data class BrowserTarget(
    val pid: Long,
    val hwnd: Long,
    val port: Int,
    val userDataDir: String,
    val pageTitle: String?,
)
```

`Headless` 单独成一个态：找到了进程但**没有窗口可嵌**（headless 实例），此时给的是
「agent 浏览器是 headless 模式，看不到画面；要看得把后端 `browser.headed` 改成 true」，
而不是笼统的"未找到"。这两个故障的处理方式完全不同。

## 8. 槽位实现（desktop）

```kotlin
@Composable
actual fun BrowserSlot(hwnd: Long, modifier: Modifier, empty: Boolean) {
    if (empty || hwnd == 0L || !Win32WindowQuery.isWindow(hwnd)) {
        SlotPlaceholder(modifier)       // 窗口没了就画占位，不硬挂死句柄
        return
    }
    key(hwnd) {                         // 句柄变了必须重建
        NativeView(
            factory = { nucleusHwndPlatformView(handle = { hwnd }) },
            modifier = modifier,
        )
    }
}
```

**必须做**：

1. `key(hwnd) { ... }` 包一层 —— `hwnd` 变了必须重建，否则嵌的是旧窗口；
2. 槽位销毁时**不调**任何 kill / terminate（子窗口的还原由 `NativeView` 自己 `SetParent(NULL)`）；
3. 挂之前先 `IsWindow(hwnd)` —— `nucleusHwndPlatformView` 的 factory 必须返回非空，
   硬挂一个死句柄会得到一块黑区；
4. **覆盖层内容槽不要撑满** —— `NativeView { content }` 的 Compose 覆盖层会吃掉浏览器的鼠标事件。
   本版不需要在画面上叠东西，留空。

**实测过的五条**（ADR-082）：跨进程嵌入 ✅、Compose 压在子窗口之上 ✅、resize 跟随 ✅、
销毁不影响外部进程 ✅、真实应用端到端 ✅。

### 8.1 FFM 的两个坑（都静默失败，不报错）

| 坑 | 现象 | 正确做法 |
|---|---|---|
| `BOOL` 当成 1 字节 | **所有窗口都判为不可见** → 永远 `Headless`，界面说"还没打开浏览器" | `ValueLayout.JAVA_INT` + `!= 0`（Win32 `BOOL` 是 4 字节） |
| 用 `EnumWindows` + upcall stub | 回调跨栈，`pid`/结果槽的传递不可靠 | `GetTopWindow(NULL)` + `GetWindow(GW_HWNDNEXT)` 显式遍历，纯同步 downcall |

> 验证时**不要把浏览器最小化**来给应用腾前台：`IsWindowVisible` 对最小化窗口返回 false，
> 会得到假的 `Headless`。

### 8.2 收起抽屉时槽位怎么处理（**不能销毁**）

`NativeView` 被移出组合树时会 `SetParent(NULL)` 把窗口还原成独立顶层窗口。
所以收起抽屉**不能**写 `if (panelOpen) { NativeView(...) }` —— 那样每次收起/展开都会
"解挂 → 变独立窗口 → 再收进来"，就是用户看到的跳变。

正确做法（`BrowserSidePanel` 里）：

```kotlin
if (!state.panelOpen) {
    CollapsedRail(...)
    // 槽位仍留在树里，挪出可视区
    Box(Modifier.size(1.dp).offset(x = (-20000).dp)) {
        if (state.takenOver) content(Modifier.size(1.dp))
    }
    return
}
```

两个细节：

1. **不能给 0 尺寸**：`NativeView` 按 Compose 布局位置 `setBounds`，0 尺寸会把窗口挪到
   `(0,0,0,0)`，而 Chromium 窗口带边框，会在窗口左上角露出一条竖线（实测）。
   给 1dp + 大负偏移。
2. 收起态用 `offset` 而不是 `padding`：`padding` 受父容器约束限制，负值不生效。

## 9. 配置项

`config_custom.json` → `app.browser`：

| 键 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `panel_open` | bool | `false` | 上次退出时抽屉是否展开 |
| `panel_width_dp` | int | `360` | 抽屉宽度 |

**已有键的处理**（见 ADR-082 的纠正 ②）：

- `headed` 目前注入 `AGENT_BROWSER_HEADED` → **后端运行期不读**（只在 config 51→52 迁移读过）。
  本版**改为**同时 `PUT /api/config` 写后端 `browser.headed`（与 `BrowserArgsReconciler`
  同一条通道），并保留环境变量注入兼容老后端。
- `args` 不变（后端仍读 `browser.chromium_args`，由 `BrowserArgsReconciler` 维护）。

> ⚠️ 改 `browser.headed` 需要 agent **下一次启动浏览器**才生效（已起的那只不会变）。

```
INFO [DESKTOP] browser: agent 开始操作浏览器（browser_exec），纳管窗口
INFO [DESKTOP] browser: 纳管 pid=11740 hwnd=398474
```

### 10.2 ⚠️ 测试方法本身的三个坑（都实际踩过）

做这个功能的验证时**很容易测出假阴性**，以下是踩过的：

**① 事件只推给 `session.resume` 过的会话。**
用脚本 `session.create` + `prompt.submit` 时，如果没先 `session.resume`，
后端不会把这个会话的 `tool.start` 推给该连接 —— 表现为客户端完全收不到工具事件，
看起来像"纳管逻辑没实现"。**必须走应用 UI**（它会自己 resume），或脚本里显式 resume。

**② `browser.headed` 是后端 `config.yaml` 的键，不是客户端 `config_custom.json` 的。**
`release-test/data/agent` 这个 home 原先是 `headed: false`（headless）。
headless 下 Chrome 没有可见窗口 → `discover()` 正确返回 `Headless` → **不会也不该纳管**。
这是正确行为，不是 bug。要测纳管必须先让后端 `headed: true`：

```powershell
# 注意：body 要包一层 `config`，否则 422
Invoke-WebRequest -Uri "http://127.0.0.1:$port/api/config?profile=default" -Method PUT `
  -Headers @{ Authorization = "Bearer $token"; 'Content-Type' = 'application/json' } `
  -Body '{"config":{"browser":{"headed":true}}}'
```

**③ 用 `SendKeys` / `WM_CHAR` 往 Compose 输入框送文本会丢字符。**
实测 `SendKeys` 把 `browser_exec` 变成 `browser—exec`、`https://` 变成 `HTTPS:/`；
`WM_CHAR` 丢 `_` 和 `:`。**用剪贴板 + `Ctrl+V`** 才可靠：

```powershell
Set-Clipboard -Value '用 browser_exec 打开 https://example.com 读一下页面标题'
# 点输入框 → Ctrl+A → Ctrl+V
```

## 11. 已知风险与降级

| 风险 | 降级 |
|---|---|
| **UIPI**：提权进程嵌入非提权窗口被拒 | 显示「因权限差异无法嵌入」+ 「在系统浏览器打开」 |
| DPI 切换画面裂 | 重挂槽位（`key(pid, hwnd, dpi)`）；真机手验 |
| agent 频繁换浏览器实例 | 5s 轮询 + `key(hwnd)` 重建；不缓存旧槽位 |
| 用户自己的 Chrome 被误认 | record 里有 `home_key`，只认本程序 `HERMES_HOME` 下的 |
| 后端版本换了 record 格式 | 解析失败当作 `NoBrowser`，不抛异常；格式变更时同步本条 |

## 12. 不做（本版明确）

- **插件宿主骨架**（ADR-064 的 S7.2）—— 推后。理由：本版先把"看 agent 在干什么"做扎实；
  插件宿主需要宿主页 + 桥 + 本地 http 服务，是另一块工作量。
- **地址栏 / 前进后退** —— 见 §0。
- **截图 / 录制** —— `nucleus.screen-capture` 只有 dev 版，且是单帧。
- **多浏览器并排** —— 一个抽屉一只浏览器。
