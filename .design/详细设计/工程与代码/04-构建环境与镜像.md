# 04 · 构建环境与镜像

> 国内网络环境下的**可复现构建配置**。所有结论都是本机（2026-10-26，Windows 11）实测，
> 不是推测。代理、镜像、Wrapper 三件事在这里定死，其余篇不重复。

---

## 1. 实测环境

| 项 | 值 |
|---|---|
| Gradle | **9.8.0**（Wrapper 锁定） |
| JDK（运行 Gradle / jpackage / jlink） | **Temurin 27**（官方 JDK，自带 `jmods/`）——开发、测试、打包、CI 全部用它，**不再使用 JBR** |
| JDK（目标字节码） | **25**（`jvmTarget = JVM_25`，major 69）：Kotlin 2.4 的 `JvmTarget` 最高只到 25 |
| 成品运行时 | Temurin 27 的 **jlink 裁剪版**（约 60 MB / 232 文件），见 `05-打包与配置.md` §11.7 |
| 本机 JDK 路径 | 写在 **`.local/local.properties`**（整个 `.local/` 不入库）：`hermes.rt.dir` + `hermes.jmods.dir` 指向同一份 Temurin 27 |
| `GRADLE_USER_HOME` | 建议独立到仓库外（本机放在 `C:\envir\gradle\repository`，**不是** `~/.gradle`） |
| 代理 | 需要时 `127.0.0.1:7890`（默认**不启用**，见 §4） |
| 首次全量构建 | 约 **5m54s**（下载 ≈870 MB 依赖）；二次 `build` **12s** |

> ⚠️ 若本机把 `GRADLE_USER_HOME` 改到别处，排查缓存问题时别只看 `~/.gradle`。

## 2. Wrapper

`gradle/wrapper/gradle-wrapper.properties` 的关键四项：

```properties
distributionUrl=https\://mirrors.cloud.tencent.com/gradle/gradle-9.8.0-bin.zip
networkTimeout=60000
retries=3
validateDistributionUrl=false
```

| 设置 | 为什么 |
|---|---|
| 腾讯云镜像 | **`services.gradle.org` 国内不可达**（生成 wrapper 时实测 URL 校验直接失败） |
| `networkTimeout=60000` + `retries=3` | 首次下载 ≈130 MB，默认 10s/0 次重试会中途失败 |
| `validateDistributionUrl=false` | 校验请求走官方端点，必然失败；镜像的 zip 有 SHA 校验兜底 |

**可用镜像实测**

| 镜像 | 状态 |
|---|---|
| `https://mirrors.cloud.tencent.com/gradle/` | ✅ 200 |
| `https://mirrors.huaweicloud.com/gradle/` | ✅ 200（备选） |
| `https://mirrors.aliyun.com/gradle/` | ❌ 404（无 `9.8.0`） |
| `https://services.gradle.org/distributions/` | ❌ 不可达 |

换镜像只需改 `distributionUrl` 一行，并保持 `validateDistributionUrl=false`。

## 3. 仓库顺序（有实测依据，别随意调）

```kotlin
// settings.gradle.kts · dependencyResolutionManagement
1. 腾讯云 maven-public      （nexus 代理 Central，构件最完整）
2. 阿里云 public            （速度快，作补充）
3. 阿里云 google            （仅 androidx / org.jetbrains.androidx）
4. jitpack.io              （仅 com.github.*）
5. mavenCentral() + google()  （兜底）
```

### 3.1 为什么腾讯排第一，而不是阿里云

实测一个反例：`com.mikepenz:multiplatform-markdown-renderer-code-jvm:0.46.0`

| 仓库 | pom | jar |
|---|---|---|
| `repo1.maven.org`（官方） | 200 | 200 |
| `maven.aliyun.com/repository/public` | 200 | **404** |
| `maven.aliyun.com/repository/central` | 200 | **404** |
| `mirrors.huaweicloud.com/repository/maven` | 200 | **404** |
| `mirrors.cloud.tencent.com/.../maven-public` | 200 | **200** |

**关键机制**：Gradle 一旦在某个仓库命中该模块的 metadata，就**不会**回退到后面的仓库。
所以「有 pom、无 jar」的镜像排在前面 = 直接构建失败。

> 结论：**最完整的镜像必须排第一**，而不是"最快的排第一"。

### 3.2 为什么 jitpack 单独限组

- `jitpack.io` **没有国内公共镜像**（实测阿里云 `repository/jitpack` 返回 401，腾讯/Ali/Huawei 均 404）。
- 但 `jitpack.io` 本身**国内可直连**（实测 `https://jitpack.io/` 200；已知构件 `gradle-simple` 200，约 1s）。
- 用 `includeGroupByRegex("com\\.github\\..*")` 限组，避免每个依赖都去 jitpack 打一圈 404。

### 3.3 插件仓库

```kotlin
// settings.gradle.kts · pluginManagement
1. maven.aliyun.com/repository/gradle-plugin   （专代理 Plugin Portal，实测稳定）
2. mirrors.cloud.tencent.com/.../gradle-plugins/
3. maven.aliyun.com/repository/public
4. gradlePluginPortal() / mavenCentral() / google()   （兜底）
```

## 4. 代理

**默认关闭**（走国内镜像已足够）。需要时二选一：

```powershell
# 一次性
.\gradlew.bat build -Dhttps.proxyHost=127.0.0.1 -Dhttps.proxyPort=7890
```

```properties
# gradle.properties（已注释，按需取消）
systemProp.https.proxyHost=127.0.0.1
systemProp.https.proxyPort=7890
systemProp.http.nonProxyHosts=localhost|127.0.0.1|maven.aliyun.com|mirrors.cloud.tencent.com|repo.huaweicloud.com
```

> `nonProxyHosts` 别漏：否则访问国内镜像也绕代理，速度反而更慢。

## 5. Kotlin DSL 的两个坑（会直接让构建失败）

### 5.1 deprecation 被当编译错误

Gradle 9.8 + CMP 1.12 起，`compose.material3` / `compose.materialIconsExtended` /
`compose.components.resources` / `compose.desktop.currentOs` 等便捷 DSL 被标记 deprecated，
而 **Kotlin DSL 脚本把 deprecation 当 error**：

```
Script compilation errors:
  Line 35: implementation(compose.material3)
                ^ 'val material3: String' is deprecated. Specify dependency directly.
```

**为什么不能"改成显式坐标"解决**：

| 依赖 | 显式坐标可行性 |
|---|---|
| `runtime` / `foundation` / `ui` / `components-resources` / `ui-test` | ✅ 有 `1.12.2` |
| **`material3`** | ❌ `org.jetbrains.compose.material3:material3` **稳定版止于 1.9.0**，1.12.x 只有 alpha/beta |
| **`materialIconsExtended`** | ❌ 固定 `1.7.3`（官方已停更，建议将来迁 Material Symbols） |
| **`desktop.currentOs`** | ❌ 需插件按当前 OS 选 skiko 变体 |

所以 `composeApp/build.gradle.kts` **首行**加了：

```kotlin
@file:Suppress("DEPRECATION")
```

这是当前唯一可行解。等 CMP 把 material3 纳入统一版本号后可以去掉。

### 5.2 `by getting` 也被弃用

```kotlin
// ❌ 报错
val desktopMain by getting
// ✅
val desktopMain = getByName("desktopMain")
```

### 5.3 `compose.uiTest` 需要 opt-in

用显式坐标绕过：`org.jetbrains.compose.ui:ui-test:1.12.2`（已进 `libs.versions.toml`）。

## 6. 依赖解析的实际结果（与版本表核对）

`./gradlew :composeApp:dependencies --configuration desktopRuntimeClasspath` 实测：

| 声明 | 实际解析 | 说明 |
|---|---|---|
| `compose.material3` | **1.9.0** | CMP 1.12.2 搭配的稳定 material3 |
| `compose.materialIconsExtended` | **1.7.3** | 官方固定版本 |
| `kotlinx-datetime:0.8.0` | **0.8.0-0.6.x-compat** | material3 1.9.0 请求 0.7.1，合并后落到官方 compat 变体（保留 0.6 的 `Instant` 等 API） |
| 其余 | 与 `libs.versions.toml` 一致 | 无冲突、无 FAILED |

> `libs.versions.toml` 里 `datetime` 直接写 `0.8.0-0.6.x-compat`，避免"写的 0.8.0、跑的是别的"。

## 7. 终端依赖（2026-10-31 更新：BossTerm 源码裁剪 + composite build）

> **本节结论已变两次**：先说 BossTerm 要 Maven 拉不到，后说改 JediTerm，现在是**源码接入**。
>
> **现状（ADR-054）**：终端宿主在 `:modules:terminal`，渲染实现在 git submodule
> `modules/terminal-bossterm`（fork `Shinglem/BossTerm` 的 `hermes` 分支），
> 由 `settings.gradle.kts` 的 `includeBuild` + `dependencySubstitution` 接入：
>
> - **不从这里拉任何 Maven 坐标** → JitPack 与 `packages.jetbrains.team` 两个仓库都已删除；
> - 仍需 Maven 镜像：pty4j / jna / icu4j / compose 等是 fork 的传递依赖；
> - 构建顺序：composite build 会先构建 `:compose-ui`，再构建 `:composeApp`；
> - CI 无额外要求（不需要 JitPack 预热，也不需要 JetBrains 官方 maven）；
> - 克隆后必须 `git submodule update --init --recursive`，否则 `:modules:terminal-bossterm` 是空目录。

### 7.1 历史记录：BossTerm 为何曾经默认关闭

> 以下是 2026-10-30 的实测存证，**已被上面的源码接入取代**，保留是为了记住 JitPack 的行为。

`hermes.terminal=false`（已删除），当时用 `-Phermes.terminal=true` 开启。

实测：

| 检查 | 结果 |
|---|---|
| `jitpack.io` 可达 | ✅ 200 |
| `com/github/jitpack/gradle-simple/1.0/*.pom` | ✅ 200（1s） |
| `com/github/kshivang/BossTerm/bossterm-core-mpp/v1.2.183/*.pom` | ❌ **超时 90s 无响应** |
| `.../v1.2.155/*.pom`（草案里写的版本） | ❌ **404** |

原因：**JitPack 是"现场构建"**——某个 tag 没人拉过就现编，大项目（BossTerm 多模块）可能几分钟到失败。
而且草案里的 `v1.2.155` 在 JitPack 上根本不存在（仓库最新 tag 为 `v1.2.183`）。

**处置**：

1. 终端依赖默认关闭，保证 `build` 恒可通过。
2. `libs.versions.toml` 的 `bossterm = "v1.2.183"`（现有 tag），不是草案的 `v1.2.155`。
3. 真要用时先手动预热，再验证：
   ```powershell
   curl.exe -o NUL -w "%{http_code}`n" --max-time 600 `
     "https://jitpack.io/com/github/kshivang/BossTerm/bossterm-core-mpp/v1.2.183/bossterm-core-mpp-v1.2.183.pom"
   ```
   返回 200 后再 `-Phermes.terminal=true` 构建。
4. 若长期失败，按 ADR-009 的备选顺序换 KetraTerm（Maven Central，Apache 2.0）→ JediTerm。

## 9. 踩坑速查

| 现象 | 原因 | 应对 |
|---|---|---|
| `Test of distribution url ... failed` | 官方源不可达 | 用腾讯镜像 + `validateDistributionUrl=false` |
| 首次构建 5–6 分钟 | 全量下载依赖 | 正常；之后 12s |
| `Could not find xxx.jar`（pom 却有） | 镜像缓存不完整 | 把腾讯 maven-public 排第一 |
| `Script compilation errors` 里全是 deprecated | Gradle 9 把 deprecation 当 error | `@file:Suppress("DEPRECATION")` |
| `material3` 找不到 `1.12.2` | CMP 的 material3 独立版本号（止于 1.9.0） | 用 DSL，不要写坐标 |
| BossTerm 解析挂住 | JitPack 现场构建 | 默认关闭终端依赖；先预热 pom |
| 缓存目录是空的 | `GRADLE_USER_HOME` 被改 | 查 `C:\envir\gradle\repository` |
| 行尾告警 / 整文件 diff | Windows 写 CRLF | 提交前转 LF（`.gitattributes` 已强制） |
| KMP 依赖"解析到但没有 jar"（`Unresolved reference` 指向某个多平台库的类） | 命中了 pom/元数据变体，jvm jar 没下载 | `./gradlew :composeApp:compileKotlinDesktop --refresh-dependencies`（实测 `multiplatform-markdown-renderer-code-jvm` 就是这种） |
| 自动化脚本 `SendKeys` / `keybd_event` 发出的按键到不了 Compose（连 `onPreviewKeyEvent` 都不触发），Enter 不发送 | 中文输入法（微软拼音）处于激活状态时代理进程吞掉合成按键 | 手法与判据见技能 [`dev-desktop-gui-e2e-testing`](../../../.ai/skill/dev-desktop-gui-e2e-testing/SKILL.md)；真实中文输入仍需人工实测 |
