# 06 · 双模式：内嵌 Local 后端与 Remote 后端

> 回答「后端从哪来」：`local` 用 `<home>/hermes/` 下的 Hermes payload 由本程序拉起子进程（**payload 不再随包携带**，由用户按 README 下载放入），`remote` 连已有后端。
> 目录与配置的分工见 [`05-打包与配置.md`](05-打包与配置.md)；取舍见
> [`../../草案/07-decisions.md`](../../草案/07-decisions.md) ADR-029 / ADR-030。
>
> 状态：**已实现**（2026-10-28）。`local` 与 `remote` 都有实现；payload 由 CI 产出
> （[`Shinglem/hermes-bundle`](https://github.com/Shinglem/hermes-bundle) 的 `bundle-windows` workflow，
> 构建原理与已知坑见那边 README），端到端验证见本文 §11。
> 以下事实均来自 hermes 源码与实测核对，标注了出处。
>
> **v0.5.0（hermes 0.23.0）起**：`local` 默认走 `gateway` 路线（`hermes gateway ensure` +
> attach 机器级 daemon），旧的自起 `dashboard` 路线保留为 `backend.local.engine = isolated`。
> 两条路线的对比、契约与实测结论见 §3.3。
>
> **落地方式**：按 `config.json` 的 `backend.mode` 在进程启动时选实现；窗口先出来，
> 后端在后台拉起，启动/失败都有专门页面（§3.2、§11）。

## 1. 目标与不变量

| # | 不变量 |
|---|---|
| I1 | **上层代码完全不感知模式**。Repository / ViewModel / UI 只拿到 `GatewayTarget(baseUrl, token)` |
| I2 | 连接契约不变：WS JSON-RPC + REST，都在 `127.0.0.1:<port>`（见 `08-data-contract.md`） |
| I3 | Local 模式**不写系统安装**：不注册服务、不写注册表、不落全局路径 |
| I4 | `isolated` 路线客户端崩溃不留孤儿后端进程（Job Object 杀光）；`gateway` 路线的 daemon 会**故意**脱离作业，正常退出由 `gateway stop` 收尾、崩溃后下次启动直接复用（见 §3.3） |
| I5 | 端口默认不写死：`isolated` 默认 `--port 0` 由 OS 分配；`gateway` 的端口由 daemon 决定（通过 `api_origin` 告知） |

| 模式 | 后端从哪来 | 启动代价 | 用户场景 | 本期 |
|---|---|---|---|---|
| `local` | `<home>/hermes/` 下的 sealed payload，spawn 子进程 | 首次 5–60s（冷启动 import + Defender 扫 `.pyc`） | 需要先放一份 payload（压缩包约 1.5 GB），从 `Shinglem/hermes-bundle` 对应版本下载 | ⏸ 推迟（payload 5.8 GB，见 §2.3） |
| `remote` | 已有后端（本机已跑的实例 / 另一台机器） | 探活 1 次 | 连自己的服务器；或用改后端调试前端 | ✅ **本期实现** |

## 2. 关键前提：只有 sealed payload 可搬迁

这是整节的地基，必须先讲清楚，否则会写出「在开发机上能跑、拷给别人就炸」的东西。

| 形态 | 特征 | 可搬迁 |
|---|---|---|
| **sealed payload**（官方桌面安装包内） | 根目录有 `manifest.json`，`repo`/`store`/`venv` 全是**相对名**；`bin/hermes.exe` 内嵌 `..\tools\python-...\python.exe` | ✅ 整个目录换盘符、换路径都能跑 |
| **self-managed source install**（本机 `C:\ai\hermes`） | 无 `manifest.json`；依赖目录名 = `sha256(app 绝对路径)[:16]`；`bin/hermes.exe` 内嵌 `C:\ai\hermes\app` | ❌ 搬走即 `RuntimeError: no dependency environment is committed for this install` |

结论：**Local 模式只能用 sealed payload**。开发机上那份 `C:\ai\hermes` 不能拷进 `release-test/hermes/`。

### 2.1 sealed payload 的标准布局（实测自官方 MSIX）

```
hermes/                          ← payload 根（= <home>/hermes）
├── manifest.json                schema/target/repo/venv/store/launchers/runtime/ref
├── enabled-features.json
├── .hermes-baked-pycache
├── bin/                         hermes.exe / hermes-agent.exe / hermes-acp.exe
├── hermes-agent/                源码快照（132 MB，8,474 文件，无 .git）
├── venv/                        依赖树（1,131 MB，56,176 文件）
├── tools/                       python / git / uv / ripgrep / llamacpp…（3,654 MB，15,975 文件）
├── uv-cache/                    离线重建 venv（908 MB）
└── pm-runtime/
```

`manifest.json` 实测原文（节选）：

```json
{"schema":1,"target":"win32-x64","repo":"hermes-agent","venv":"venv","store":"tools",
 "runtime":{"repoDir":"hermes-agent","toolsDir":"tools",
   "storePython":"tools/python-3.14.7+20260901-win32-x64/python.exe",
   "sitePackages":"venv/Lib/site-packages",
   "commands":{"hermes":"bin/hermes.exe", ...}},
 "ref":"e06df9c2..."}
```

**磁盘成本**：解压后约 **5.8 GB**。这是 Local 模式的真实代价，不是可以含糊过去的数字。

### 2.2 可用性判据（4 条，缺一不可）

| # | 判据 | 不满足的后果 |
|---|---|---|
| P1 | `manifest.json` 存在且可解析 | 说明不是 sealed 形态 |
| P2 | `manifest.target` 与本机架构一致（`win32-x64` / `win32-arm64`） | 解释器与 DLL 架构不匹配，启动即崩 |
| P3 | `manifest.runtime.commands.hermes` 指向的文件存在 | 无法 spawn |
| P4 | 存在 `hermes-agent/` 且 `venv/Lib/site-packages` 非空 | 依赖树缺失 |

**不要**用「`bin/hermes.exe` 能不能跑」来判定——它跑失败的原因和「payload 不完整」无法区分，报错会误导。

### 2.3 payload 从哪来

官方**没有**独立发布的 payload 发行物。只有两条路：

| 路 | 做法 | 代价 |
|---|---|---|
| **A 从官方 MSIX 抽** | `stable.appinstaller`（XML）→ 其中 `MainBundle Uri` 指向 `.msixbundle` → 解两层 zip → `app/resources/agent-payload/` 整个目录即 payload 根 | 下载 **4.33 GB**，解出 2.52 GB msix，最终 5.83 GB；峰值磁盘 **~12 GB** |
| **B 自己构建** | `python -m scripts.bundles.stage --out <DIR> --ref HEAD`（等价 `npm run payload --workspace apps/desktop`）；只要原生部分用 `hermes pm bundle --out <DIR>` | 需要 host Python 3.11+ / Git / 外网（拉 pinned CPython、uv、Node、llamacpp 等数 GB） |

实测的通道入口（2026-10-27）：

```
https://hermes-assets.nousresearch.com/releases/win32/stable/stable.appinstaller
  → Version 2026.6864.2132.0
  → MainBundle: https://hermes-assets.nousresearch.com/releases/tag/rc.3-v0.22.0/HermesBundled-2026.6864.2132.0-win.msixbundle
https://hermes-assets.nousresearch.com/releases/win32/canary/canary.appinstaller
```

**抽取时必须用 `makeappx.exe unpack`**（Windows SDK）。用普通解压器的坑：zip 中央目录里
`tools/python-3.14.7%2B20260901-win32-x64` 的名字是 URI 编码的，而 `manifest.json` /
`pyvenv.cfg` / `bin/hermes.exe` 引用的是 `python-3.14.7+20260901-win32-x64`。
解出来字面 `%2B` → `storePython` 路径对不上 → 启动即失败，且报错完全指不出这个原因。

> **本期不做程序内下载**（见 §9）。`release-test/hermes/` 由开发/发布流程放好，
> 程序只做检测与引导。理由：4.33 GB 下载 + 双层解压 + `%2B` 陷阱 + 峰值 12 GB 磁盘，
> 这套链路的失败面比整个客户端其余部分加起来还大，且和"能不能用起来"无关。

## 3. 模式抽象

### 3.1 接口

```kotlin
// core/backend/BackendProvider.kt
enum class BackendMode { LOCAL, REMOTE }

sealed interface BackendBootState {
    data object Idle : BackendBootState
    data class Starting(val step: String) : BackendBootState   // "正在启动本地后端…" / "等待端口…"
    data class Ready(val target: GatewayTarget) : BackendBootState
    data class Failed(val error: AppError, val detail: String?) : BackendBootState
}

interface BackendProvider {
    val mode: BackendMode
    val state: StateFlow<BackendBootState>
    /** 幂等；已 Ready 时立即返回。失败后再次调用等于重试。 */
    suspend fun start()
    suspend fun stop()
}
```

两个实现：`LocalBackendProvider` / `RemoteBackendProvider`。

### 3.2 对上层透明怎么保证

现有传输层已经是「每次操作现取地址」：

```kotlin
val targetProvider = { GatewayTarget(baseUrl = preferences.baseUrl, token = resolveToken()) }
```

改成 `targetProvider = { provider.currentTarget() }` 即可，**Repository / ViewModel / UI 一行不改**。

唯一的时序约束：`gateway.start()` 必须在 `Ready` 之后。所以：

// 实际实现（2026-10-28）
main()
 ├─ 解析 config → 选 Provider（local / remote）
 ├─ application { Window { … } }
 ├─ LaunchedEffect: provider.start()        ← 后台拉起，不阻塞首帧
 ├─ 界面**立刻**渲染（AppShell 直接上屏，不设启动页拦截）
 │     StatusBar 上实时显示：本地后端：<step> / 就绪 (:port) / 启动失败
 │     点这条状态 → BackendDetailDialog（原因 + 控制台尾 + 重试启动）
 ├─ backend Ready → ShellViewModel 主动重连 gateway（不等指数退避）
 └─ onCloseRequest: container.close() → gateway.close → 各子进程 terminate → exitApplication()
```

两条硬约束：

1. **后端没起来也要能操作界面** —— 所以 `Ready` 才渲染主界面是错的（早前版本如此，已改）。
2. **未就绪时不能回落到 remote 地址** —— `LocalBackendProvider.currentTarget()` 在 Ready 前返回
   `http://127.0.0.1:0`。用配置里的 `remote.base_url` 会连到机器上另一个 Hermes（本机就有 9119），
   把会话写到别人的数据上。

启动页的文案必须能区分**卡在哪一步**（payload 校验 / spawn / 等端口 / 连接 WS），
否则用户看到的永远是「转圈」，而这条路线上每步失败原因完全不同。

### 3.3 两条 Local 路线：`gateway`（默认，0.23+）与 `isolated`

`backend.local.engine` 决定 `local` 模式走哪条；两者对上层同样透明，差别只在「后端进程归谁管」。

| | `gateway`（默认） | `isolated`（回退） |
|---|---|---|
| 后端怎么起 | `<payload>/bin/hermes.exe gateway ensure --json`，由上游起**机器级 daemon** | 我们自己 spawn `dashboard --isolated` |
| 进程归属 | detached daemon（**脱离**我们的 Job Object） | 我们的前台子进程 |
| 端口从哪来 | ensure 输出的 `endpoint.api_origin` | ready 文件 / `HERMES_*_READY` 哨兵 |
| 客户端退出 | 显式 `gateway stop -y`（限本 home） | 本句柄 `terminate()` |
| 客户端崩溃 | daemon **残留**（下次启动 ensure 直接复用） | Job Object 杀光 |
| 能力保证 | owner 侧统一：队列 / history / steer / rewind | 与 owner 语义可能分叉 |

**为什么默认换成 gateway**：0.23.0 起官方 Desktop、TUI、webapp 全部改成
`ensure → attach`（`ui-tui/CANONICAL_GATEWAY.md`、`apps/desktop/electron/local-gateway.ts`），
「一个 gateway 拥有该机器上全部会话」是上游唯一的 canonical 语义。我们自起 isolated server
等于在机器上多开一套 owner，队列与 history 会和别的入口分叉。

**契约与实测结论**（v0.23.0，本机 payload 实测）：

| 项 | 值 |
|---|---|
| ensure 输出 | stdout 单行 JSON：`state`/`reason_code`/`endpoint`/`client_code_sha`；exit code 0 ready / 3 incompatible / 4 authorization / 5 starting·deadline·absent / 6 draining / 7 inaccessible·conflict |
| endpoint 字段 | `profile_id`（绝对路径，就是 home）、`instance_id`、`authority_epoch`、`runtime_protocol`（必须 =1）、`api_origin`、`supervisor`、`capabilities`、`control_home?`、`code_sha?` |
| 鉴权 | 我们注入的 `HERMES_DASHBOARD_SESSION_TOKEN` 被 daemon 继承 → WS `/api/ws?token=` 与 REST `X-Hermes-Session-Token` 都认它（错误 token → 403 / 401）；loopback 的 `/api/status` 无需鉴权，业务接口仍需 token |
| Web UI | gateway listener 会按需挂载 dashboard，`GET /` 返回 dashboard HTML；**不注入** `window.__HERMES_SESSION_TOKEN__`。**客户端不使用它**（0.5.0 起不再提供任何浏览器入口），payload 里带不带 `web_dist` 都不影响客户端 |
| 绿色化 | daemon 强制 `HERMES_HOME=<我们传的 home>`，数据 / 日志（`<home>/logs/gateway-stdio.log`）/ 控制 socket 全在程序目录内 |
| 关停 | `gateway stop -y` 输出 `✓ Stopped gateway for this profile`，作用域只到本 home；**绝不加 `--all`**（那是 host gateway，会停到别人的 profile） |

**不能设的变量**：`HERMES_PARENT_PID` / `HERMES_PARENT_START_MARKER` / `HERMES_DESKTOP_READY_FILE`
——daemon 不是我们的子进程，父进程看门狗与 ready 文件这两套机制它都不认。

**关键坑**：ensure 那个短命进程**不能**绑进我们的 Job Object。daemon 用
`CREATE_BREAKAWAY_FROM_JOB` 脱离父作业，而 Windows 只允许在作业显式设置
`JOB_OBJECT_LIMIT_BREAKAWAY_OK` 时 breakaway —— 把 ensure 塞进我们那个不允许 breakaway 的作业，
daemon 就永远起不来。

`exe` 必须是 payload 里的 `bin/hermes.exe`（sealed payload 的 launcher 会切到自带 python，
日志里的 daemon 命令行即 `payload/tools/python-…/python.exe -m hermes_cli.main …`）。

## 4. Local 模式（isolated）：子进程规格

### 4.1 命令行

```
<payload>/bin/hermes.exe dashboard --host 127.0.0.1 --port 0 --skip-build --no-open
```

**只起一个进程，用 `dashboard` 而不是 `serve`。** 两者提供同一套 WS JSON-RPC + REST
（上游 help：`serve` 是 "backend server (headless; powers the desktop app and remote backends)"），
差别只在 `dashboard` 额外提供 Web UI 静态资源 —— 不过客户端自 0.5.0 起只用 RPC/REST，
**共用同一个端口**，也不需要维护第二条 `serve` 路径。

`--host` / `--port` 来自 `backend.local.host` / `backend.local.port`（默认 `127.0.0.1` / `0`）。

| 参数 | 为什么 |
|---|---|
| `--host 127.0.0.1` | 只绑 loopback。绑非 loopback 会触发认证 gate，且 Host/Origin 白名单只认 `localhost`/`127.0.0.1`/`::1` |
| `--port 0` | OS 分配。写死 9119 会与用户已跑实例冲突；`--port 0` 也让多实例天然共存 |
| `--skip-build` | 运行时不跑 npm 构建（几十秒 + 依赖 npm store）。**代价是 payload 必须自带 `web_dist`**，见 §4.1.1 |
| `--no-open` | 别让它自己拉起系统浏览器 —— 界面在客户端里，浏览器是可选入口 |
| `--profile <name>` | 只在需要钉住 profile 时加。不传则跟随 payload 内的 sticky `active_profile` |
| `--isolated` | **必须加**。机器上已有别的 dashboard 时（例如官方桌面端占着 9119），新进程会 attach 到那台 host 后端并 `exit 0`（`Hermes dashboard already running on this host: PID …, port …`），我们就绪判定只能看到"进程立刻退出" → 本地后端永远起不来。它同时跳过 `_route_named_profile_dashboard` 的机器级重定向 |

#### 4.1.1 `web_dist` 是 payload 的一部分

`pm bundle` 用 `git archive` 做快照，而 `hermes_cli/web_dist` 是 `npm run build` 的产物
（在 `.gitignore` 里），**不在 archive 里**。缺了它 `dashboard` 会直接退出：

```
⚠ --skip-build was passed but no web dist found at: <payload>/hermes-agent/hermes_cli/web_dist
```

所以 `hermes-bundle` 的构建流程必须在 `pm bundle` 之后把 install checkout 里的
`hermes_cli/web_dist` 复制进 payload（与 `install-stamp.json` 同一趟）。

> 客户端自 0.5.0 起不再探测、也不再提供打开 Web UI 的入口；它留在 payload 里只服务
> 官方自己的 dashboard / webapp，删掉不会影响本客户端。

**不要用 `bin/hermes.cmd`**：它是 cmd 黑框 + base64 包装的 `python -I`；`.exe` 才是 console-script。

**不用 `hermes serve --stop` 来关停**：它虽然已按 `HERMES_HOME` 作用域扫描（`#113978`，
只停同 home 的后端），但本质仍是「扫进程表 + 猜归属」。客户端直接持有子进程句柄，
`descendants().destroy()` → 3s → `destroyForcibly()` 只作用于自己那棵树，
物理上不可能碰到别的安装 —— 见 [`09-后端关停纪律.md`](09-后端关停纪律.md)。

#### 4.1.2 对外共享：为什么是「回环 + 隧道」而不是绑 `0.0.0.0`

后端 2026-06 的加固把绑定分成两种模式：

| 绑定 | 模式 | 凭据 |
|---|---|---|
| `127.0.0.1` / `::1` / `localhost` | **loopback** | `X-Hermes-Session-Token`（就是 `HERMES_DASHBOARD_SESSION_TOKEN`），WS 走 `?token=` |
| 其它任何地址（含 `0.0.0.0`） | **gated** | 登录 cookie / 单次 ticket；**必须配置 auth provider（口令或 OAuth）** |

本客户端只会发 session token，**在 gated 模式下一律 401**。所以「绑 0.0.0.0 让别人连」
对桌面端不成立 —— 那条路只对浏览器登录页有效。官方帮助也是这个口径：
*"Bind 127.0.0.1 + tunnel to keep it local."*

可用的三种共享方式（都建立在 loopback 上）：

| 场景 | 做法 |
|---|---|
| 本机脚本 / 其它工具 | `backend.local.port` 固定 + `backend.local.token` 固定，直接连 `127.0.0.1:<port>` |
| 别的机器上的 Hermes 客户端 | 本机固定端口与 token；对端 `ssh -L 9119:127.0.0.1:<port> user@host`，客户端 `backend.mode=remote`、`base_url=http://127.0.0.1:9119`、token 填同一个 |
| 浏览器 | 同一条隧道，开 `http://127.0.0.1:9119`（dashboard 同端口自带 Web UI） |

要点：隧道让后端看到的仍是**回环连接**，鉴权沿用 session token，代码一行都不用改；
TLS、身份、可达性由隧道层负责（Tailscale 同理）。

代价与注意：

- `backend.local.token` 明文落在 `config.json`，等同一把 API key —— 不要提交进仓库、不要发给不该给的人。
- `backend.local.port` 固定后，与已占该端口的实例（例如官方桌面端 9119）冲突会**启动失败**，
  报 `端口被占用（port=N）`；换一个端口即可。
- `backend.local.host` 留默认值。填非回环地址会进入 gated 模式，客户端连不上（UI 的 hint 里也写了这句）。

### 4.2 环境变量（实测自官方 `electron/main.ts:12257-12278`）

| 变量 | 值 | 作用 / 不设的后果 |
|---|---|---|
| `HERMES_HOME` | payload 数据根（必须**含 `installs/`** 的那一层）；成品里是 `<home>/data/agent` | 不设则回落 `~/.hermes`，把用户家目录写脏 |
| `HERMES_DASHBOARD_SESSION_TOKEN` | 自铸 32 hex | 敏感端点校验它；不设则后端每进程随机生成，客户端拿不到 → 21 个敏感端点全部 401 |
| `HERMES_DESKTOP` | `1` | 启用 cron tick、MCP discovery、孤儿回收、loopback 下 `public_url` gate 豁免（副作用见 §4.5） |
| `HERMES_PARENT_PID` | 本进程 PID | 父进程 watchdog |
| `HERMES_PARENT_START_MARKER` | **本进程的创建时间**：`winms:<Unix 毫秒>` | 防 PID 复用误判。⚠️ **必须是真的创建时间**（`ProcessHandle.current().info().startInstant()`），传 `System.currentTimeMillis()` 会让后端把「父进程已被替换」判定为真，启动约 2 秒后自杀 —— 表现为客户端无限重连 |
| `HERMES_PARENT_NONCE` | 16 字节 hex | 与 marker **必须成对**，否则 watchdog 自动 disarm |
| `TERMINAL_CWD` | 工作目录 | 工具/终端默认 cwd，显式钉住避免继承残留 |
| `PYTHONPATH` / `PYTHONHOME` | 空串 | 防止继承别的 checkout 的模块路径 |
| `PYTHONUTF8` | `1` | 强制 UTF-8；Windows GBK locale 下 stdio 会乱码（中文项目必设） |
| `HERMES_DISABLE_LAZY_INSTALLS` | `1` | 切断启动时的懒装依赖路径，避免连接时才炸 |
| `HERMES_DESKTOP_READY_FILE` | `<dataDir>/runtime/ready-<nonce>.json` | 绑定后写 `{"port":N}`；**首选的端口发现通道** |
| `HERMES_WEB_DIST` | —— | **不设**。纯 JSON-RPC 客户端不需要 SPA 静态资源 |

`stdio = [ignore, pipe, pipe]`：stdin 必须 ignore。

**必须是白名单传给子进程，不整份继承 `System.getenv()`。** 两个理由：
1. 客户端自己的 `HDC_*` 变量一个都不该漏进后端
2. 用户 shell 里的其它变量（代理、`PYTHON*`、云凭据）也不该被后端"意外吸收"

实现上：从空 `MutableMap` 开始，只放上表里的变量 + `PATH`/`SYSTEMROOT`/`TEMP`/`USERPROFILE` 这类
OS 运行必需的项。

### 4.3 就绪握手

绑定成功后，后端往**真 stdout（fd 1）**直写两行哨兵：

```
HERMES_BACKEND_READY port=<N>
HERMES_DASHBOARD_READY port=<N>      ← 兼容旧解析器，两行都会发
```

**判定优先级：ready 文件 > stdout 哨兵。**

| 通道 | 优点 | 缺点 |
|---|---|---|
| `HERMES_DESKTOP_READY_FILE`（150ms 轮询 JSON） | 不受 stdio 缓冲/编码影响；pythonw 无控制台时是正规通道 | 需要先删残留文件 |
| stdout 哨兵 | 官方 Desktop 用的 | 解析必须**不做行首锚定**：uvicorn 的 stderr 块末尾无换行，哨兵会被拼到 `Started server process [4711]` 后面 |

正确正则（踩过坑的版本，**按合并流匹配**）：

```
/(?<!\w)HERMES_(?:BACKEND|DASHBOARD)_READY port=(\d+)/
```

**两个通道都要有**：stdout/stderr 必须持续读并落日志——不读会让子进程因 pipe 满而阻塞，
崩了也没堆栈；但判定用文件更稳。

端口冲突另有一行哨兵 `BACKEND_PORT_IN_USE port=<N>`，用于把「起不来」和「端口被占」区分开。

**超时**：默认 **90s**，下限 **45s**。冷启动 30–60s 是正常的（import 整条
`hermes_cli.main → web_server → FastAPI/uvicorn` 链，Defender 还要扫新 `.pyc`）。
给 30s 会把正常启动误判为失败——这与 `prompt.submit` 需要 1800s 是同一类错误。

### 4.4 关停

**后端没有 HTTP shutdown 端点**，Windows 上也没有 SIGTERM 语义。

```
provider.stop()
 ├─ gateway.close()                              ← 先断 WS，避免它写字时对端消失
 ├─ process.destroy()                            ← Windows = TerminateProcess
 ├─ 等 3s
 ├─ 未退出 → process.destroyForcibly()
 └─ 兜底：HERMES_PARENT_PID/START_MARKER/NONCE 的 watchdog 让后端在父进程消失后自杀
```

三层缺一不可：`destroy()` 不能保证子进程树全死（后端会拉工具子进程），watchdog 兜住
「客户端被强杀」这一路。

### 4.5 `HERMES_DESKTOP=1` 的取舍（必须知情）

| 设了 | 不设 |
|---|---|
| ✅ cron tick 由后端自己跑 | ❌ cron 不跑 |
| ✅ MCP discovery 在绑定后自动起 | ❌ 需手动 |
| ✅ 孤儿回收 + loopback gate 豁免 | ❌ 失去这两条 |
| ⚠️ **会替用户执行他自己配置的 cron 作业** | ✅ 不越界 |

官方 Desktop 设了它。本项目语义相同（就是个桌面客户端）→ **设**。但要在设置页说明
"本地模式会执行你配置的定时任务"，因为这是用户可感知的副作用。

## 8. 坑

| 现象 | 原因 | 应对 |
|---|---|---|
| 拷到别的机器后报 `no dependency environment is committed for this install` | 用的是 self-managed 源码安装，不是 sealed payload | 只接受 sealed payload；见 §2 |
| spawn 后立刻退出，日志只有一行 RuntimeError | `HERMES_HOME` 指到了没有 `installs/` 的目录 | `HERMES_HOME` 必须是 payload 数据根 |
| 启动"成功"但敏感端点全部 401 | 没设 `HERMES_DASHBOARD_SESSION_TOKEN` | 自铸 token 并通过 env 注入；不要走命令行参数（进程列表可见） |
| 解析端口偶发失败 | stdout 哨兵被拼接到 stderr 块的末尾（无换行） | 用 `(?<!\w)HERMES_(?:BACKEND\|DASHBOARD)_READY port=(\d+)`，不锚定行首 |
| `gateway ensure` 返回 `windows_interpreter_unavailable` | 上游在 Windows 上要用无窗口解释器重启 daemon，`_resolve_detached_python` 解析不到 | 只接受 sealed payload 的 `bin/hermes.exe`（含 `tools/python-*` 与 venv），别指向系统 python |
| attach 之后客户端退出，daemon 还在跑 | daemon 用 `CREATE_BREAKAWAY_FROM_JOB` 主动脱离作业 | 正常退出走 `gateway stop -y`；崩溃后由下次 `ensure` 复用，不硬杀 |
| `gateway stop` 把别人的后端也停了 | 用了 `--all`（作用于 host gateway，不是当前 profile） | 只允许不带 `--all` 的 stop；作用域全靠注入的 `HERMES_HOME` |
| 正常冷启动被判超时 | 给了 30s，而冷启动要 30–60s | 默认 90s，下限 45s |
| 子进程卡住不输出、也不就绪 | stdout/stderr 没被读，pipe 缓冲满 | 必须开两个线程持续读并落环形缓冲 |
| 关闭程序后 `hermes.exe` 还在 | `destroy()` 只杀直接子进程 | 三段式关停 + 父进程 watchdog env |
| 顺手杀掉用户自己的 Hermes | 用了 `hermes serve --stop`（全机扫描） | 只杀自己 spawn 的 PID 树 |
| 端口冲突 | 写死 9119 | `--port 0` + 读就绪回报的端口 |
| 本地后端"启动即退出"，日志写 `Hermes dashboard already running on this host: PID …, port 9119` | 机器上已有官方桌面端的 dashboard；不带 `--isolated` 时新进程**attach 到那台 host 后端并 exit 0** | 后端命令固定加 `--isolated`（见 §4.1） |
| 中文乱码 | Windows GBK locale 下 Python stdio 默认非 UTF-8 | `PYTHONUTF8=1`（客户端自己的 stdout 不受影响） |
| 抽 MSIX 后启动失败但报错看不懂 | `%2B` 文件名编码，`storePython` 路径对不上 | 用 `makeappx.exe unpack`；解完核对目录名是 `+` |
| 删了 `tools/` 想瘦身，结果被判 payload 不完整 | `facts.json` 记的是 tree digest | 裁剪后必须 `python -m scripts.bundles.payload rehash` |
| 直接跑 `venv\Scripts\python.exe` 起不来 | `venv\pyvenv.cfg` 里的 `home` 是构建机绝对路径（正常现象） | 走 `bin/hermes.exe` 或 `tools/python-…/python.exe` + `venv/Lib/site-packages` |
| 用户没料到定时任务被执行 | `HERMES_DESKTOP=1` 的副作用 | 设置页说明 + `runCron` 开关 |
| 启动页一直转圈，不知道卡哪 | 只有单一 Loading 态 | `Starting(step)` 区分：校验 payload / spawn / 等端口 / 连 WS |

### 11.3 踩过的坑：`HERMES_PARENT_START_MARKER` 传错 = 后端自杀

第一版用 `winms:${System.currentTimeMillis()}`，后端启动约 2 秒就被父进程 watchdog 收掉，
客户端表现为「一直重连」。后端源码（`web_server_lifecycle.py`）：

```python
# winms: 是父进程创建时间（Unix ms），与 FILETIME 换算后比较
actual_unix_ms = (dotnet_ticks - 621_355_968_000_000_000) // 10_000
return actual_unix_ms == expected_unix_ms
```

传当前时间必然不等 → `_parent_start_marker_mismatch_is_conclusive()` 返回真 → `_request_orphan_shutdown()`。
正确写法：

```kotlin
parentStartMarker = "winms:" + ProcessHandle.current().info().startInstant()
    .map { it.toEpochMilli() }.orElse(0L)
```

> 排查线索：`%LOCALAPPDATA%\hermes-compose\logs\backend-serve.log` 会**重复出现** `HERMES_BACKEND_READY port=…`
> （每次重启一个新端口），而 `hermes-home/logs/agent.log` 里没有任何异常 —— 因为它是「正常退出」。


> `LocalBackendE2eTest` 未设 `HERMES_E2E_PAYLOAD` 时直接返回（CI 不需要 6 GB payload）；
> 本地验证命令写在测试的 KDoc 里。
