## 2. 不做的后果（为什么这不是"省一个进程"）

加进"登录自启"之后，重复实例从偶发变成**必然**：计划任务用 `--silent` 启动 → 没有窗口、只有托盘，
而 Windows 默认把新托盘图标折叠进 `^` —— 用户看不到任何窗口，很自然再双击一次。

| 后果 | 依据 |
|---|---|
| 两套 cron 调度器，同一 profile 的定时任务跑两次 | 后端日志 `Desktop cron scheduler will tick 1 profile(s)`，每个 serve 各起一套 |
| 同一个 `state.db` 被两个 serve 同时写 | WAL 允许并发，但 session 索引 reconcile / owner 记录会互相覆盖 |
| 两个后端抢 host lock，第二个降级 observe-only | 实测错误：`Host backend lock could not be opened (...gateway-locks\host-serve.lock); this backend is not discoverable` |
| logback 轮转互相踩 | `FixedWindowRollingPolicy` 靠 rename 完成轮转，隐含"单一写者"前提（`desktop`/`gateway`/`dashboard` 三份日志共用目录） |
| 两个托盘图标、两份内存（每份还有整套 MCP 子进程树） | 直接可观察 |
| 提权后两份同时 `computer_use` 会互相打架 | 都是管理员，谁也拦不住谁 |

## 3. 载体：命名内核对象

```
Local\HermesCompose-<home hash>-instance   互斥量  存在 = 已有一份在跑
Local\HermesCompose-<home hash>-activate   自动重置事件  第二实例 SetEvent → 第一实例显示窗口
```

| 备选 | 为什么不用 |
|---|---|
| 锁文件 / PID 文件 | **强杀留僵尸锁**（文件不会被自动清理），下次启动要处理"锁文件存在但进程已死"的判别，判别本身又会因 PID 复用出错 |
| 端口锁（bind 一个固定端口） | 占端口、要处理防火墙/端口被占、还要做超时；且端口不是按 home 隔离的天然键 |
| 本地 socket / 命名管道 | 能顺带传消息，但要处理 ACL、超时、协议；只为"显示窗口"这一个动作引入一套 IPC 不划算 |
| `Global\` 命名空间 | 需要 `SeCreateGlobalPrivilege`（管理员有、普通用户没有）→ 提权实例与非提权实例**看不到彼此**，单实例在最需要它的场景失效 |
| `Local\` 命名空间 | ✅ 会话级、同一用户跨完整性级别可见 |

**内核对象最大的好处**：句柄随进程退出由内核回收，**强杀不会留锁**（S4 天然成立）。
这正是锁文件方案最难处理的情形。

### 3.1 为什么还要一个事件对象

只拦不留问题：用户双击后"什么都没有发生"，会反复点、以为程序坏了。
事件的语义是"**请把窗口显示出来**"，第一实例起一个等待线程：

```
收到 activate → 窗口在托盘里 → 显示并前置（SetForegroundWindow 失败就只显示）
               窗口已显示   → 尽力前置
```

## 4. 命名：按 `<home>` 哈希

```
HermesCompose-<sha256(home 规范化绝对路径) 前 8 位小写十六进制>
```

- 必须用**规范化**后的路径（`File.getCanonicalFile()`）：大小写、短路径 `PROGRA~1`、符号链接都会算出不同的名字
- 不同 `<home>` → 不同名字 → 两份便携包可以同时运行（S1 的另一半，是**设计目标**不是缺陷）
- 与计划任务名（`07` §3.5）用同一套 hash，便于用户对照

## 5. 启动时序（权威版本）

`main()` 的每一步都有失败出口，顺序不能随意调（理由在表格后面）：

```text
0. 打开 <home>/logs/startup.log，写第一段（见 §7）        ← 不依赖配置解析、不依赖 logback
1. 解析配置（ConfigLoader）
     失败 → 写 startup.log（含文件与字段）→ 退出码 2（见 `05` §3.2）
2. 重启交接：args 里有 --successor-pid=<pid>？            ← 只在「重启客户端」这条路径出现（§13）
     等该进程退出（退出即释放 mutex），最多 15 s
3. 只读探测：OpenMutexW(instance) 成功？                  ← 副作用为零，不解锁不创建
     是 → 该实例是 --silent 吗？
           ├─ 是（来自计划任务）→ 静默退出 0（用户正在用，别抢前台）
           └─ 否 → OpenEventW + SetEvent → 退出 0        ← 不来第二份，不弹 UAC
     否 → 继续
4. 需要提权？(app.elevate=ask 且 isElevated()==false)
     是 → ShellExecuteExW("runas") 重启自己 → 退出 0     ← 此时**尚未持有** mutex；
                                                            交接参数剥掉（已交过一次）
     用户拒绝 UAC → 记 WARN 到 startup.log，继续往下（普通权限）
5. CreateMutexW(instance)
     ERROR_ALREADY_EXISTS → 与步骤 3 相同处理（并发竞态的兜底）
     否则持有到进程结束
6. CreateEventW(activate) + 起等待线程
7. autostart 对账（只读；`07` §3.6）
8. application { 窗口 / 托盘 / 后端 }
```

| 为什么是这个顺序 | 不这么做会怎样 |
|---|---|
| **3 用只读探测，而不是直接 `CreateMutex`** | 直接创建的话，若当前进程随后要 `runas` 重启自己，旧进程仍持有 mutex → 提权后的新进程看到 `ALREADY_EXISTS` → 去唤醒那个正要退出的旧进程 → **活锁** |
| **单实例判断在提权判断之前** | 否则用户双击时先被 UAC 拦一道，点完"是"才被告知"已经有一份在跑" |
| **1 在 3 之前** | 配置坏时要报"配置错误"（真问题）而不是"已有一份"（误导），所以第二份也会解析一遍配置（毫秒级）；顺带也让 §13 的交接按解析后的 home 工作 |
| **2 在 3 之前** | 「重启客户端」时旧进程还持锁（它要确认新进程活着才退），不等就必然自杀 → **程序消失**（§13） |
| **5 的 `ALREADY_EXISTS` 仍要处理** | 只读探测与正式创建之间有窗口期，两个进程可能同时通过步骤 3 |
| **事件在 6 创建** | 它是给**后来的**实例用的；自己创建后不需要自唤醒 |

## 6. 唤醒语义与权限

| 第一实例 | 第二实例 | 结果 |
|---|---|---|
| 普通 | 普通 | ✅ 唤醒 |
| 普通 | elevated | ✅ 唤醒（高完整性写低完整性对象允许） |
| elevated | elevated | ✅ 唤醒 |
| elevated | 普通 | ⚠️ 取决于对象完整性标签（见坑 3），失败则**只提示不唤醒** |

失败时的降级文案：「已有一份 Hermes 正在以管理员身份运行，请从托盘打开」。**不能静默退出**，
否则用户依然不知道发生了什么（S3 的底线是"有明确反馈"）。

## 7. 早期日志 `startup.log`

### 7.1 为什么必须有

实测（2026-10-29）：把 `config.json` 写成 `{ this is broken json`，用 `--silent` 启动后

```
进程：0 个
data/logs 下 8 个文件：长度一字节未变
home 根：没有任何痕迹文件
```

因为 `ConfigLoader` 抛 `ConfigError` → `showFatal(silent=true)` 只做 `System.err.println` 就退出，
而 `javaw` 没有控制台 —— 这一行直接丢进 null。在"登录自启"场景下这意味着
**用户看不到窗口、我们也查不到原因**。

### 7.2 规格

| 项 | 值 |
|---|---|
| 路径 | `<home>/logs/startup.log`（`<home>` 由 `-Dhdc.home` 或 exe 位置确定，不依赖配置） |
| 写入方式 | `Files.writeString(..., CREATE, APPEND)`，UTF-8，**完全不经过 logback**（此时它还没初始化） |
| 截断 | 启动时若文件 > 256 KB → 覆写为一行 `--- startup.log rotated at <time> ---` |
| 不轮转 | 一次启动十几行；按天/按大小轮转反而让"最早那几行"更难找 |

每次启动至少写这些行：

```
2026-10-29T11:02:13.481Z  INFO   start            pid=27436 elevated=false silent=true
2026-10-29T11:02:13.482Z  INFO   args             -Dhdc.home=D:\Hermes --silent
2026-10-29T11:02:13.483Z  INFO   cwd              C:\Windows\System32
2026-10-29T11:02:13.484Z  INFO   home             D:\Hermes
2026-10-29T11:02:13.590Z  INFO   instance         acquired name=HermesCompose-a1b2c3d4
2026-10-29T11:02:13.601Z  INFO   config           ok mode=local log=INFO
2026-10-29T11:02:13.602Z  INFO   autostart        task=HermesCompose-a1b2c3d4 state=ENABLED
2026-10-29T11:02:15.870Z  INFO   ui               window shown
```

失败场景写 `ERROR` 并带完整原因；`cwd` 这一行是刻意留的（elevated + 计划任务下最常见的问题是相对路径）。

配置解析成功后 logback 接管细节日志，`startup.log` 只在**关键节点**再追加（窗口显示、退出码），
不重复 logback 的内容。

## 8. 坑（现象 / 原因 / 应对）

| # | 现象 | 原因 | 应对 |
|---|---|---|---|
| 1 | 提权实例与非提权实例互相"看不见" | 用了 `Global\` 命名空间，普通用户没有 `SeCreateGlobalPrivilege` | 一律 `Local\` |
| 2 | 开启提权后启动变成死循环 / 提权后再启动会唤醒旧进程 | mutex 在 `runas` 之前创建，旧进程持锁退出中被新进程当成"已有实例" | 步骤 1 只做**只读探测**，`CreateMutex` 放到提权判断之后（§5） |
| 3 | 普通实例唤醒 elevated 实例时 `SetEvent` 报 `ERROR_ACCESS_DENIED` | 强制完整性控制（MIC）默认 no-write-up：对象完整性标签高于调用者就不能写 | 创建事件时显式把 SACL 完整性标签设为 **Medium**（`SetSecurityInfo(LABEL_SECURITY_INFORMATION)`）；做不到就降级为提示（§6）。**待实测**（T6） |
| 4 | 强杀后下次启动说"已有一份在运行" | 用了锁文件/PID 文件 | 用内核对象，句柄随进程回收（S4） |
| 5 | 计划任务触发时把用户正在用的窗口抢到前台 | `--silent` 触发也走了唤醒分支 | `--silent` 的第二实例**静默退出**，不唤醒（§5 步骤 1） |
| 6 | 两份便携包只有一份能起 | 名字没用 home 哈希（或哈希没规范化路径） | `sha256(File.getCanonicalFile().path)` 前 8 位 |
| 7 | 大小写不同的同一路径被当成两份安装 | 未规范化 | 同上，必须 `getCanonicalFile()` |
| 8 | 旧版本客户端（没有事件对象）与新版本混跑时，新版本唤醒失败 | `OpenEvent` 返回 null | 降级为"提示 + 退出"，不阻塞（旧版本本来也没有唤醒能力） |

### 12.4 跨权限唤醒的实测结论（T6）

P1 落地后补测：**提权实例创建的事件对象，普通权限实例可以直接 `OpenEventW` + `SetEvent`**。

```
提权实例（elevated，pid 40320）在跑
→ 启动一份普通实例（elevate=never）
→ 普通实例日志：already running; activate=true
→ 提权实例日志：activate request #1 -> window shown
```

所以 `08` §8 坑 3 的担心在本机不成立：**不需要**给事件对象显式设 Medium 完整性标签（SACL），
默认 DACL/IL 就允许同用户跨完整性级别写。反向（elevated 唤醒 medium）本来就允许（no-read-up 只挡读，
写方向是高→低）。`SingleInstance` 因此保持现在的简单实现，没有引入 `SetSecurityInfo`。

## 13. 强制单实例 + 重启交接（2026-10-29）

### 13.1 为什么去掉开关

`app.single_instance` 是"从没实现过的键"，实现时照抄了默认值 `true`。现在定死：

| 理由 | 说明 |
|---|---|
| 关掉它没有任何正当用途 | 两个实例 = 两套 cron + 同一个 `state.db` 两个写者 + 两份 logback 轮转（§2 全部条目） |
| 它是**故障开关**，不是偏好 | 用户点它只会得到"看起来能用、实际互相踩"的状态，排查成本极高 |
| 多开的正当需求是**换 `<home>`** | 单实例本来就按 `<home>` 哈希隔离（§4）—— 想跑两份不同 profile，复制一份便携包即可，不需要关开关 |

移除范围：`AppSection.singleInstance` 字段、设置页字段、`DEFAULT_CONFIG_TEMPLATE` 与
`packaging/config/config.json` 里的键。`Main.kt` 里 `if (singleInstanceEnabled)` 分支全部去掉，
`instance` 从可空变为非空。

**老配置兼容**：`ConfigAssembler.RETIRED_KEYS` 把 `app.single_instance` 列为"已废弃"，
残留时输出 `已废弃的配置键: app.single_instance（桌面端强制单实例，已不可关闭，见 08 篇 §13；config.json）`，
而不是混进"未知配置键（拼错了？）"。`HDC_APP_SINGLE_INSTANCE` 同理不再报"未知环境变量"。

### 13.2 强制之后立刻暴露的问题：重启会自杀

「重启客户端」的实现是**旧进程还活着**的时候拉起新进程 —— 它必须确认新进程真的起来了
（`waitFor(2500ms)` + `isAlive`）才能关自己的窗口。这段窗口里：

```text
旧进程：持有 Local\...-instance  ──spawn──▶ 新进程
                                            └─ 探测：mutex 存在 → 「已有一份在跑」
                                               → requestActivate（唤醒旧进程，无意义）
                                               → 退出 0
旧进程：2.5 s 后确认新进程"活着" → 认为重启成功 → 退出
结果：两个都没了 —— 用户看到的是「点了重启，程序消失」
```

这个 bug 在单实例落地时就存在了（重启按钮比单实例先提交），只是没人在单实例之后点过重启。
开关一去掉就没有退路，必须一起修。

### 13.3 交接协议：`--successor-pid=`

```text
旧进程 restart()：
  1. 后端 shutdown()
  2. 命令行剥掉 --silent / --tray / 残留的 --successor-pid
  3. 追加 --successor-pid=<旧进程 pid>，拉起新进程
  4. 等 2.5 s 确认新进程活着 → 返回 true → 上层退出（退出即释放 mutex）

新进程 main()：
  步骤 2 解析 --successor-pid → awaitExit(pid, 15 s, 100 ms 轮询)
    进程不在 / PID 非法 / 等于自己 → 立即返回 true
    15 s 还没退 → WARN 到 startup.log，然后照常走「已有实例」分支
```

| 设计点 | 理由 |
|---|---|
| 用 PID 而不是"交接文件/事件" | 无残留状态可清理；PID 失效就是"已退出"，天然幂等 |
| 只在这条路径上出现 | 用户双击、计划任务、`App.bat` 都没有这个参数，正常启动零开销 |
| 提权重启前**剥掉** | 那条路径上旧进程从未持有 mutex，不需要等；万一 PID 被复用，白等 15 s 还会误判成"已有实例" |
| 重启用 `strip` 再追加 | 重复重启不累积；`RestartSupport.DEV_MODE` 下也安全 |
| 超时 15 s | 覆盖旧进程 `waitFor(2.5 s)` + 关窗 + JVM 退出；超时后降级为正常单实例语义（"已有一份在运行"），不会卡死 |
