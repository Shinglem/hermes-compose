# 15 · 关停安全规格：绝不能影响机器上的其他 Hermes

> 背景：同一台机器上已经有另一个 Hermes（本机 9119 dashboard / 8642 OpenAI API）。
> 客户端内置的 payload 必须做到「只停自己」，且**在任何异常路径下都不误伤**。
> 依据：`hermes_cli/dashboard_procs.py`、`main_dashboard.py`、`main.py` 的 `--status/--stop` 实现 + 实测。

---

## 1 先看清 `serve --stop` 到底怎么选目标

```python
pids = _scan_dashboard_processes(exclude_pids=…)          # ① 扫进程表拿 (pid, cmdline)
ancestors = _caller_ancestor_pids()                       # ② 排除自己和祖先进程
pids = _pids_owned_by_hermes_home(pids, scope_home=…)     # ③ 只留 home 匹配的
```

三道闸，**每一道的失败方向都是「不停」，不是「误停」**：

| 闸 | 机制 | 失败时的行为 |
|---|---|---|
| ① 匹配 | canonical token matcher（不是 argv 子串，避免 `herdr --session hermes server` 被误杀，#121156）；另用 spawn-ledger 补漏 | 读不到命令行 → **扫不到** → 不停 |
| ③ home | 读目标进程的 **exec-time env**（psutil），回放 `_apply_profile_override`；破坏性调用要求 `require_launch_identity` | 环境不可读（别的用户 / 加固） → **spare** → 不停 |

实测印证：本机那个 9119 的 `python.exe`（pid 16020）命令行对普通权限**不可读**，
不带 `HERMES_HOME` 的 `serve --status` 返回 `No hermes dashboard or serve processes running.` ——
它既没被列出，也不会被 `--stop` 命中。

### 那还有没有误伤的可能？

有，只有一个场景：**两个实例的 `HERMES_HOME` 相同**。此时 ③ 不区分，会把「同一个 home 的所有后端」一起停。
这正是必须用铁律把它挡在启动之前的原因。

---

## 2 铁律

### R1 `HERMES_HOME` 必须是我们独占的私有目录，且启动前校验

```text
HERMES_HOME 必须是绝对路径
且必须位于客户端自己的 userData 下（例如 <userData>\hermes-home）
且不得等于 %USERPROFILE%\.hermes、%APPDATA%\hermes、或任何既有安装的 home
且目录内必须存在我们写入的归属标记（如 .hermes-payload-owner，内容=payload 绝对路径的 hash）
```

标记文件让「误把用户 home 当自己的」在启动阶段就失败，而不是在关停阶段才发现。

### R2 首选：用 Job Object 物理隔离，不靠扫描

客户端把 `serve`/`dashboard` 起在自己的 Job 里：

```text
CreateJobObject + SetInformationJobObject(JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE)
CreateProcess(CREATE_SUSPENDED) → AssignProcessToJobObject(job, child) → ResumeThread
```

- 关停 = `TerminateJobObject(job)`：作用是**内核句柄**，物理上不可能波及 Job 外的进程
- 客户端崩溃/被强杀时，系统连带回收整棵子进程树 → 不留孤儿，也不需要拿 PID 去猜
- 这条路径**完全不依赖** `HERMES_HOME` 扫描，是「绝对不能影响别人」的最强保证

关停顺序建议：`serve --stop`（优雅，10 s 超时）→ 仍是我们的子进程 → `TerminateJobObject`（兜底）。

> **已落地（2026-10-29）**：`WindowsJobObject` + `BackendProcessJob`（`core/backend/`）。
> 只做 `KILL_ON_JOB_CLOSE`，不调 `TerminateJobObject` —— 正常关停仍走上表的句柄销毁，
> Job 负责「客户端非正常消失」这一种情形。**不需要 JNA**：项目字节码目标是 25，
> `java.lang.foreign` 是正式 API（实测 `Linker.defaultLookup()` 在 Windows 上找不到
> `kernel32` 的导出，必须 `SymbolLookup.libraryLookup("kernel32", Arena.global())`）。

### R3 若用 `--stop`，必须三证齐备

```powershell
# 1) 显式私有 home（禁止默认/继承）
$env:HERMES_HOME = '<userData>\hermes-home'

# 2) 先拿白名单（只读）
$status = & "$payload\bin\hermes-agent.exe" serve --status

# 3) 白名单里每条命令行都必须指回本 payload，否则整体中止
#    合法行形如： PID 1234 [serve]: <payload>\bin\hermes.exe serve --port 9120
#    任何一行不含 <payload>\bin\hermes  →  不要执行 --stop，记录并报警
```

伪代码：

```text
if HERMES_HOME is unset or equals a known foreign home:        abort
lines = parse(status_output)
if any(line.cmdline does not startswith(payload_bin_dir)):      abort   # 有异常目标，整体不动
serve --stop                                                    # 只停已核对过的这批
if exit_code != 0:                                              fall back to TerminateJobObject
```

### R4 端口被占：换端口，不杀进程

启动前探 `127.0.0.1:<port>`，被占就顺延到下一个候选端口（或 `--port 0` 让 OS 分配，
从 `HERMES_BACKEND_READY port=N` 哨兵读回实际端口）。**永远不要**为了腾端口去杀 listener。

### R5 禁止清单（写进 code review checklist）

| 禁止 | 原因 |
|---|---|
| `taskkill /IM hermes.exe`、`taskkill /F /IM python.exe` | 名字匹配会扫到别人的安装 |
| `Stop-Process -Name …`、按进程名遍历 | 同上 |
| 在未设 `HERMES_HOME` 的 shell 里跑 `serve --stop` / `dashboard --stop` | 作用域会退化成默认 home |
| 用默认 home（`~/.hermes`）启动后再 `--stop` | 与用户既有安装同 home → 一起停 |
| `POST /api/gateway/restart` 当关停用 | 它重启的是**消息平台网关**，且会 spawn 新进程 |
| 依赖「PID 从某处读到」直接 `TerminateProcess` | 进程已退出时 PID 会被复用，可能杀到无关进程 |

## 3 落地状态（客户端已实现，2026-10-28）

R1–R5 已按下面的方式实现（见 `composeApp/src/commonMain/kotlin/dev/shinglem/hermes/core/backend/`）：

| 规格 | 实现 |
|---|---|
| R1 私有 home + 归属标记 | `LocalBackendPlanner.classifyHome()` 拒绝相对路径 / `~/.hermes` 等外来 home / payload 内部路径；`LocalBackendProvider.start()` 写 `<home>/.hermes-portable-owner`（内容 = payload 路径），已存在且不一致则拒绝启动 |
| R2 物理隔离 | 两层：① 正常关停只对 `ProcessBuilder` 句柄 `descendants().destroy()` → 3s → `destroyForcibly()`；② **Job Object 兜底**（2026-10-29 落地）：`WindowsJobObject` 用 FFM 调 `CreateJobObjectW` + `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`，后端子进程启动后立刻 `AssignProcessToJobObject`，客户端被强杀/崩溃时内核杀光 Job 内进程 |
| R3 `--stop` 三证 | **不使用** `--stop`（已由 R2 覆盖，更强） |
| R4 端口被占换端口 | 启动参数固定 `--port 0`（OS 分配），端口从 ready 文件 / `HERMES_(BACKEND|DASHBOARD)_READY port=N` 哨兵读回；收到 `BACKEND_PORT_IN_USE` 直接判失败，绝不杀 listener |
| R5 禁止清单 | 代码里没有 `taskkill`、没有按名字查找、没有 PID 复用风险（句柄由 OS 持有；Job 成员资格只来自我们自己 spawn 的进程） |

**为什么必须自己兜 Job Object**（实测，2026-10-29）：payload 自带的 parent-death watchdog
（`hermes_cli/web_server_lifecycle.py::_start_parent_death_watchdog` → `_is_serve_orphaned`）
在 Windows 上**不会触发**。我们该传的 env 全都正确传到了后端进程（用 psutil 读后端子进程的
`HERMES_PARENT_PID` / `_START_MARKER` / `_NONCE` 三项确认），问题在它只比较**进程创建时间**：

| 步骤 | 实测结果 |
|---|---|
| 强杀客户端 46 s 后 | `serve` + `dashboard` 仍在跑 |
| `psutil.pid_exists(父PID)` | `False`（进程确实没了） |
| `_process_start_marker(父PID)` | 仍返回 `win:639288015913679532`（Windows 上进程对象未销毁时还能读到原创建时间） |
| 与期望 marker 比较 | **完全相等** → `_is_serve_orphaned` 返回 `False` → watchdog 认为父进程健在 |

它拿不到"进程已退出"这个事实，只看"创建时间对不对"。所以孤儿只能由客户端兜：
Job Object 生效后同样的强杀实验，**1 秒内**后端清零。

尚未落地的项：规格 §3 的第 5 项（端口冲突演练）尚未写成自动化测试；
Job Object 的 3 条行为（关闭句柄杀进程 / 孙进程一起清 / Job 外进程不受影响）已有单测
（`WindowsJobObjectTest`）。
