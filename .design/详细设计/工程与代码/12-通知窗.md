# 12 · 通知窗（自绘 + Windows 原生）

> **回答"怎么做"**：应用内通知窗与 Windows 原生 toast 的实现、取舍，以及**为什么默认不建开始菜单快捷方式**。
> 相关：`AGENTS.md` 硬约束 8（不引 WebView 的边界）、[`10-Windows触屏输入.md`](10-Windows触屏输入.md)（运行时基线）。

---

## §0 两条通路

| 通路 | 何时用 | 开始菜单 | 通知中心留存 | 按钮 |
|---|---|---|---|---|
| **应用内自绘窗**（`NotificationOverlay`，M3 卡片） | 默认 | 无痕迹 | ❌ | ✅ |
| **Windows 原生 toast**（`nucleus.notification-windows`） | 用户在设置里打开开关 | 需要一个 `.lnk` | ✅ | ✅ |

纯提示（一轮完成等，没有按钮）仍走**托盘气泡**：进通知中心、不挡屏幕，两条通路都不需要它。

## §1 AUMID 与开始菜单：四组实测（2026-11-04）

Windows 的 AUMID 归属**只认开始菜单里的 `.lnk`**（其 `PKEY_AppUserModel_ID` 属性）。
本机实测（同一份代码、同一 AUMID 变量）：

| # | 快捷方式位置 | `HKCU\...\AppUserModelId` 键 | 结果 |
|---|---|---|---|
| 1 | 用户级开始菜单 | 有 | ✅ toast 出现、按钮回调 `onActivated(once)` |
| 2 | 桌面 | 有（AUMID 写在 .lnk 里） | ❌ 无 toast、无事件 |
| 3 | 无 | 有 | ⚠️ 看似成功 —— **假象** |
| 4 | 无 | 无（全新 AUMID） | ❌ 无 toast、30 秒内连 `onDismissed` 都没有 |

**第 3 组是坑**：AUMID 一旦通过 `.lnk` 注册过一次，Windows 会记住（shell 通知缓存），
把 `.lnk` 和注册表键都删掉后仍能工作一阵。换全新 AUMID（第 4 组）才暴露真相 ——
**排障时必须用没注册过的 AUMID**，否则会被缓存骗。

排除掉的替代方案：

| 方式 | 为什么不行 |
|---|---|
| `HKCU\Software\Classes\AppUserModelId\<id>` | 只负责显示名/图标/设置页可见性，不建立映射 |
| 桌面 / 程序目录的 `.lnk` | shell 只扫开始菜单（用户级 + 公共） |
| `App Paths` 注册表项 | 与 AUMID 无关 |
| COM activator（`INotificationActivationCallback`） | 解决"应用未运行时点按钮如何拉起"，不替代 `.lnk` |
| 进程内 `SetCurrentProcessExplicitAppUserModelID` | 必需但不充分 |

**藏不住**：`.lnk` 设 `Hidden`、放进 `Programs\.hermes\` 且目录设 `Hidden+System`，
`shell:AppsFolder`（开始菜单"所有应用"的数据源）**照样列出**。唯一不出现在"所有应用"的位置是
`Programs\Startup`，但那等于强制开机自启，不可接受。

## §2 多实例共存

快捷方式文件名与 AUMID 都带 `<home>` 哈希（与单实例互斥量同一套算法：`SHA-256(canonicalPath)` 前 4 字节）：

```
AUMID            Shinglem.HermesDesktop.<hash>
快捷方式          %APPDATA%\Microsoft\Windows\Start Menu\Programs\<产品名> (<hash>).lnk
```

两份便携包各自有独立的通知身份，互不覆盖；同一份包的目录移动后 `<home>` 变了、哈希也变，
于是会生成**新的** `.lnk`（旧的那条留在原地，需要时可手工删）。

### 已存在就不重建（2026-11-05 起：按"是否已有指向本程序的快捷方式"判）

老逻辑只看**文件名**（`<产品名> (<hash>).lnk`），于是这些情况都会再建一个：
用户自己建过指向同一 exe 的快捷方式、旧版本用固定名建过、便携包换了目录（`<hash>` 变了）。
现在改成"先看有没有指向本程序的快捷方式"，判定抽成纯函数 `planShortcut(...)`
（`platform/ShortcutScan.kt`）：

| 次序 | 条件 | 结果 | 日志 `reason=` |
|---|---|---|---|
| 1 | 自己那个名字的 `.lnk` 还在 | 沿用（不扫描、零 IO） | `filename` |
| 2 | 扫描失败（目录读不了 / 权限） | 退回老行为：新建 | `created`（`note=scan-failed`） |
| 3 | `Programs\` 下有直接子项、target == 当前 exe、且**带** AUMID | 复用它的名字与 AUMID | `target` |
| 4 | 直接子项、target 命中、但**不带** AUMID | 把 AUMID **补写进该 `.lnk`**（见下），成功后复用；补写失败才新建 | `target` / `patching-failed` |
| 5 | 只有嵌套子目录里的命中 | 没法可靠复用（库自己拼 `Programs\<appName>.lnk`）→ 新建 | `created`（`note=nested`） |
| 6 | 一条都没命中 | 新建 | `created` |

- **扫描只在第 1 步不满足时做一次**，启动路径上没有额外开销；成品通常命中第 1 步。
- **读 `.lnk` 不引 COM**：`pointsTo()` 把字节按 `Latin1` / `UTF-16LE`（奇偶两种对齐）各解一次，
  大小写不敏感 `contains` 当前 exe 路径；`ShortcutParser` 再按 MS-SHLLINK 取 LinkInfo 的
  `LocalBasePath`（优先 unicode）与 property store 里的 `PKEY_AppUserModel_ID`
  （`{9F4C2855-…}` / pid 5）。
  本机实测：`Hermes Desktop Compose (fb97bfde).lnk` → `Shinglem.HermesDesktop.fb97bfde`、
  `飞书.lnk` → `com.electron.Feishu`、`Visual Studio Code.lnk` → `Microsoft.VisualStudioCode.Portable`。
- 复用的语义只能是"同一个名字 + `REQUIRE_NO_CREATE`"，或"读它的 AUMID 后按那个 AUMID 初始化" ——
  `WindowsNotificationCenter.initialize(aumid, appName, policy)` **没有"指定已有路径"的参数**。
- **复用的用户快捷方式不删**：关掉开关时只删我们自己建的（`shortcutOwned`），
  外来的 AUMID 也不重写它的注册键（免得覆盖用户配的 DisplayName / IconUri）。
- ⚠️ `REQUIRE_NO_CREATE` 在文件**缺失时也返回 `true`**（它只表示"不创建"），所以可用性
  仍由自己查 `isFile` 判定，不能拿 `initialize` 的返回值当"快捷方式可用"。

#### 补写 AUMID：PowerShell + COM（2026-11-06 定案）

"指向本程序但没 AUMID"的 `.lnk`（典型就是用户自己建的 `Hermes.lnk`）**不能直接用于 toast**。
处置是**把 `PKEY_AppUserModel_ID` 写进这个已有文件**（保留它的文件名 / 图标 / 参数），再按它复用，
**不新建第二个入口**。实现见 `platform/ShortcutAumidWriter.kt`：

- 子进程：`%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe -NoProfile -NonInteractive
  -ExecutionPolicy Bypass -EncodedCommand <base64(UTF-16LE 脚本)>`（不依赖 `pwsh`）。
- 脚本里 `Add-Type -Language CSharp` 编译内嵌的 COM 互操作：`ShellLink` coclass →
  `IPersistFile::Load(path, STGM_READWRITE)` → `IPropertyStore::SetValue/Commit` → **`IPersistFile::Save`**。
- **两个实测坑**：① 只 `Commit()` **不落盘**，必须 `Save(path, true)`；② 写完后用同一个 COM 对象
  读回是空的（属性存储缓存）→ 校验改成**重新读文件字节**（与判定同一套 `parseShortcut`）。
- 写前备份 `<name>.lnk.bak`；10 s 超时强杀；采集 exit code + stderr。
- **不进启动关键路径**：实测 2.0–2.6 s/次（含 `Add-Type` 编译）。`sync()` 先落 `ready=false`
  （通知回退自绘窗），在 `Dispatchers.IO` 后台跑，`syncGeneration` 保证过期的结果被丢弃；
  成功一次后字节里已有 AUMID，后续启动走第 3 步、**不再起进程**。
- 失败（只读 / 策略禁用 / 超时）→ 退回新建带 AUMID 的条目（`reason=patching-failed`），
  日志与设置页都写明原因，**不能因此不发通知**。

实测（2026-11-05，判定与解析）：

| 场景 | 结果 |
|---|---|
| 本机已有 `Hermes Desktop Compose (fb97bfde).lnk`，走真实 `sync(true)` | `ready=true`、mtime 前后一致、开始菜单无新增（`reason=filename`） |
| 把它改名成 `我的 Hermes.lnk`（模拟用户自建），换一个 home 再 `sync(true)` | 复用该条（`shortcutPath=…\我的 Hermes.lnk`）、无新增（`reason=target`） |
| 扫描 78 个真实 `.lnk` | 两条指向本程序的都识别（带 AUMID 的那条被优先选中） |
| `Hermes.lnk`（无 AUMID）补写 AUMID，`pwsh 7` 与 `powershell.exe 5.1` 各一遍 | 写入成功、target 保留、文件 1040 B → 1131 B |

### `.lnk` 的 target 是动态取的

库用 `GetModuleFileNameW` 取**当前进程的 exe**（dll 里没有任何 `java.exe` 字面量），实测：

| 启动方式 | `.lnk` TargetPath |
|---|---|
| 打包版 `hermes-desktop-compose.exe` | `…\app\hermes-desktop-compose\hermes-desktop-compose.exe` |
| 开发态 `gradle run` | `C:\envir\java\version\jdk-27\bin\java.exe`（宿主就是它） |

所以成品指向自己的 exe、开发态指向跑它的那个 JDK，**没有写死路径**。开发态那条 `Arguments`
是空的（从开始菜单点只会起一个裸 `java`），但 toast 不受影响 —— AUMID 归属来自 `.lnk` 的
属性而不是 target。

## §2.5 任务栏图标（必须注册 IconUri）

`WindowsNotificationCenter.initialize` 内部会调 `SetCurrentProcessExplicitAppUserModelID`，
**进程的 AUMID 一变，Windows 就按新 AUMID 去找任务栏 / 通知图标** —— 没注册时退回宿主进程
（`java.exe`）的咖啡杯。实测：打开开关前任务栏是应用图标，打开后变成 JVM 图标。

修法（`registerAumid`）：

```
HKCU\Software\Classes\AppUserModelId\Shinglem.HermesDesktop.<id>
    DisplayName     = Hermes Desktop Compose (<id>)
    IconUri         = %LOCALAPPDATA%\hermes-compose\app-icon.ico
    ShowInSettings  = 1
```

- `app-icon.ico` 从 `desktopMain/resources` 解压（开发态没有 exe 可指，成品也一样用这份）。
- 写注册表用 `reg.exe`（一次启动 3 次调用，各 ~30ms）：FFM 调 `RegCreateKeyExW` 那条路在本机
  静默失败了，`reg.exe` 更省事；只在"开关打开"的启动路径上执行。
- 关掉开关时把这条键连同开始菜单 `.lnk` 一起删掉。
- 任务栏图标有缓存：改完要重启应用；必要时重启 explorer 才刷新。

### §2.6 还要把进程 AUMID 清回默认

`initialize` 改的是**进程级** AUMID，而任务栏按 AUMID 分组 —— 于是同一个应用会变成
"固定项 + 运行窗口"两个按钮（实测 2026-11-04，两个都叫 Hermes）。toast 是
`CreateToastNotifier(aumid)` 显式指定身份发出的，**不依赖进程这个值**，所以
`initialize` 之后立刻清掉（`ProcessAumid.clear()`，桌面端 FFM 调 shell32）：

```
SetCurrentProcessExplicitAppUserModelID("")   // rc=0
SetCurrentProcessExplicitAppUserModelID(NULL) // ✗ 返回 E_INVALIDARG (0x80070057)
```

清空后进程回到"按 exe 分组"，任务栏恢复单按钮；toast 与按钮回调实测仍正常
（探针：`initialize ok=true` → `clear rc=0` → toast 照常弹出并带按钮）。

> 开发态（`:composeApp:run`，宿主是 `java.exe`）与已固定的打包版 exe **本来就是两个程序**，
> 那种情况下出现两个按钮与 AUMID 无关 —— 对照：开关关闭时同样是两个。

### §2.7 自绘窗：多条并存（队列 + 最多 3 条堆叠）

**曾经的 bug（#16）**：`NotificationInbox` 是单槽（`MutableStateFlow<NotificationRequest?>`），
`post()` 直接覆盖，`NotificationOverlay` 只订阅一条。同一会话连来多个审批时，后一条顶掉前一条 ——
前一条既没被看见、`ReminderGate` 又已经记过 id，于是永远不再提醒，表现为"只通知一个"。

**现在**：

| 位置 | 行为 |
|---|---|
| `NotificationInbox`（common） | 有序队列：`queue`（全部）+ `active`（前 `MAX_VISIBLE = 3` 条）。同一 `id` 重复投递忽略 |
| `NotificationOverlay`（desktop） | 每条一个独立 `Window`，右下角**纵向堆叠**，最新的一条贴底（与 Windows 通知中心一致）；按卡片高度累计计算 y，上面那条收起后下面的自动上移 |
| 自动收起 | 每条自己的 `LaunchedEffect(request.id) + delay(autoDismissMs)`，互不干扰 |
| 关闭 / 点按钮 | `dismiss(id)` 只移除那一条；排队中的自动补位 |

队列语义（`NotificationInboxTest` 钉住 9 条）：3 条能同时显示、5 条时先显示 3 条、
关掉 1 条后第 4 条补位、只移除对应那条、重复 id 忽略、`dismissAll` 清空。

**为什么是 3 条**：审批卡片 152dp + 阴影留白约 176dp，3 条约 528dp；再多会糊住整个右下角，
而且用户也分不清该先看哪个。超过 3 条的排队而不是丢弃。

## §3 开关与回退

`state.json` 的 `ui.nativeNotifications`（**缺省关** = 自绘窗）—— 只存"打开"这一侧，
没打开过的用户机器上零系统痕迹。

```
设置里打开 → SettingsViewModel.setNativeNotifications(true)
              └─ NativeNotifications.sync(true)
                   ├─ 自己那个名字的 .lnk 在？REQUIRE_NO_CREATE（不重建）
                   ├─ 不在 → 扫开始菜单找"指向本程序的 .lnk"（planShortcut）
                   │    ├─ 命中且带 AUMID → 用它（REQUIRE_NO_CREATE，复用）
                   │    └─ 否则 → REQUIRE_CREATE（创建）
                   └─ 检测该名字的 .lnk 是否存在 → status
通知触发   → SystemNotifications.show(...)
              ├─ NativeNotifications.show(...) 成功 → 原生 toast
              └─ 失败（未启用 / 快捷方式被删 / 库不可用）→ NotificationInbox → 自绘窗
```

`NativeNotificationStatus` 三个字段分工：`requested`（用户想不想要）、`ready`（真能用）、
`message`（不可用原因）。设置页在 `degraded` 时用 `error` 色显示原因 ——
**不能因为快捷方式被删就静默变成"没有通知"**。

## §4 依赖与体积

```toml
nucleus = "2.5.18"
nucleus-notification-windows = { module = "dev.nucleusframework:nucleus.notification-windows", version.ref = "nucleus" }
```

- MIT；Maven Central（`repo1.maven.org`，核对 2026-11-04）。
- 传递依赖只有 `kotlin-stdlib` + `nucleus.core-runtime`（后者也只依赖 stdlib）——**不拖整个 Nucleus 框架**。
- native 库打在 jar 里（`nucleus/native/win32-x64/nucleus_notification_windows.dll`，210 KB），
  由 `core-runtime` 的 `NativeLibraryLoader` 解压加载 → 现有的 `lib/*.jar` 打包机制直接可用。
- 需要 `--enable-native-access=ALL-UNNAMED`（`packaging/jvm.args` 已有）。
- ⚠️ **`nativeDistributions` 必须显式声明 `modules(...)`**：compose 插件默认只按 jdeps 静态
  分析带 7 个模块，产物一启动就 `NoClassDefFoundError: javax/naming/NamingException`（实测
  2026-11-04）。已在 `build.gradle.kts` 里传 `modules(*runtimeModules.toTypedArray())`，
  与 `rt/` 用同一套列表。正式绿色版走 `jlinkReleaseRuntime` → `rt/`，本来就有 `java.naming`，
  所以这个坑只在 `createDistributable` / MSI 上暴露。
- 线程：库自带专用 MTA 线程发 WinRT 调用；`onActivated` 从 COM RPC 线程回来，
  `NativeNotifications` 用 `Dispatchers.Main.immediate` 切回去再执行动作（改 Compose 状态 / 发 RPC）。

## §5 已知限制

| 限制 | 说明 |
|---|---|
| 用户删掉开始菜单快捷方式 | 运行中删掉后 nucleus 的 `show` 会**静默失败**（实测：`callback` 无错、toast 不出现、`.lnk` 也不重建），所以 `show` 自己先查一次快捷方式在不在，不在就置 `ready=false` + 回退自绘窗并在设置页给出原因；重新打开开关会重建（`REQUIRE_CREATE`） |
| 应用未运行时点按钮 | 没有注册 COM activator，Windows 会启动 exe（带 arguments），单实例把它退掉 → 动作丢失。托盘常驻场景可接受 |
| 全屏独占 | 自绘窗可能不置顶；原生 toast 由系统决定 |
| `tag` / `group` | WinRT 限制各 16 字符，固定 `hermes` / `approval` |
| 开发态任务栏两个按钮 | `gradle run` 的宿主是 `java.exe`，与已固定的打包版 exe 是两个不同程序；成品单 exe 运行时按 §2.6 清空进程 AUMID 后只有一个 |

## §6 验收

| # | 判据 | 怎么验 |
|---|---|---|
| N1 | 默认（开关关）不创建任何开始菜单条目 | 全新 home 启动 → `shell:AppsFolder` 里没有该应用 |
| N2 | 打开开关后创建 `.lnk` 且状态为"开启" | 设置页状态行显示完整路径 |
| N3 | 原生 toast 带按钮，点击就地处理 | 触发审批 → 点「允许一次」→ agent 继续 |
| N4 | 关掉开关后回退自绘窗 | 触发审批 → 应用内 M3 卡片 |
| N5 | 快捷方式被删后不静默失效 | **运行中**删 `.lnk` → 再触发 → 回退自绘窗 + 设页显示原因（探针实测：nucleus 在缺 `.lnk` 时静默失败，故 `show` 前置自查）|
| N6 | 两份便携包并存 | 两个不同 home 各开一次 → 开始菜单两条、互不覆盖 |
| N7 | 已有指向本程序的快捷方式时不新建 | 删掉自己那条、留一条用户自建的（带 AUMID）→ 打开开关 → 开始菜单无新增，日志 `reused=<名字> reason=target`（2026-11-05 实测通过） |
| N7b | 用户自建的 `.lnk` **无 AUMID** 时补写后再复用 | 只留 `Hermes.lnk`（无 AUMID）→ 打开开关 → 不新建、文件里出现 AUMID、有 `.lnk.bak`、toast 正常（`reason=target`，日志带 `patched`）；同一目录再重启一次 → 不再起 PowerShell |
| N7c | 补写失败要退新建而不是不发通知 | `Hermes.lnk` 设只读 → 打开开关 → 新建带 AUMID 的条目（`reason=patching-failed`），设置页显示"写不进通知身份，已新建" |
| N8 | 多条审批都能看到 | 同一会话连发 3 个审批 → 右下角 3 条堆叠；连发 5 个 → 先 3 条，关掉 1 条后第 4 条补位 |
